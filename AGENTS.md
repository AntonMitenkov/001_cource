# AGENTS.md

Инструкции для AI-агента по генерации учебного курса.

---

## 1. Источник истины

При генерации контента агент обязан опираться исключительно на следующие файлы:

- `specs/` — спецификации курса, модулей и уроков
- `knowledge/` — база знаний (глоссарий, архитектурные паттерны, принципы)
- `templates/` — шаблоны для генерации материалов
- `AGENTS.md` — этот файл (правила работы)

Любые отклонения от этих источников запрещены.

---

## 2. Обязательный контекст перед генерацией лекции

Перед созданием любой лекции агент **должен** прочитать и проанализировать:

1. `specs/course-charter.md` — устав курса, цели и границы
2. `specs/syllabus.md` — общая структура и последовательность тем
3. `specs/lessons/lesson-XX.spec.md` — спецификация конкретного урока
4. `templates/lesson.md` — шаблон структуры лекции
5. `knowledge/glossary.md` — терминология и определения

**Порядок действий:**
```
1. Прочитать course-charter.md → понять цель курса
2. Прочитать syllabus.md → увидеть место урока в программе
3. Прочитать lesson-XX.spec.md → получить требования к уроку
4. Свериться с glossary.md → использовать корректную терминологию
5. Применить template/lesson.md → сгенерировать контент по шаблону
```

---

## 3. Запрещено

❌ **Менять спецификации** без явной команды пользователя.  
❌ **Писать контент лекции** без предварительно утверждённой `lesson-XX.spec.md`.  
❌ **Выдумывать факты, источники, точные цифры** или статистику. Если данных нет — указать "[требуется проверка]".  
❌ **Использовать одну базу данных как универсальное решение.** Всегда объяснять выбор через контекст и trade-offs.  
❌ **Описывать очередь сообщений как полноценную замену базе данных.** Это разные инструменты с разными гарантиями.  
❌ **Углубляться в код**, если это явно не требуется спецификацией. Курс фокусируется на архитектурном уровне.  
❌ **Использовать маркетинговые формулировки** ("революционный", "лучший на рынке", "единственно верный").  

---

## 4. Обязательные принципы

✅ **Курс готовит студентов к курсу "Базы данных".**  
   - Не заменять материал курса по БД, а создавать базу для его понимания.
   - Акцент на выборе типов СУБД, а не на синтаксисе SQL.

✅ **Структура каждой лекции:**
   - Цель обучения (learning objective)
   - Практическое задание (practice)
   - Глоссарий (ключевые термины)
   - Anti-patterns (типичные ошибки)
   - Мостик к следующей лекции (связь тем)

✅ **Архитектурные решения объясняются через trade-offs.**  
   - Нет "серебряных пуль".
   - Каждое решение имеет преимущества и недостатки.
   - Выбор зависит от контекста (NFR, бюджет, команда, масштаб).

✅ **Технологии — примеры, а не стандарты.**  
   - PostgreSQL, Kafka, Redis и др. приводятся как иллюстрации концепций.
   - Избегать фраз "используйте только X".
   - Подчёркивать, что выбор инструмента зависит от требований.

## 5. Формат материалов

- **Формат файлов:** Markdown (`.md`)
- **Язык:** Русский
- **Стиль:** Академичный, практико-ориентированный
  - Чёткие определения терминов
  - Примеры из реальной практики
  - Минимум воды, максимум сути
  - Структурированность (заголовки, списки, таблицы)

**Пример заголовка лекции:**
```markdown
# Лекция XX: [Название темы]

## Цель
[Чёткая формулировка результата обучения]

## Основной материал
[...]

## Практика
[Задание для закрепления]

## Глоссарий
- **Термин**: определение

## Anti-patterns
- [Ошибка]: почему это плохо

## Мостик к следующей лекции
[Связь с темой следующего занятия]
```

## 6. Рабочий процесс агента

1. **Анализ запроса** → определить тип задачи (лекция, практика, кейс, спецификация)
2. **Проверка контекста** → убедиться, что все обязательные файлы прочитаны
3. **Генерация черновика** → создать контент по шаблону
4. **Самопроверка** → свериться с правилами из раздела 3 и 4
5. **Вывод результата** → предоставить файл пользователю на проверку

---

## 7. Обработка ошибок

Если агент обнаруживает:
- Противоречия в спецификациях → запросить уточнение у пользователя
- Недостающие данные → пометить `[TODO: требуется уточнение]`
- Выход за рамки компетенции курса → указать на это явно
