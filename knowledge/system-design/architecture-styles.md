# Архитектурные стили (Architecture Styles)

## 1. Краткое определение
Архитектурный стиль — это набор принципов и ограничений, определяющих структуру системы, взаимодействие компонентов и организацию данных. Выбор стиля влияет на масштабируемость, поддерживаемость и стоимость владения системой.

## 2. Зачем это нужно в курсе
- Позволяет студентам понимать спектр доступных архитектурных решений.
- Помогает выбирать стиль под конкретные бизнес-требования и ограничения.
- Дает основу для сравнения подходов (trade-offs) в практических заданиях.
- Формирует понимание эволюции архитектуры от простого к сложному.

## 3. Ключевые понятия

### Monolith (Монолит)
- **Описание**: Единое приложение, содержащее весь бизнес-функционал, UI и работу с данными.
- **Плюсы**: Простота разработки, тестирования и деплоя на старте; транзакционность «из коробки».
- **Минусы**: Сложность масштабирования отдельных частей; риск «большого кома»; долгий цикл релиза при росте.
- **Когда использовать**: Стартапы, MVP, небольшие команды, простые домены.

### Modular Monolith (Модульный монолит)
- **Описание**: Монолит с четким разделением на модули по бизнес-возможностям, с ограниченным взаимодействием между ними.
- **Плюсы**: Сохраняет простоту деплоя монолита, но улучшает поддерживаемость и тестируемость.
- **Минусы**: Требует дисциплины от команды; риск деградации в «большой ком» без контроля зависимостей.
- **Когда использовать**: Зрелые продукты, где микросервисы избыточны, но нужна структура.

### Microservices (Микросервисы)
- **Описание**: Архитектура из независимо развертываемых сервисов, каждый из которых отвечает за свою бизнес-возможность.
- **Плюсы**: Независимое масштабирование; разные стеки технологий; отказоустойчивость.
- **Минусы**: Высокая операционная сложность; распределенные транзакции; сетевые задержки.
- **Когда использовать**: Крупные системы, несколько команд, высокие требования к доступности и масштабированию.

### Event-Driven Architecture (Событийно-ориентированная архитектура)
- **Описание**: Компоненты взаимодействуют через асинхронные события, публикуемые в брокер сообщений.
- **Плюсы**: Слабая связанность; возможность обработки пиковых нагрузок; гибкость интеграции.
- **Минусы**: Сложность отладки; eventual consistency; необходимость обработки дублей и потерь.
- **Когда использовать**: Интеграция разнородных систем, потоковая обработка данных, реактивные системы.

### Serverless (Бессерверная архитектура)
- **Описание**: Выполнение кода в управляемой среде облачного провайдера без явного управления серверами (FaaS).
- **Плюсы**: Оплата за фактическое использование; автоматическое масштабирование; нет ops-нагрузки.
- **Минусы**: Cold starts; vendor lock-in; сложность локальной отладки; лимиты времени выполнения.
- **Когда использовать**: Обработка событий, периодические задачи, непостоянные нагрузки.

### Hybrid (Гибридная архитектура)
- **Описание**: Комбинация нескольких стилей (например, модульный монолит + микросервисы для горячих участков).
- **Плюсы**: Гибкость; возможность постепенной миграции; оптимизация затрат.
- **Минусы**: Повышенная сложность понимания системы; разнородный стек мониторинга.
- **Когда использовать**: Легаси-системы в процессе модернизации; специфичные требования к отдельным модулям.

## 4. Как использовать при генерации лекций
- При описании эволюции системы показывай переход от монолита к микросервисам как ответ на рост нагрузки.
- Объясняй выбор стиля через призму NFR (производительность, доступность, стоимость).
- В кейсах предлагай студентам выбрать стиль и обосновать его через trade-offs.
- Подчеркивай, что не существует «серебряной пули» — каждый стиль имеет свои компромиссы.

## 5. Типичные ошибки
- ❌ **Микросервисы «на старте»**: Выбор сложной архитектуры для проекта с неопределенными требованиями.
- ❌ **Распределенный монолит**: Микросервисы с сильной связанностью и общими базами данных.
- ❌ **Игнорирование операционных затрат**: Неучет сложности мониторинга и деплоя распределенных систем.
- ❌ **События вместо транзакций**: Попытка заменить ACID-транзакции событиями там, где нужна строгая согласованность.
- ❌ **Serverless для долгих процессов**: Использование FaaS для задач с длительным временем выполнения.
