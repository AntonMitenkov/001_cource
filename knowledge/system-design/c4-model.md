# C4 Model

## 1. Краткое определение
C4 Model — это упрощенная нотация для визуализации архитектуры программного обеспечения на четырех уровнях абстракции: **Context** (Контекст), **Container** (Контейнер), **Component** (Компонент) и **Code** (Код). В рамках данного курса мы фокусируемся на первых двух уровнях для описания высокоуровневой архитектуры.

## 2. Зачем это нужно в курсе
- Дает студентам единый язык для описания архитектуры.
- Позволяет быстро набросать контекст системы без углубления в детали реализации.
- Используется как основной артефакт в практических заданиях по проектированию.
- Помогает отделить внешние зависимости от внутренней структуры решения.

## 3. Ключевые понятия

### Level 1: System Context Diagram (Системный контекст)
- **Цель**: Показать систему как «черный ящик» в окружении пользователей и внешних систем.
- **Элементы**:
  - **Person**: Пользователь или роль (например, «Менеджер», «Клиент»).
  - **Software System**: Наша система или внешние системы (платежный шлюз, почтовый сервис).
  - **Relationship**: Стрелки с подписями, описывающие взаимодействие (например, «отправляет заказ», «возвращает статус»).
- **Правило**: Никаких технологий внутри, только границы системы и связи.

### Level 2: Container Diagram (Контейнеры)
- **Цель**: Раскрыть «черный ящик» и показать основные технологические блоки.
- **Элементы**:
  - **Container**: Отдельно развертываемая единица (Web App, Mobile App, API Service, Database, Message Broker). *Важно: не путать с Docker-контейнером.*
  - **Technology**: Стек технологий для каждого контейнера (например, React, Java/Spring, PostgreSQL).
- **Правило**: Показывать только значимые контейнеры, игнорировать внутренние компоненты.

> **Примечание**: Уровни Component и Code в курсе не рассматриваются, так как они относятся к детальному дизайну и реализации, а не к архитектурному проектированию.

## 4. Как использовать при генерации лекций
- При описании кейса всегда начинай с **System Context**, чтобы обозначить границы задачи.
- Для разбора архитектурных стилей используй **Container Diagram**, чтобы показать распределение ответственности (например, где лежит логика: в монолите или микросервисах).
- В шаблонах практических заданий требуй от студентов создания диаграммы C4 Level 1 и Level 2.
- Используй Mermaid.js для рендеринга схем в Markdown.

## 5. Типичные ошибки
- ❌ **Смешивание уровней**: Попытка показать базу данных и внешний банк на одной диаграмме контекста без выделения центральной системы.
- ❌ **Избыточность на уровне контейнеров**: Изображение внутренних классов или функций вместо целых приложений/сервисов.
- ❌ **Отсутствие технологий**: Контейнеры без указания стека (непонятно, это фронтенд или бэкенд).
- ❌ **Двусторонние стрелки без пояснений**: Всегда подписывай, кто инициирует запрос и какой данные передаются.
- ❌ **Игнорирование внешних зависимостей**: Забывают нарисовать смежные системы (LDAP, Payment Gateway), с которыми интеграция критична.
