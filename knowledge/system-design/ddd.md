# Domain-Driven Design (DDD)

## 1. Краткое определение
Domain-Driven Design (DDD) — это подход к разработке ПО, который фокусируется на глубоком понимании предметной области (domain) и отражении её структуры в коде и архитектуре системы. DDD предоставляет инструменты для работы со сложными доменами через единый язык и четкие границы контекстов.

## 2. Зачем это нужно в курсе
- Помогает студентам связывать бизнес-требования с техническими решениями.
- Дает методы декомпозиции сложных систем на управляемые части.
- Формирует навык общения с заказчиками на их языке.
- Позволяет проектировать масштабируемые архитектуры через правильное разделение ответственности.

## 3. Ключевые понятия

### Ubiquitous Language (Единый язык)
- **Определение**: Общий словарь терминов, используемый разработчиками и экспертами предметной области.
- **Зачем**: Устраняет недопонимание между бизнесом и техникой; каждый термин имеет одно значение.
- **Пример**: «Заказ» (Order) всегда означает оформленную заявку клиента, а не черновик в корзине.
- **Правило**: Если термин меняется в коде, он должен измениться в документации и речи, и наоборот.

### Bounded Context (Ограниченный контекст)
- **Определение**: Граница, внутри которой работает определенная модель предметной области со своим языком.
- **Зачем**: Позволяет разным частям системы использовать одни и те же термины по-разному без конфликтов.
- **Пример**: «Продукт» в контексте «Каталог» — это описание и цена, а в контексте «Доставка» — габариты и вес.
- **Правило**: Одна модель — один контекст. Не пытайтесь создать универсальную модель на всю систему.

### Context Map (Карта контекстов)
- **Определение**: Диаграмма, показывающая взаимосвязи между ограниченными контекстами.
- **Типы связей**:
  - **Partnership**: Контексты сотрудничают на равных.
  - **Shared Kernel**: Общая часть модели между контекстами.
  - **Customer-Supplier**: Один контекст зависит от другого.
  - **Conformist**: Зависимый контекст вынужден следовать модели поставщика.
  - **Anti-Corruption Layer (ACL)**: Слой защиты от чужой модели.
  - **Open Host Service**: Публикация API для всех.
  - **Published Language**: Общий формат обмена (например, JSON Schema).
- **Зачем**: Визуализирует зависимости и помогает планировать интеграцию.

### Связь с данными
- **Правило**: Каждый ограниченный контекст должен иметь свою базу данных (Database per Context).
- **Запрет**: Прямые JOIN между таблицами разных контекстов.
- **Интеграция**: Только через API или события (Event-Driven).
- **Полиглотное хранение**: Разные контексты могут использовать разные типы БД (SQL, NoSQL) под свои нужды.

## 4. Как использовать при генерации лекций
- При описании кейса сначала определи ключевые термины (Ubiquitous Language).
- Разбивай систему на Bounded Contexts на основе бизнес-процессов, а не технических слоев.
- Используй Context Map для показа интеграции между сервисами в микросервисной архитектуре.
- Подчеркивай, что границы контекстов часто становятся границами микросервисов.
- В практических заданиях требуй от студентов выделения контекстов и описания связей между ними.

## 5. Типичные ошибки
- ❌ **Единая модель на всё**: Попытка создать универсальную сущность «Пользователь» для всех контекстов.
- ❌ **Технические границы вместо бизнес-логических**: Разделение на контексты по слоям (UI, Backend, DB) вместо бизнес-возможностей.
- ❌ **Игнорирование ACL**: Прямое заимствование чужих моделей данных без адаптера.
- ❌ **Общая база данных**: Несколько контекстов пишут в одни и те же таблицы, создавая скрытую связанность.
- ❌ **DDD для CRUD**: Применение сложных паттернов DDD там, где достаточно простого скрипта или формы.
