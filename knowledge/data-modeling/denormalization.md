# Денормализация

## Определение

Денормализация — осознанное введение избыточности в нормализованную схему данных для повышения производительности чтения.

**Важно:** денормализация — это НЕ ошибка проектирования. Это архитектурное решение, которое должно быть задокументировано в ADR.

## Когда допустима

| Ситуация | Обоснование |
|:---|:---|
| Read-heavy нагрузка | Частые SELECT с множеством JOIN |
| Избежание JOIN | Объединение данных из 5+ таблиц в один запрос |
| Кэширование агрегированных данных | Предвычисленные суммы, счётчики |
| Аналитика (OLAP) | Колоночное хранение, звёздная схема |
| Поисковые индексы | Дублирование данных для полнотекстового поиска |

## Компромиссы

| Аспект | Нормализация | Денормализация |
|:---|:---|:---|
| Избыточность | Минимальная | Повышенная |
| Аномалии обновления | Нет | Возможны |
| Производительность чтения | Ниже (JOIN) | Выше |
| Производительность записи | Выше | Ниже (обновление копий) |
| Целостность | Обеспечена СУБД | Требует приложения/триггеров |
| Сложность схемы | Высокая (много таблиц) | Ниже (меньше JOIN) |

## Риск рассинхронизации

При денормализации данные хранятся в нескольких местах. Если обновление одного экземпляра не синхронизировано с другим, возникает рассинхронизация.

**Меры снижения риска:**
- Триггеры для автоматической синхронизации
- Асинхронное обновление (события, очереди)
- Регулярная проверка консистентности (reconciliation jobs)
- TTL для кэшированных данных

## Обязательное документирование

Каждая денормализация должна быть зафиксирована в ADR:
ADR-005: Денормализация имени клиента в таблице заказов
Контекст
Запрос списка заказов с именем клиента требует JOIN 3 таблиц.
Нагрузка: 5000 запросов/сек.
Решение
Дублировать имя клиента в таблицу заказов.
Последствия
Снижение latency запроса с 150мс до 30мс
Необходимость синхронизации при смене имени
Риск рассинхронизации при сбое
