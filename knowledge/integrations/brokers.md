# Message Brokers

## Message Broker

Промежуточное программное обеспечение, принимающее сообщения от
производителей и доставляющее их потребителям. Брокер берёт на себя
задачи маршрутизации, хранения, подтверждения и повторной доставки.

Основные модели:
- **Point-to-point (очередь)**: одно сообщение → один потребитель.
- **Publish/Subscribe (pub/sub)**: одно сообщение → множество подписчиков.

Примеры: RabbitMQ, Apache Kafka (гибрид), NATS, Apache Pulsar,
ActiveMQ Artemis, AWS SNS/SQS, Azure Service Bus.

## Pub/Sub

Модель, при которой издатель (publisher) отправляет сообщение в тему
(topic), а подписчики (subscribers) получают копии.

Свойства:
- Издатель не знает подписчиков и наоборот.
- Масштабирование подписчиков не влияет на издателя.
- Каждая подписка может иметь собственный offset/cursor.

Применение: широковещательные события, фан-аут, CQRS-проекции,
уведомления.

Примеры: Google Cloud Pub/Sub, AWS SNS, Redis Pub/Sub, NATS JetStream.

## Routing (маршрутизация)

Механизм определения, какому потребителю или очереди направить сообщение.

Виды маршрутизации:
- **Direct** — по точному ключу (routing key).
- **Topic / wildcard** — по шаблону (`order.*.created`).
- **Fan-out** — копия во все привязанные очереди.
- **Content-based** — по содержимому заголовков или тела.

Пример: в RabbitMQ exchange-типы `direct`, `topic`, `fanout`,
`headers` реализуют перечисленные стратегии.

## Acknowledgement (подтверждение)

Механизм, при котором потребитель явно сообщает брокеру об успешной
обработке сообщения.

Варианты:
- **Auto-ack**: брокер считает сообщение доставленным сразу после отправки.
- **Manual ack**: потребитель подтверждает после бизнес-логики.
- **Nack / reject**: сигнал о невозможности обработки → requeue или DLQ.

Ack — ключевой элемент гарантий доставки at-least-once.

## Persistence (durability)

Сохранение сообщений на диск для переживания перезагрузки брокера.

Уровни:
- **Transient**: только в памяти (минимальная задержка).
- **Durable**: запись в WAL/journal перед подтверждением приёма.
- **Replicated**: копирование на несколько узлов кластера.

Выбор уровня — компромисс между задержкой, пропускной способностью
и гарантиями.

Пример: RabbitMQ `persistent` messages + quorum queues;
Kafka `acks=all` + `min.insync.replicas`.

## Retry в контексте брокера

Если потребитель не подтвердил сообщение или вернул nack:
1. Брокер может немедленно повторить доставку (requeue).
2. Либо задержать повтор на интервал (delayed retry).
3. После исчерпания попыток — направить в DLQ.

Важно: повтор должен быть идемпотентным на стороне потребителя
(см. лекцию по outbox/inbox).

## Dead Letter Queue (DLQ)

Специальная очередь, куда попадают сообщения, которые не удалось
обработать после заданного числа попыток.

Назначение DLQ:
- Изоляция «ядовитых» сообщений.
- Ручной разбор и корректировка.
- Мониторинг и алертинг по количеству «мёртвых» писем.
- Повторная отправка после исправления бага.

Примеры поддержки: RabbitMQ DLX (Dead Letter Exchange),
AWS SQS Redrive Policy, Azure Service Bus DLQ, Kafka через
отдельный `.dlq` топик.

Подробно — см. файл `dlq-retry.md`.
