# DLQ и Retry: операционные паттерны

## Retry Policy (политика повторных попыток)

Набор правил, определяющих, когда и как повторять обработку сообщения
или вызов при сбое.

Параметры политики:
- Максимальное число попыток.
- Интервал между попытками (фиксированный, экспоненциальный,
  с джиттером).
- Какие ошибки считаются retryable (таймаут, 5xx, сетевой сбой),
  а какие — нет (4xx, ошибка валидации).
- Общий таймаут (deadline) на все попытки.

Примеры реализации: Spring Retry, Polly (.NET), Resilience4j,
gRPC retry policy, AWS SDK built-in retry.

## Exponential Backoff

Стратегия увеличения задержки между попытками по экспоненте:
delay = base_interval × 2^(attempt − 1) [+ jitter]

Зачем:
- Даёт сбойному сервису время восстановиться.
- Снижает вероятность «retry storm» при массовом сбое.
- Jitter (случайная добавка) предотвращает синхронизацию волн
  повторов от множества клиентов.

Типичные значения: base = 100 мс – 1 с, множитель ×2, cap = 30–60 с,
jitter = 0–50 % от текущей задержки.

## Dead Letter Queue (DLQ)

Очередь для сообщений, которые невозможно обработать после исчерпания
retry-попыток.

Жизненный цикл сообщения:
1. Первое попадание в основную очередь.
2. N попыток обработки с backoff.
3. Все попытки неудачны → сообщение перемещается в DLQ.
4. Оператор/автоматика разбирает DLQ.

Что хранить вместе с сообщением в DLQ:
- Оригинальное тело.
- Заголовки и метаданные.
- Причину последней ошибки (stack trace / error code).
- Количество попыток и таймстемпы.
- Идентификатор исходного источника.

Примеры: RabbitMQ Dead Letter Exchange, AWS SQS Redrive,
Azure Service Bus DLQ, Kafka `topic.dlq` (по соглашению).

## Poison Message

Сообщение, которое принципиально не может быть успешно обработано:
- Повреждённый формат / несовместимая схема.
- Ссылка на несуществующий ресурс.
- Бизнес-правило, делающее обработку невозможной.
- Баг в коде потребителя, не связанный с временным сбоем.

Стратегия работы с poison message:
- Не бесконечно повторять → расходует ресурсы.
- Классифицировать: retryable vs non-retryable.
- Non-retryable сразу направлять в DLQ.
- В DLQ — тегировать для ручного или автоматического разбора.

## Мониторинг

Ключевые метрики:
- Глубина основной очереди и DLQ (lag).
- Возраст старейшего необработанного сообщения.
- Число retry-попыток в единицу времени.
- Доля сообщений, попавших в DLQ (poison rate).
- Время обработки (processing latency) по перцентилям.
- Количество nack / reject.

Алерты:
- Глубина DLQ > 0 (или > порога) за окно.
- Возраст сообщения в очереди > SLA.
- Резкий рост retry rate (признак каскадного сбоя).
- Потребитель не подтверждает сообщения (consumer stall).

Инструменты наблюдения: Prometheus + Grafana, Datadog, CloudWatch,
Jaeger/Zipkin для распределённого трейсинга пути сообщения.

## Operational Considerations (операционные аспекты)

1. **Определение SLA обработки.** Сколько времени сообщение может
   находиться в очереди до эскалации.

2. **Ёмкость DLQ.** DLQ не должна быть «чёрной дырой». Регулярный
   процесс разбора: исправление → повторная публикация (replay) или
   архивация.

3. **Повторная отправка из DLQ.** Инструменты replay должны сохранять
   исходные заголовки и не дублировать уже обработанные сообщения
   (inbox на стороне потребителя).

4. **Версионирование схем.** Несовместимость схемы — частая причина
   poison message. Schema Registry и backward compatibility снижают риск.

5. **Изоляция токсичных потоков.** При массовом сбое downstream-сервиса
   полезно временно приостановить consumption или перенаправить поток
   в карантинную очередь, чтобы не забивать DLQ.

6. **Тестирование.** Включать в интеграционные тесты сценарии:
   - Таймаут downstream.
   - Повреждённое сообщение.
   - Дубликат доставки.
   - Поведение при переполнении очереди.

7. **Документация runbook.** Для каждой очереди и DLQ описать:
   кто отвечает, как диагностировать, как replay-ить, когда эскалировать.

8. **Стоимость хранения.** Очереди с долгим TTL и DLQ без очистки
   потребляют диск и память. Политики retention должны быть явными.
