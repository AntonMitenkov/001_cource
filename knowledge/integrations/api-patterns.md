# Паттерны и подходы к построению API

## REST (Representational State Transfer)

Архитектурный стиль, в котором взаимодействие строится вокруг ресурсов и
стандартных HTTP-методов (GET, POST, PUT, PATCH, DELETE).

Ключевые принципы:
- Ресурс идентифицируется URI.
- Состояние передаётся в каждом запросе (stateless).
- Семантика определяется методом HTTP и кодом ответа.
- Представление ресурса отделено от его хранения.

REST подходит, когда нужна широкая совместимость, понятная модель CRUD
и экосистема инструментов (кэширование, проксирование, документация).

Примеры экосистемы: Spring Boot WebFlux, Express.js, FastAPI.

## gRPC

Фреймворк удалённого вызова процедур поверх HTTP/2 с бинарной
сериализацией (Protocol Buffers).

Особенности:
- Строгая типизация контракта через `.proto`-файлы.
- Четыре модели вызова: unary, server streaming, client streaming,
  bidirectional streaming.
- Низкая задержка, компактный размер сообщений.
- Встроенная генерация клиентских и серверных заглушек.

Применение: межсервисное общение внутри кластера, высоконагруженные
внутренние API.

Примеры: gRPC (официальные реализации для Go, Java, Python, .NET),
Envoy как gRPC-aware прокси.

## GraphQL

Язык запросов и среда исполнения, позволяющая клиенту декларировать
точную структуру нужных данных.

Особенности:
- Единая точка входа (endpoint).
- Клиент управляет объёмом и глубиной выборки (нет over-fetching /
  under-fetching).
- Строгая типизированная схема (schema-first).
- Мутации для изменений, подписки для реактивных обновлений.

Применение: мобильные и SPA-клиенты, агрегация данных из нескольких
источников.

Примеры: Apollo Server, Hasura, graphql-java.

## API Gateway

Единая точка входа для внешних клиентов перед множеством микросервисов.

Ответственности:
- Маршрутизация и балансировка запросов.
- Аутентификация и авторизация.
- Rate limiting, throttling, quota.
- Трансформация протоколов (REST → gRPC и наоборот).
- Агрегация ответов.
- Наблюдаемость: логирование, трейсинг, метрики.

Примеры: Kong, AWS API Gateway, Traefik, Envoy Gateway, Spring Cloud Gateway.

## BFF (Backend For Frontend)

Узкий шлюз, ориентированный на конкретный тип клиента (web, mobile,
partner). В отличие от универсального API Gateway, BFF знает специфику
представления данных для своего клиента.

Когда уместен:
- Разные клиенты требуют принципиально разных агрегатов данных.
- Нужно скрыть сложность внутренних сервисов.
- Команда фронтенда хочет контролировать контракт без влияния на бэкенд.

Пример: отдельный BFF для мобильного приложения, который отдаёт
денормализованный JSON и скрывает 12 внутренних вызовов.

## Contract-First подход

Контракт взаимодействия (OpenAPI/Swagger, AsyncAPI, `.proto`, GraphQL
SDL) проектируется и фиксируется до реализации.

Преимущества:
- Параллельная разработка клиента и сервера по согласованному контракту.
- Автоматическая генерация документации, заглушек, тестов.
- Явная точка для code review и governance.
- Упрощение эволюции API.

Инструменты: Swagger/OpenAPI 3.x, AsyncAPI, buf (для protobuf),
Apollo Schema Registry.

## Версионирование API

Стратегии:
- **URI-версия**: `/api/v1/orders`, `/api/v2/orders`.
- **Заголовок**: `Accept: application/vnd.example.v2+json`.
- **Query-параметр**: `/orders?api-version=2024-06`.
- **Контрактная версия**: отдельный мажорный тег в gRPC / GraphQL
  schema versioning.

Выбор стратегии зависит от аудитории API (публичное vs внутреннее)
и допустимой сложности маршрутизации.

## Обратная совместимость (Backward Compatibility)

Правила сохранения совместимости:
- Не удалять и не переименовывать существующие поля.
- Новые поля добавлять как опциональные.
- Не менять семантику существующих полей.
- Для gRPC: не переиспользовать номера полей.
- Для баз данных событий: эволюция схемы через Schema Registry.

Когда обратная совместимость невозможна — вводим новую мажорную версию
и публикуем политику deprecation с явным сроком жизни старой версии.

Примеры инструментов контроля: Buf breaking-change linting,
openapi-diff, Pact (contract testing).
