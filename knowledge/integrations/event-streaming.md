# Event Streaming

## Event Log

Неизменяемая, упорядоченная по времени последовательность событий.
Каждое событие получает монотонно возрастающий идентификатор (offset)
и не может быть изменено или удалено в рамках политики хранения.

Свойства:
- Append-only: новые записи добавляются в конец.
- Неизменяемость: прочитанное событие не меняется.
- Долговременное хранение: от дней до бесконечности.
- Детерминированный порядок в рамках партиции.

Примеры: Apache Kafka topic, Apache Pulsar topic, AWS Kinesis
Data Stream, Azure Event Hubs.

## Event Streaming

Парадигма обработки данных, в которой события непрерывно публикуются,
хранятся, читаются и обрабатываются потоками в реальном времени.

Отличие от классического обмена сообщениями:
- Акцент на потоке как источнике истины.
- Потребитель сам управляет позицией чтения (offset).
- Поддержка оконных агрегаций, joins, CEP (Complex Event Processing).

Примеры платформ: Apache Kafka + Kafka Streams, Apache Flink,
Apache Pulsar Functions, AWS Kinesis Analytics.

## Replay (повторное чтение)

Возможность перечитать историю событий с произвольного offset.

Применение:
- Восстановление состояния нового потребителя.
- Исправление ошибки в логике обработки (пересчёт проекций).
- Аудит и расследование инцидентов.
- Тестирование на исторических данных.

Replay возможен благодаря тому, что брокер не удаляет событие
сразу после чтения (в отличие от классической очереди).

## Partitioning (партиционирование)

Разделение логического потока на независимые партиции для
параллелизма и масштабируемости.

Принципы:
- Ключ партиционирования (partition key) определяет, в какую партицию
  попадёт событие.
- Внутри партиции порядок гарантирован; между партициями — нет.
- Количество партиций задаёт верхний предел параллелизма потребителей.

Пример: `order_id` как ключ → все события одного заказа в одной партиции.

## Ordering (порядок событий)

Гарантии порядка:
- **Глобальный порядок** — одна партиция; ограничивает пропускную
  способность.
- **Порядок по ключу** — партиционирование по сущности; баланс между
  порядком и параллелизмом.
- **Без гарантий порядка** — максимальная пропускная способность.

При проектировании важно явно определить, какой уровень порядка
требуется бизнес-логике.

## Consumer Group

Логическая группа потребителей, совместно читающих один поток.

Свойства:
- Каждая партиция назначается ровно одному участнику группы
  (в модели Kafka).
- Добавление/удаление участника вызывает rebalance.
- Каждая группа хранит собственный offset → независимый прогресс.
- Несколько групп читают один поток без влияния друг на друга
  (pub/sub поверх логa).

Пример: сервис аналитики и сервис уведомлений — разные consumer
group на одном топике `orders.events`.

## Отличие Event Streaming от Message Queue

| Аспект | Message Queue | Event Streaming |
|---|---|---|
| Модель потребления | Сообщение удаляется после ack | Событие остаётся, читается по offset |
| Хранение | Краткосрочный буфер | Долгосрочный лог |
| Порядок | FIFO в рамках очереди | Гарантирован в рамках партиции |
| Replay | Как правило, нет | Да, с произвольного offset |
| Масштабирование чтения | Конкурирующие потребители | Consumer groups, независимый offset |
| Семантика | «Выполни задачу» | «Вот факт, реагируй если нужно» |
| Пример | RabbitMQ, SQS | Kafka, Pulsar, Kinesis |

Обе модели не исключают друг друга: в одной системе очередь может
использоваться для task-обработки, а event log — для аудита и проекций.
