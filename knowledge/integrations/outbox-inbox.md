# Transactional Outbox и Inbox Pattern

## Проблема согласованности

Бизнес-операция часто включает два действия:
1. Изменение состояния в базе данных (например, создание заказа).
2. Публикация события во внешний брокер (например, `OrderCreated`).

Если выполнять их в разных системах, возникает окно несогласованности:
- БД зафиксирована, но событие не отправлено → подписчики не узнали.
- Событие отправлено, но транзакция БД откатилась → подписчики
  получили ложный факт.

## Transactional Outbox

Паттерн, при котором событие записывается в **ту же транзакцию**,
что и бизнес-изменение.

Схема работы:
1. В рамках одной БД-транзакции:
   - Обновляются бизнес-таблицы.
   - В таблицу `outbox` вставляется строка с событием.
2. Транзакция фиксируется атомарно.
3. Отдельный процесс (poller, CDC-коннектор) читает `outbox` и
   публикует события в брокер.
4. После успешной публикации строка в `outbox` помечается отправленной
   или удаляется.

Гарантия: событие не потеряется и не появится раньше бизнес-изменения.

Варианты доставки из outbox:
- Поллинг таблицы по расписанию.
- CDC (Change Data Capture): Debezium, Maxwell читают WAL/transaction
  log и транслируют изменения outbox-таблицы в Kafka.

Примеры: Debezium + Kafka Connect, Ballerina/Spring Integration
outbox-адаптеры.

## Inbox Pattern

Паттерн на стороне потребителя, обеспечивающий идемпотентную обработку.

Схема работы:
1. Потребитель получает событие.
2. В рамках одной локальной транзакции:
   - Проверяет таблицу `inbox`: обработан ли уже `message_id`?
   - Если нет — выполняет бизнес-логику и вставляет `message_id`
     в `inbox`.
   - Если да — пропускает (дубликат).
3. Фиксирует транзакцию.

Таблица `inbox` периодически очищается от записей старше
гарантийного окна (например, 7 дней).

## Идемпотентность

Свойство операции: повторное выполнение с тем же входом не изменяет
результат.

В контексте интеграций:
- Каждое событие несёт уникальный идентификатор (`event_id`).
- Потребитель дедуплицирует по `event_id` (через inbox или иной
  idempotency store).
- Внешние вызовы проектируются идемпотентными (idempotency key
  в заголовке запроса).

Идемпотентность превращает at-least-once в effectively-once с точки
зрения бизнес-эффекта.

## At-Least-Once Delivery

Гарантия: каждое сообщение будет доставлено потребителю **хотя бы
один раз**, но возможны дубликаты.

Почему не exactly-once «из коробки»:
- Сеть ненадёжна: ack может потеряться → брокер повторит доставку.
- Потребитель может упасть между обработкой и подтверждением.
- Распределённые транзакции (2PC) дороги и хрупки.

Стратегия: принимаем at-least-once как транспортную гарантию и
компенсируем дубликаты на уровне бизнес-логики (inbox, идемпотентные
операции).

## Как согласовать бизнес-изменение и публикацию события

Итоговый чек-лист для лекции:
1. **Одна транзакция** для бизнес-данных и записи в outbox.
2. **Асинхронная доставка** из outbox в брокер (poller или CDC).
3. **At-least-once** на участке outbox → брокер → потребитель.
4. **Inbox + идемпотентность** на стороне потребителя.
5. **Мониторинг**: метрики глубины outbox, задержки доставки,
   количества дубликатов в inbox.

Такая связка устраняет dual-write problem без распределённых
транзакций и сохраняет автономность сервисов.
