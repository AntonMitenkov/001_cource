# Типы СУБД: обзор классов

## Relational (Реляционные)

**Назначение:** Хранение структурированных данных с поддержкой транзакций,
сложных запросов и обеспечения целостности через связи между таблицами.

**Типовые задачи:**
- Финансовые операции (банки, платежи)
- CRM/ERP системы
- Инвентаризация и управление запасами
- Системы с сложными связями и бизнес-правилами

**Примеры:** PostgreSQL, MySQL, Oracle Database, Microsoft SQL Server,
SQLite

**Когда использовать:**
- Требуется ACID-транзакции
- Данные хорошо структурированы и схемы стабильны
- Нужны сложные JOIN-запросы и агрегации
- Важна целостность связей

**Когда не использовать:**
- Данные слабо структурированы или схема часто меняется
- Требуется горизонтальное масштабирование на сотни узлов
- Простые операции чтения/записи без сложных запросов
- Миллиарды записей с высокой нагрузкой записи

---

## Key-Value

**Назначение:** Хранение простых пар ключ-значение с минимальной задержкой
доступа.

**Типовые задачи:**
- Кэширование (сессии, конфигурации)
- Rate limiting, счётчики
- Краткосрочное хранение временных данных
- Быстрый lookup по уникальному ключу

**Примеры:** Redis, Memcached, Amazon DynamoDB, etcd

**Когда использовать:**
- Нужна максимальная скорость чтения/записи
- Данные простые (нет вложенных структур)
- Доступ всегда по ключу
- Допустима eventual consistency (для многих реализаций)

**Когда не использовать:**
- Нужны сложные запросы, фильтрация, JOIN
- Требуется строгая схема или валидация данных
- Нужны вторичные индексы
- Объёмы данных требуют аналитической обработки

---

## Document (Документо-ориентированные)

**Назначение:** Хранение полуструктурированных данных в виде документов
(JSON, BSON, XML) с гибкой схемой.

**Типовые задачи:**
- Каталоги товаров, профили пользователей
- Контент-менеджмент системы
- API-бэкенды с изменчивыми требованиями
- Логирование и сбор событий

**Примеры:** MongoDB, CouchDB, Amazon DocumentDB, Couchbase

**Когда использовать:**
- Схема данных нестабильна или вариативна
- Данные естественно представляются как документы
- Нужна горизонтальная масштабируемость
- Вложенные структуры удобнее плоских таблиц

**Когда не использовать:**
- Требуется множество JOIN между коллекциями
- Строгая схема обязательна (compliance, регуляторика)
- Сложные транзакции с множеством документов
- Высокая нагрузка на запись с частыми обновлениями вложенных полей

---

## Wide-Column (Ширококолоночные)

**Назначение:** Хранение огромных объёмов данных с высокой нагрузкой
записи и чтения по ключу.

**Типовые задачи:**
- IoT-данные (сенсоры, метрики)
- Социальные сети (ленты, сообщения)
- Time-series данные
- Глобально распределённые системы

**Примеры:** Apache Cassandra, ScyllaDB, HBase, Google Bigtable

**Когда использовать:**
- Петабайтные объёмы данных
- Требуется линейное горизонтальное масштабирование
- Запись преобладает над чтением
- Нужна геораспределённость и multi-datacenter репликация
- Допустима eventual consistency

**Когда не использовать:**
- Нужны сложные запросы и JOIN
- Частые обновления существующих записей
- Требуется строгая согласованность
- Небольшие объёмы данных (overhead архитектуры)

---

## Graph (Графовые)

**Назначение:** Моделирование и хранение данных как графов (узлы, рёбра,
свойства) для эффективной работы со связями.

**Типовые задачи:**
- Социальные сети (друзья, подписки)
- Рекомендательные системы
- Обнаружение мошенничества (связи между транзакциями)
- Knowledge graphs, онтологии
- Анализ сетевой топологии

**Примеры:** Neo4j, Amazon Neptune, JanusGraph, ArangoDB, TigerGraph

**Когда использовать:**
- Связи между сущностями важнее самих сущностей
- Нужно обходить граф на несколько уровней глубины
- Сложные паттерны связей (пути, циклы)
- Рекомендации на основе графовых алгоритмов

**Когда не использовать:**
- Простые CRUD-операции без сложных связей
- Большие объёмы данных с минимальным числом связей
- Нужна агрегация по множеству записей
- Стоимость инфраструктуры не окупается сложностью

---

## Time-Series

**Назначение:** Эффективное хранение и запросы к временным рядам
(метрики, события, телеметрия).

**Типовые задачи:**
- Мониторинг инфраструктуры (CPU, память, сеть)
- Финансовые тикеры и котировки
- IoT-сенсоры
- Application performance monitoring

**Примеры:** InfluxDB, TimescaleDB, Prometheus, VictoriaMetrics,
QuestDB, TDengine

**Когда использовать:**
- Данные имеют временную метку (timestamp) как ключевое измерение
- Высокая скорость записи (миллионы точек в секунду)
- Агрегации по временным окнам (среднее, min/max, percentiles)
- Нужно эффективное сжатие временных рядов
- Автоматическое удаление старых данных (retention policies)

**Когда не использовать:**
- Данные не имеют временной природы
- Нужны сложные JOIN с другими типами данных
- Частые обновления исторических записей
- Требования к ACID-транзакциям

## Search Engine (Поисковые движки)

**Назначение:** Полнотекстовый поиск, нечёткое соответствие, фасетная
навигация и аналитика по тексту.

**Типовые задачи:**
- Поиск по каталогам товаров
- Лог-аналитика
- Поиск документов с ранжированием релевантности
- Автодополнение и suggest

**Примеры:** Elasticsearch, Apache Solr, OpenSearch, Meilisearch,
Typesense

**Когда использовать:**
- Нужен полнотекстовый поиск с токенизацией и стеммингом
- Нечёткий поиск (опечатки, синонимы)
- Фасетная фильтрация (категории, бренды, ценовые диапазоны)
- Near real-time аналитика по логам

**Когда не использовать:**
- Как primary storage для бизнес-данных (это secondary index)
- Нужна строгая согласованность и транзакции
- Сложные обновления существующих записей
- Хранение больших бинарных объектов

## Vector DB (Векторные базы данных)

**Назначение:** Хранение и поиск по векторным представлениям (embeddings)
с использованием similarity search.

**Типовые задачи:**
- Semantic search (поиск по смыслу, а не ключевым словам)
- Рекомендательные системы на основе embeddings
- RAG (Retrieval-Augmented Generation) для LLM
- Image/similarity search
- Anomaly detection

**Примеры:** Pinecone, Weaviate, Milvus, Qdrant, Chroma, pgvector
(PostgreSQL extension)

**Когда использовать:**
- Работа с embeddings (от LLM, CNN, других моделей)
- Поиск ближайших соседей (k-NN, ANN)
- Semantic search поверх текстовых или мультимедийных данных
- Интеграция с AI/ML pipeline

**Когда не использовать:**
- Традиционные CRUD-операции с бизнес-данными
- Требуется точное соответствие (exact match), а не similarity
- Данные не имеют векторного представления
- Высокие требования к latency (vector search медленнее B-tree)

## Object Storage (Объектное хранилище)

**Назначение:** Хранение больших объёмов неструктурированных данных
(файлы, изображения, видео, бэкапы) как объектов с метаданными.

**Типовые задачи:**
- Хранение медиа-контента (фото, видео)
- Бэкапы и архивы
- Статические ресурсы для веб-приложений
- Data lake для сырых данных

**Примеры:** Amazon S3, Google Cloud Storage, Azure Blob Storage,
MinIO, Ceph

**Когда использовать:**
- Большие файлы (от МБ до ТБ)
- Append-only или immutable данные
- Нужна географическая репликация и durability (99.999999999%)
- Доступ по HTTP/HTTPS (REST API)
- Экономичное долгосрочное хранение

**Когда не использовать:**
- Частые обновления существующих объектов (objects are immutable)
- Транзакционные операции
- Нужна файловая система с произвольным доступом (используйте EFS/NFS)
- Низколатентный доступ к маленьким объектам

---

## Data Warehouse / Lakehouse

**Назначение:** Аналитическая обработка больших объёмов данных с сложных
запросами и агрегациями.

**Типовые задачи:**
- Business intelligence и отчётность
- ETL/ELT pipeline
- Машинное обучение на исторических данных
- Data analytics и data science

**Примеры:**
- **Data Warehouse:** Snowflake, Google BigQuery, Amazon Redshift,
  ClickHouse (OLAP)
- **Lakehouse:** Databricks, Apache Hudi, Apache Iceberg, Delta Lake

**Когда использовать:**
- Аналитические запросы по историческим данным
- Объёмы в терабайты и петабайты
- Сложные агрегации и JOIN между множеством таблиц
- Data pipeline для консолидации данных из разных источников
- Нужна columnar storage и vectorized query execution

**Когда не использовать:**
- OLTP-нагрузка (транзакционные операции)
- Real-time требования (latency в секундах)
- Маленькие объёмы данных (overhead инфраструктуры)
- Частые обновления отдельных записей

---

## Event Streaming Platform (Платформы потоковой обработки событий)

**Назначение:** Приём, хранение и обработка потоков событий в реальном
времени.

**Типовые задачи:**
- Event-driven architecture
- Real-time analytics и мониторинг
- Stream processing (CEP — Complex Event Processing)
- Message broker для распределённых систем
- CDC (Change Data Capture)

**Примеры:** Apache Kafka, Apache Pulsar, Amazon Kinesis, Azure Event
Hubs, Redpanda

**Когда использовать:**
- Нужен event log как источник истины
- Требуется replay истории событий
- Real-time обработка потоков данных
- Pub/sub с высокой пропускной способностью
- Интеграция множества систем через события

**Когда не использовать:**
- Как primary storage для CRUD-операций
- Нужны сложные запросы и JOIN
- Требование к мгновенной согласованности (eventual consistency)
- Простые сценарии обмена сообщениями (используйте RabbitMQ/SQS)

## Сводная таблица выбора

| Критерий | Реляционные | NoSQL | Специализированные |
|---|---|---|---|
| Схема | Строгая | Гибкая | Зависит от типа |
| Масштабирование | Вертикальное + read replicas | Горизонтальное | Зависит от типа |
| Consistency | Strong | Eventual (часто) | Зависит от типа |
| Запросы | SQL, сложные JOIN | Простые, по ключу | Специфичные для домена |
| Объём данных | ТБ (обычно) | ПБ | Зависит от типа |
| Latency | Средний | Низкий | Зависит от типа |

**Принцип:** Современные системы часто используют **полиглотное
хранение** (polyglot persistence) — разные СУБД для разных задач
в одной системе.
