# Типы СУБД: Полный обзор и критерии выбора

## Обзор

Современный ландшафт систем управления базами данных (СУБД) чрезвычайно разнообразен. Помимо классических реляционных баз данных, существует множество специализированных решений, ориентированных на конкретные задачи: от кэширования и поиска по смыслу до аналитики петабайтов данных.

**Ключевой принцип:** Современные системы часто используют **полиглотное хранение (polyglot persistence)** — комбинирование разных СУБД для разных задач в рамках одной системы.

---

## 1. Реляционные СУБД (Relational)

**Назначение:** Хранение структурированных данных с поддержкой транзакций, сложных запросов и обеспечения целостности через связи между таблицами (реляционная модель Кодда).

**Модель данных:** Таблицы, строки, колонки, связи.
**Язык запросов:** SQL.
**Транзакции:** Полная поддержка ACID.
**Масштабирование:** Преимущественно вертикальное (реже — горизонтальное через шардирование).

**Типовые задачи:**
*   Финансовые операции (банки, платежи).
*   CRM/ERP системы.
*   Инвентаризация и управление запасами.
*   Системы со сложными бизнес-правилами и связями.

**Примеры:** PostgreSQL, MySQL, Oracle Database, Microsoft SQL Server, SQLite.

**Когда использовать:**
*   Требуются ACID-транзакции.
*   Данные хорошо структурированы, а схема стабильна.
*   Нужны сложные JOIN-запросы и агрегации.
*   Критически важна целостность связей.

**Когда не использовать:**
*   Данные слабо структурированы или схема часто меняется.
*   Требуется горизонтальное масштабирование на сотни узлов.
*   Нужны лишь простые операции чтения/записи без сложной логики.
*   Ожидаются миллиарды записей с экстремально высокой нагрузкой на запись.

### В центре внимания: PostgreSQL
Продвинутая open-source РСУБД, де-факто стандарт для новых проектов.
*   **Расширяемость:** Поддержка JSONB (документы), массивов, hstore.
*   **Специализированные расширения:** PostGIS (геоданные), pgvector (векторный поиск).
*   **Встроенные возможности:** Полнотекстовый поиск, репликация, партиционирование.

## 2. Документо-ориентированные СУБД (Document)

**Назначение:** Хранение полуструктурированных данных в виде документов (обычно JSON/BSON) с гибкой схемой.

**Модель данных:** Документы, коллекции.
**Схема:** Гибкая (разные документы в одной коллекции могут иметь разную структуру).
**Транзакции:** Ограниченная поддержка (часто ACID на уровне одного документа или, в новых версиях, кластера).

**Типовые задачи:**
*   Каталоги товаров, пользовательские профили.
*   Контент-менеджмент системы (CMS).
*   API-бэкенды с изменчивыми требованиями.
*   Логирование и сбор событий.

**Примеры:** MongoDB, Couchbase, CouchDB, Amazon DocumentDB.

**Когда использовать:**
*   Схема данных нестабильна или вариативна.
*   Данные естественно представляются в виде документов (агрегатов).
*   Нужна горизонтальная масштабируемость.
*   Вложенные структуры удобнее плоских таблиц.

**Когда не использовать:**
*   Требуется множество JOIN между коллекциями.
*   Строгая схема обязательна (compliance, регуляторика).
*   Нужны сложные транзакции, затрагивающие множество документов.
*   Высокая частота обновлений вложенных полей.

### В центре внимания: MongoDB
Лидер среди документных БД.
*   **Мощный инструментарий:** Aggregation Pipeline для сложной аналитики прямо в БД.
*   **Управляемый сервис:** MongoDB Atlas (managed cloud).
*   **Транзакции:** Поддержка multi-document транзакций (на уровне кластера с версии 4.0).

## 3. Хранилища «Ключ-Значение» (Key-Value)

**Назначение:** Хранение простых пар ключ → значение с минимальной задержкой доступа.

**Производительность:** Экстремально высокая (данные хранятся в памяти).
**Запросы:** Только по ключу (нет сложных запросов или фильтрации).

**Типовые задачи:**
*   Кэширование (сессии, конфигурации, горячие данные).
*   Rate limiting, счётчики.
*   Краткосрочное хранение временных данных.
*   Pub/Sub (издатель-подписчик) и очереди.

**Примеры:** Redis, Memcached, Amazon DynamoDB, etcd.

**Когда использовать:**
*   Нужна максимальная скорость чтения/записи.
*   Данные простые (нет вложенных структур).
*   Доступ к данным всегда по уникальному ключу.
*   Допустима eventual consistency (для распределенных реализаций).

**Когда не использовать:**
*   Нужны сложные запросы, фильтрация по полям или JOIN.
*   Требуется строгая схема или валидация данных.
*   Нужны вторичные индексы.
*   Объёмы данных требуют аналитической обработки.

### В центре внимания: Redis
Де-факто стандарт для in-memory хранилищ.
*   **Богатые структуры данных:** Строки, списки, множества, хэши, sorted sets.
*   **Коммуникация:** Pub/Sub, Streams.
*   **Модули:** RedisSearch (полнотекстовый поиск), RedisJSON, RedisTimeSeries.
*   **Персистентность:** Снимки (RDB) и журнал операций (AOF).

## 4. Колоночные (Ширококолоночные) СУБД (Wide-Column)

**Назначение:** Хранение огромных объёмов данных с высокой нагрузкой на запись и чтение по ключу. Данные физически хранятся по колонкам, а не по строкам.

**Оптимизация:** Агрегации и аналитические запросы.
**Масштабирование:** Горизонтальное, линейное.

**Типовые задачи:**
*   IoT-данные (сенсоры, метрики).
*   Социальные сети (ленты, сообщения).
*   Time-series данные (см. также отдельный раздел).
*   Глобально распределённые системы.

**Примеры:** Apache Cassandra, ScyllaDB, HBase, Google Bigtable, ClickHouse (как OLAP-вариант).

**Когда использовать:**
*   Петабайтные объёмы данных.
*   Требуется линейное горизонтальное масштабирование.
*   Запись преобладает над чтением (для Cassandra/HBase).
*   Нужна геораспределённость и multi-datacenter репликация.
*   Допустима eventual consistency.

**Когда не использовать:**
*   Нужны сложные запросы и JOIN.
*   Частые обновления существующих записей.
*   Требуется строгая согласованность (ACID).
*   Небольшие объёмы данных (overhead архитектуры).

### В центре внимания: ClickHouse
Колоночная СУБД, ориентированная на аналитику (OLAP).
*   **Скорость:** Экстремальная скорость агрегаций за счёт колоночного хранения и сжатия.
*   **Масштабируемость:** Линейная.
*   **Происхождение:** Разработана в Яндексе.

## 5. Графовые СУБД (Graph)

**Назначение:** Моделирование и хранение данных как графов (узлы, рёбра, свойства) для эффективной работы со связями.

**Оптимизация:** Обход графа, поиск путей и сложных паттернов связей.

**Типовые задачи:**
*   Социальные сети (друзья, подписки).
*   Рекомендательные системы.
*   Обнаружение мошенничества (анализ связей между транзакциями).
*   Графы знаний (knowledge graphs), онтологии.
*   Анализ сетевой топологии.

**Примеры:** Neo4j, Amazon Neptune, JanusGraph, ArangoDB, TigerGraph.

**Когда использовать:**
*   Связи между сущностями важнее самих сущностей.
*   Нужно обходить граф на несколько уровней глубины.
*   Сложные паттерны связей (пути, циклы).
*   Рекомендации на основе графовых алгоритмов (PageRank, community detection).

**Когда не использовать:**
*   Простые CRUD-операции без сложных связей.
*   Данные в основном табличные, связи редки.
*   Нужна агрегация по множеству записей (для этого лучше подходят колоночные БД).
*   Стоимость инфраструктуры и экспертизы не окупается сложностью.

---

## 6. Векторные СУБД (Vector)

**Назначение:** Хранение и поиск по векторным представлениям (эмбеддингам) с использованием поиска по сходству (similarity search).

**Модель данных:** Векторы высокой размерности.
**Запросы:** Поиск ближайших соседей (k-NN, ANN).

**Типовые задачи:**
*   Семантический поиск (поиск по смыслу, а не по ключевым словам).
*   RAG (Retrieval-Augmented Generation) для LLM.
*   Рекомендательные системы на основе embeddings.
*   Поиск похожих изображений (image similarity search).
*   Обнаружение аномалий.

**Примеры:** Qdrant, Pinecone, Weaviate, Milvus, Chroma, pgvector (расширение PostgreSQL).

**Когда использовать:**
*   Работа с embeddings (от LLM, CNN и других моделей).
*   Поиск ближайших соседей.
*   Семантический поиск поверх текстовых или мультимедийных данных.
*   Интеграция с AI/ML пайплайнами.

**Когда не использовать:**
*   Традиционные CRUD-операции с бизнес-данными.
*   Требуется точное соответствие (exact match), а не similarity.
*   Данные не имеют векторного представления.
*   Высокие требования к latency (векторный поиск медленнее поиска по B-tree индексу).

### В центре внимания: Qdrant
Высокопроизводительная векторная БД, написанная на Rust.
*   **Фильтрация:** Эффективный поиск с фильтрацией по метаданным (payload).
*   **Гибкость:** Поддержка различных метрик расстояния (Cosine, Dot Product, Euclid).
*   **Масштабируемость:** Распределённый режим работы.

## 7. Поисковые движки (Search Engine)

**Назначение:** Полнотекстовый поиск, нечёткое соответствие, фасетная навигация и аналитика по тексту.

**Типовые задачи:**
*   Поиск по каталогам товаров.
*   Лог-аналитика (ELK стек).
*   Поиск документов с ранжированием релевантности.
*   Автодополнение (suggest) и исправление опечаток.

**Примеры:** Elasticsearch, Apache Solr, OpenSearch, Meilisearch, Typesense.

**Когда использовать:**
*   Нужен полнотекстовый поиск с токенизацией, стеммингом и языковым анализом.
*   Нечёткий поиск (опечатки, синонимы).
*   Фасетная фильтрация (категории, бренды, ценовые диапазоны).
*   Near real-time аналитика по логам.

**Когда не использовать:**
*   Как основное хранилище бизнес-данных (это вторичный индекс).
*   Нужна строгая согласованность и транзакции.
*   Сложные обновления существующих записей.
*   Хранение больших бинарных объектов.

---

## 8. Хранилища временных рядов (Time-Series)

**Назначение:** Эффективное хранение и запросы к данным, привязанным ко времени (метрики, события, телеметрия).

**Типовые задачи:**
*   Мониторинг инфраструктуры (CPU, память, сеть).
*   Финансовые котировки и тикеры.
*   IoT-сенсоры.
*   Application Performance Monitoring (APM).

**Примеры:** InfluxDB, TimescaleDB (расширение PostgreSQL), Prometheus, VictoriaMetrics, QuestDB, TDengine.

**Когда использовать:**
*   Временная метка (timestamp) является ключевым измерением.
*   Высокая скорость записи (миллионы точек в секунду).
*   Агрегации по временным окнам (среднее, min/max, процентили).
*   Нужно эффективное сжатие временных рядов.
*   Автоматическое удаление старых данных (retention policies).

**Когда не использовать:**
*   Данные не имеют временной природы.
*   Нужны сложные JOIN с другими типами данных.
*   Частые обновления исторических записей.
*   Требования к ACID-транзакциям.

---

## 9. Хранилища данных и Озера (Data Warehouse / Lakehouse)

**Назначение:** Аналитическая обработка больших объёмов данных (OLAP) со сложными запросами и агрегациями.

**Типовые задачи:**
*   Business Intelligence (BI) и отчётность.
*   ETL/ELT пайплайны.
*   Машинное обучение на исторических данных.
*   Data Science и аналитика.

**Примеры:**
*   **Data Warehouse:** Snowflake, Google BigQuery, Amazon Redshift, ClickHouse.
*   **Lakehouse:** Databricks, Apache Hudi, Apache Iceberg, Delta Lake.

**Когда использовать:**
*   Аналитические запросы по историческим данным.
*   Объёмы от терабайт до петабайт.
*   Сложные агрегации и JOIN между множеством таблиц.
*   Консолидация данных из разных источников.
*   Нужна columnar storage и векторизованное выполнение запросов.

**Когда не использовать:**
*   OLTP-нагрузка (транзакционные операции).
*   Требования к real-time (задержки в секундах и меньше).
*   Маленькие объёмы данных (overhead инфраструктуры).
*   Частые обновления отдельных записей.

---

## 10. Платформы потоковой обработки (Event Streaming)

**Назначение:** Приём, хранение и обработка потоков событий в реальном времени.

**Типовые задачи:**
*   Event-driven архитектура.
*   Real-time аналитика и мониторинг.
*   Stream processing (Complex Event Processing).
*   Message broker для распределённых систем.
*   Change Data Capture (CDC).

**Примеры:** Apache Kafka, Apache Pulsar, Amazon Kinesis, Azure Event Hubs, Redpanda.

**Когда использовать:**
*   Нужен event log как источник истины (source of truth).
*   Требуется перечитывание (replay) истории событий.
*   Обработка потоков данных в реальном времени.
*   Интеграция множества систем через события.
*   Pub/Sub с высокой пропускной способностью.

**Когда не использовать:**
*   Как основное хранилище для CRUD-операций.
*   Нужны сложные запросы и JOIN по данным.
*   Требование мгновенной согласованности (подходит eventual consistency).
*   Простые сценарии обмена сообщениями (можно использовать RabbitMQ/SQS).

---

## 11. Объектные хранилища (Object Storage)

**Назначение:** Хранение больших объёмов неструктурированных данных (файлы, изображения, видео, бэкапы) как объектов с метаданными.

**Типовые задачи:**
*   Хранение медиа-контента (фото, видео).
*   Бэкапы и архивы.
*   Статические ресурсы для веб-приложений.
*   Data Lake для сырых данных.

**Примеры:** Amazon S3, Google Cloud Storage, Azure Blob Storage, MinIO, Ceph.

**Когда использовать:**
*   Большие файлы (от мегабайт до терабайт).
*   Append-only или неизменяемые (immutable) данные.
*   Нужна географическая репликация и высочайшая надёжность (durability).
*   Доступ по HTTP/HTTPS (REST API).
*   Экономичное долгосрочное хранение.

**Когда не использовать:**
*   Частые обновления существующих объектов (объекты неизменяемы).
*   Транзакционные операции.
*   Нужна файловая система с произвольным доступом (используйте EFS/NFS).
*   Низколатентный доступ к миллионам маленьких объектов.

## Сводная таблица выбора

| Критерий | Реляционные | Документные | Ключ-значение | Колоночные/Широкие | Графовые | Векторные |
|:---|:---|:---|:---|:---|:---|:---|
| **Схема** | Строгая | Гибкая | Отсутствует | Гибкая (по колонкам) | Гибкая (граф) | Фиксированная (вектор) |
| **Транзакции** | Полные ACID | Ограниченные | Нет | Ограниченные | Зависит от БД | Нет |
| **Масштабирование** | Вертикальное | Горизонтальное | Горизонтальное | Горизонтальное | Зависит от БД | Горизонтальное |
| **Типичные запросы** | Точечные, диапазоны, JOIN | По документу | По ключу | Агрегации, по ключу | Обход графа | Поиск соседей |
| **Основное применение** | Финансы, ERP | CMS, каталоги, профили | Кэш, сессии, счётчики | Аналитика, IoT, Big Data | Соцсети, рекомендации | AI/ML, RAG, семантика |

**Принцип:** Современные системы часто используют **полиглотное хранение** — разные СУБД для разных задач в одной системе. Например, PostgreSQL для транзакций, Redis для кэша, Elasticsearch для поиска и Qdrant для RAG.
