# Модели согласованности: ACID, BASE и CAP

## ACID (Транзакционная модель)

**ACID** — набор свойств, гарантирующих надёжную обработку транзакций
в реляционных БД.

### Atomicity (Атомарность)

Транзакция выполняется целиком или не выполняется вовсе.

**Пример:** Перевод 100$ со счёта A на счёт B:
```
BEGIN TRANSACTION
UPDATE accounts SET balance = balance - 100 WHERE id = A
UPDATE accounts SET balance = balance + 100 WHERE id = B
COMMIT
```
Если второй UPDATE упадёт, первый тоже откатится. Либо оба счёта
обновились, либо ни один.

**Гарантия:** Нет частичных обновлений.

### Consistency (Согласованность)

Транзакция переводит БД из одного согласованного состояния в другое
согласованное состояние.

**Пример:** Constraint `CHECK (balance >= 0)` не позволит списать больше,
чем есть на счёте. Foreign key не позволит создать заказ для
несуществующего пользователя.

**Гарантия:** Все constraints, triggers, rules соблюдаются.

### Isolation (Изолированность)

Параллельные транзакции не влияют друг на друга так, как если бы они
выполнялись последовательно.

**Уровни изоляции (SQL standard):**
- **Read Uncommitted:** Видны незакоммиченные изменения (dirty reads)
- **Read Committed:** Видны только закоммиченные изменения
- **Repeatable Read:** Повторное чтение возвращает те же данные
- **Serializable:** Полная изоляция (как последовательное выполнение)

**Компромисс:** Чем выше изоляция, тем ниже производительность
(больше блокировок).

**Гарантия:** Предсказуемое поведение при конкурентном доступе.

### Durability (Надёжность)

После COMMIT изменения сохраняются даже при сбое системы.

**Механизмы:**
- Write-ahead logging (WAL): изменения сначала в лог, потом в данные
- fsync на диск
- Репликация на другие узлы

**Гарантия:** Закоммиченные данные не потеряются.

**Типичные СУБД:** PostgreSQL, MySQL (InnoDB), Oracle, SQL Server

## BASE (Модель распределённых систем)

**BASE** — альтернативная модель для распределённых NoSQL-систем,
жертвующая strict consistency ради доступности и масштабируемости.

### Basic Availability (Базовая доступность)

Система остаётся доступной для чтения и записи, даже если некоторые узлы
недоступны.

**Пример:** В Cassandra при падении одного узла из трёх записи
продолжают работать (при `consistency_level = ONE`).

**Компромисс:** Возможна частичная недоступность данных (некоторые узлы
могут отставать).

### Soft State (Мягкое состояние)

Состояние системы может изменяться со временем даже без новых входных
данных (из-за репликации, разрешения конфликтов).

**Пример:** В eventual consistency системе узел A принял запись в T1,
узел B ещё не получил реплику. В T2 состояние A и B различается, но
в T3 (после репликации) синхронизируется.

**Следствие:** Клиенты должны быть готовы к временной несогласованности.

### Eventual Consistency (Согласованность в конечном счёте)

Если прекратится приём новых записей, все узлы в конечном счёте придут
к одному состоянию.

**Временное окно несогласованности:** От миллисекунд до минут (зависит
от настроек репликации и сетевой задержки).

**Пример:** DynamoDB с eventual consistency: запись на узле A доступна
мгновенно, на узле B — через 50-500 мс (в зависимости от региона).

**Гарантия:** Со временем все реплики синхронизируются.

**Типичные СУБД:** Cassandra, DynamoDB, CouchDB, Riak

## Модели согласованности (Consistency Models)

### Strong Consistency (Строгая согласованность)

После записи все последующие чтения (с любого узла) возвращают новое
значение.

**Как достигается:**
- Синхронная репликация (запись подтверждается только после обновления
  всех реплик)
- Распределённые транзакции (2PC — Two-Phase Commit)
- Консенсус-алгоритмы (Raft, Paxos)

**Цена:**
- Высокая latency (ожидание всех реплик)
- Снижение доступности (если узел недоступен, запись блокируется)

**Пример:** PostgreSQL с synchronous replication, CockroachDB,
etcd, ZooKeeper.

### Eventual Consistency (Согласованность в конечном счёте)

После записи чтения могут возвращать старое значение, но со временем
все чтения вернут новое.

**Как достигается:**
- Асинхронная репликация
- Conflict resolution (last-write-wins, vector clocks)

**Цена:**
- Клиенты могут видеть устаревшие данные
- Нужна логика обработки конфликтов

**Пример:** Cassandra, DynamoDB (default), DNS.

### Causal Consistency (Причинная согласованность)

Если операция A причинно связана с операцией B (например, B прочитала
результат A), то все узлы увидят A перед B.

**Пример:** Пользователь написал комментарий (A), другой ответил на него
(B). Все увидят комментарий перед ответом, даже если узлы
рассинхронизированы.

**Компромисс:** Между несвязанными операциями порядок не гарантирован.

### Read-Your-Writes Consistency

Клиент всегда видит свои собственные записи.

**Как достигается:**
- Sticky sessions (клиент всегда обращается к одному узлу)
- Client-side caching метаданных (vector clocks, timestamps)

**Пример:** Пользователь обновил профиль, сразу видит изменения,
даже если другие пользователи видят старую версию.

## CAP Theorem (Теорема CAP)

**CAP** — фундаментальное ограничение распределённых систем:
невозможно одновременно обеспечить все три свойства:

- **C**onsistency (согласованность): все узлы видят одни и те же данные
- **A**vailability (доступность): каждый запрос получает ответ
- **P**artition tolerance (устойчивость к разделению): система работает
  при потере связи между узлами

### Классическая интерпретация

**В нормальных условиях (нет network partition):**
Можно обеспечить CA (consistency + availability).

**При network partition (потеря связи между узлами):**
Приходится выбирать между:
- **CP:** Гарантировать согласованность, но жертвовать доступностью
  (запросы к недоступным узлам блокируются)
- **AP:** Гарантировать доступность, но жертвовать согласованностью
  (узлы принимают записи, но могут расходиться)

**Важно:** Partition tolerance **обязательна** в реальных
распределённых системах (сеть ненадёжна), поэтому выбор всегда между
CP и AP при partition.

### Примеры

**CP-системы (consistency при partition):**
- ZooKeeper, etcd: при partition minority partition становится
  недоступной, majority продолжает работать
- PostgreSQL synchronous replication: если replica недоступна,
  транзакция блокируется

**AP-системы (availability при partition):**
- Cassandra: оба partition продолжают принимать записи, разрешают
  конфликты позже
- DynamoDB eventual consistency: оба partition работают,
  синхронизируются после восстановления связи

## PACELC Theorem (Расширение CAP)

**PACELC** уточняет CAP, добавляя поведение системы в нормальных условиях
(без partition).

**Формулировка:**
- Если есть **P**artition → выбираем **A**vailability или **C**onsistency
- **E**lse (нет partition) → выбираем **L**atency или **C**onsistency

### Типовые комбинации

**PA/EL (Availability + Low Latency):**
- Cassandra, DynamoDB
- Всегда доступны, минимальная latency
- Consistency жертвуется при partition и в нормальных условиях

**PC/EC (Consistency везде):**
- PostgreSQL synchronous, ZooKeeper
- Строгая согласованность всегда
- Высокая latency (ожидание реплик)

**PA/EC (Availability при partition, Consistency в норме):**
- MongoDB (с `writeConcern: majority`)
- Cassandra с `QUORUM` consistency
- Доступны при partition, согласованы в нормальных условиях

**PC/EL (Consistency при partition, Low Latency в норме):**
- Spanner (Google)
- Редкая комбинация, требует точных часов (atomic clocks)

## Практические рекомендации

### Когда выбирать ACID:
- Финансовые операции (банки, платежи)
- Критичные бизнес-транзакции
- Сложные бизнес-правила с constraints
- Объёмы данных помещаются в одну БД

### Когда выбирать BASE:
- Глобально распределённые системы
- Петабайтные объёмы данных
- Допустима временная несогласованность
- Высокая доступность критичнее строгой согласованности

### Как проектировать:
1. **Определите требования:** Какая consistency нужна для каждой операции?
2. **Используйте гибридный подход:** ACID для критичных операций,
   eventual для остальных
3. **Документируйте гарантии:** Аналитики и разработчики должны понимать,
   какие данные актуальны
4. **Тестируйте сценарии failures:** Как система ведёт себя при partition?
5. **Мониторьте lag:** Время синхронизации реплик — ключевая метрика

### Пример из практики

**Платёжная система:**
- **ACID (PostgreSQL):** Балансы счетов, транзакции
- **BASE (Cassandra):** История операций, логи аудита
- **Eventual consistency приемлема:** Логи могут отставать на секунды,
  но балансы всегда согласованы

**Результат:** Строгая согласованность там, где критично, и высокая
доступность для менее критичных данных.
