# OLTP vs OLAP: два мира обработки данных

## Определения

**OLTP (Online Transaction Processing)** — обработка транзакций в реальном
времени. Система оптимизирована для быстрых операций записи и чтения
отдельных записей с обеспечением целостности данных.

**OLAP (Online Analytical Processing)** — аналитическая обработка. Система
оптимизирована для сложных запросов, агрегаций и сканирования больших
объёмов исторических данных.

## Ключевые различия

| Характеристика | OLTP | OLAP |
|---|---|---|
| **Тип нагрузки** | Много коротких транзакций | Мало сложных запросов |
| **Объём данных за запрос** | Единицы-десятки записей | Миллионы-миллиарды записей |
| **Схема данных** | Нормализованная (3NF) | Денормализованная (star/snowflake) |
| **Оптимизация storage** | Row-based (построчное) | Column-based (колоночное) |
| **Consistency** | Strong (ACID) | Eventual (часто) |
| **Retention** | Текущие данные | Исторические данные (годы) |
| **Обновления** | Частые, точечные | Редкие, массовые (batch) |
| **Latency требования** | Миллисекунды | Секунды-минуты |
| **Пользователи** | Конечные пользователи, приложения | Аналитики, data scientists |

## Примеры задач

### OLTP-задачи:
- Оформление заказа в интернет-магазине
- Перевод денег между счетами
- Регистрация нового пользователя
- Обновление статуса задачи
- Поиск конкретного товара по ID

### OLAP-задачи:
- Отчёт о продажах по регионам за квартал
- Анализ когорт пользователей
- Расчёт метрик retention и churn
- Прогнозирование спроса на основе исторических данных
- A/B тестирование результатов

## Почему одна БД не подходит для обоих типов нагрузки

### 1. Конфликт требований к storage

**OLTP** оптимизирован для:
- Быстрого чтения/записи отдельных строк
- Row-based storage: вся запись читается/пишется целиком
- B-tree индексы для точечного доступа

**OLAP** оптимизирован для:
- Сканирования миллионов строк
- Column-based storage: читаются только нужные колонки
- Сжатие по колонкам (run-length encoding, dictionary encoding)
- Vectorized query execution

**Пример:** Запрос `SELECT AVG(price) FROM orders WHERE date > '2024-01-01'`
в OLTP-БД (PostgreSQL) должен прочитать все строки таблицы `orders`
(миллионы записей), хотя нужны только колонки `price` и `date`.
В OLAP-БД (ClickHouse) читаются только эти две колонки в сжатом виде,
что в 100-1000 раз быстрее.

### 2. Конфликт схем данных

**OLTP** использует нормализованную схему:
- Избегание дублирования данных
- Много таблиц, сложные JOIN
- Обновления затрагивают одну-две таблицы

**OLAP** использует денормализованную схему:
- Star schema (fact tables + dimension tables)
- Snowflake schema (нормализованные измерения)
- Данные подготовлены для быстрого сканирования
- Избегание JOIN (или минимизация)

**Проблема:** Если использовать одну БД, придётся либо жертвовать
производительностью OLTP (из-за JOIN), либо усложнять аналитику (из-за
нормализации).

### 3. Конфликт нагрузки

**OLTP:**
- Тысячи параллельных транзакций
- Блокировки на уровне строк
- Высокая конкуренция за ресурсы CPU/memory

**OLAP:**
- Одиночные запросы потребляют 100% CPU на минуты
- Сканирование больших объёмов данных
- Тяжёлые операции сортировки и агрегации

**Проблема:** OLAP-запрос может заблокировать OLTP-транзакции или
исчерпать ресурсы, что приведёт к деградации пользовательского опыта.

### 4. Конфликт требований к обновлениям

**OLTP:**
- Частые точечные обновления (UPDATE)
- Транзакционная целостность критична
- Нужны триггеры, constraints, foreign keys

**OLAP:**
- Редкие массовые загрузки (batch insert)
- Данные append-only или обновляются целиком (партициями)
- Constraints и foreign keys замедляют загрузку

### 5. Конфликт retention policies

**OLTP:**
- Хранит активные данные (последние месяцы/годы)
- Архивация старых данных для производительности

**OLAP:**
- Хранит исторические данные (5-10+ лет)
- Нужен полный контекст для трендов и прогнозов
