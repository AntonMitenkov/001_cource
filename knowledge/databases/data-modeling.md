# Моделирование данных: от концепции к реализации

## Уровни моделирования данных

### Conceptual Model (Концептуальная модель)

**Назначение:** Высокоуровневое описание бизнес-сущностей и их связей
без технических деталей.

**Аудитория:** Бизнес-аналитики, product owners, stakeholders.

**Содержание:**
- Основные сущности (Customer, Order, Product)
- Связи между сущностями (Customer places Order, Order contains Product)
- Бизнес-правила (Customer can have multiple Orders)

**Инструменты:** Доски, диаграммы в Miro/Figma, текстовые описания.

**Пример:**
```
Customer (1) --- places ---> (*) Order
Order (*) --- contains ---> (*) Product
```

### Logical Model (Логическая модель)

**Назначение:** Детализация концептуальной модели с атрибутами, типами
данных и правилами нормализации, но без привязки к конкретной СУБД.

**Аудитория:** Data architects, разработчики.

**Содержание:**
- Атрибуты сущностей (Customer: id, name, email, created_at)
- Типы данных (INTEGER, VARCHAR, TIMESTAMP)
- Primary keys, foreign keys
- Нормализация (обычно до 3NF)
- Constraints и business rules

**Инструменты:** ERD-редакторы (draw.io, Lucidchart, DataGrip).

**Пример:**
```
CUSTOMERS
- customer_id (PK, INT)
- name (VARCHAR(100))
- email (VARCHAR(255), UNIQUE)
- created_at (TIMESTAMP)

ORDERS
- order_id (PK, INT)
- customer_id (FK → CUSTOMERS)
- order_date (TIMESTAMP)
- status (ENUM: pending, shipped, delivered)
```

### Physical Model (Физическая модель)

**Назначение:** Реализация логической модели в конкретной СУБД с учётом
производительности и особенностей хранения.

**Аудитория:** DBA, разработчики.

**Содержание:**
- Специфичные для СУБД типы данных (PostgreSQL UUID, JSONB)
- Индексы (B-tree, GIN, GiST)
- Партиционирование таблиц
- Денормализация для производительности
- Storage engines
- Compression, partitioning strategies

**Пример:**
```
customers
- customer_id UUID PRIMARY KEY DEFAULT gen_random_uuid()
- name VARCHAR(100) NOT NULL
- email VARCHAR(255) UNIQUE NOT NULL
- created_at TIMESTAMPTZ DEFAULT NOW()

Индексы:
- idx_customers_email (B-tree на email)
- idx_customers_created_at (B-tree на created_at DESC)
```

## ERD (Entity-Relationship Diagram)

**Назначение:** Визуальное представление логической модели данных.

### Основные элементы

**Entities (Сущности):**
- Прямоугольники
- Представляют бизнес-объекты (Customer, Order, Product)

**Attributes (Атрибуты):**
- Колонки внутри прямоугольников
- Свойства сущностей (name, email, price)

**Relationships (Связи):**
- Линии между сущностями
- Типы связей:
  - **One-to-One (1:1):** User — Profile
  - **One-to-Many (1:N):** Customer — Orders
  - **Many-to-Many (M:N):** Students — Courses (через junction table)

### Обозначения (Crow's Foot notation)

**Кардинальность:**
- `|` — exactly one
- `O` — zero or one (optional)
- `|<` — one or many
- `O<` — zero or many

**Примеры:**
```
Customer |---O< Order
```
Читается: «Customer может иметь ноль или более Orders»

```
Order |---|< OrderItem >|---| Product
```
Читается: «Order содержит один или более OrderItem, каждый ссылается
ровно на один Product»


### Кардинальность и обязательность

**Кардинальность (Cardinality):** Сколько экземпляров сущности участвуют
в связи.
- 1, N, M

**Обязательность (Optionality):** Обязательна ли связь.
- Mandatory (`|`) — связь обязательна
- Optional (`O`) — связь опциональна

**Примеры:**
- `Customer |---O< Order` — Customer может не иметь Orders (реалистично)
- `Order |---|< OrderItem` — Order должен иметь хотя бы один OrderItem

## Normalization (Нормализация)

**Назначение:** Устранение избыточности данных и аномалий обновления
через декомпозицию таблиц.

### Аномалии, которые устраняет нормализация

**Аномалия вставки:** Невозможно добавить данные без наличия других.
Пример: нельзя добавить товар, пока не создан хотя бы один заказ.

**Аномалия удаления:** При удалении одних данных теряются другие.
Пример: при удалении последнего заказа теряется информация о клиенте.

**Аномалия обновления:** Изменение данных нужно делать в нескольких местах.
Пример: переименование категории требует обновления во всех строках
заказов, где она упоминается.


### Нормальные формы

**1NF (Первая нормальная форма):**
- Все атрибуты атомарны (нет массивов, списков, JSON в колонках)
- Каждая строка уникальна (есть primary key)
- Нет повторяющихся групп колонок

**Нарушение 1NF:**
```
orders: order_id = 1, products = "product_a, product_b"
```
Исправление: вынести в отдельную таблицу order_items.

**2NF (Вторая нормальная форма):**
- Выполнена 1NF
- Нет partial dependencies (частичных зависимостей)
- Все неключевые атрибуты зависят от всего составного ключа

**Нарушение 2NF:**
```
order_items:
  order_id (PK)
  product_id (PK)
  product_name  ← зависит только от product_id, а не от полного ключа
  quantity
```
Исправление: вынести `product_name` в таблицу `products`.

**3NF (Третья нормальная форма):**
- Выполнена 2NF
- Нет transitive dependencies (транзитивных зависимостей)
- Неключевые атрибуты не зависят от других неключевых атрибутов

**Нарушение 3NF:**
```
orders:
  order_id (PK)
  customer_id
  customer_name   ← зависит от customer_id, а не от order_id
  customer_email  ← зависит от customer_id
```
Исправление: вынести данные клиента в таблицу `customers`.

**BCNF (Boyce-Codd Normal Form):**
- Выполнена 3NF
- Каждая детерминанта является потенциальным ключом
- Устраняет редкие аномалии, оставшиеся после 3NF

### Преимущества нормализации

- Устранение избыточности: данные хранятся в одном месте
- Целостность: изменения применяются один раз
- Меньше аномалий: нет проблем с UPDATE/DELETE
- Экономия дискового пространства

### Недостатки нормализации

- Сложные запросы: много JOIN
- Производительность: JOIN медленнее чтения одной таблицы
- Сложность понимания схемы для новых разработчиков

## Denormalization (Денормализация)

**Назначение:** Намеренное нарушение нормальных форм для улучшения
производительности чтения.

### Типовые паттерны денормализации

**1. Дублирование атрибутов**

Вместо JOIN с таблицей `customers` храним имя и email прямо в `orders`:
```
orders:
  order_id
  customer_id (FK)
  customer_name   ← дублируем
  customer_email  ← дублируем
```
Выигрыш: чтение заказа без JOIN.
Цена: при изменении имени нужно обновить и orders.


**2. Предварительные агрегации**

Вместо COUNT/SUM в реальном времени храним готовое значение:
```
customers:
  customer_id
  total_orders_count  ← обновляется при создании/удалении заказа
  total_spent_amount
```
Выигрыш: мгновенное чтение агрегатов.
Цена: поддержка актуальности при каждой транзакции.


**3. Материализованные представления**

Предварительно вычисленный результат запроса, обновляемый периодически:
```
monthly_sales_report:
  month
  total_revenue
  orders_count
  avg_order_value
```
Выигрыш: аналитика без тяжёлых запросов.
Цена: данные отстают от реальных на период обновления.


**4. Широкие таблицы (flat tables)**

Вместо 5 нормализованных таблиц — одна с дублированием:
```
flat_orders:
  order_id
  customer_name
  customer_email
  product_name
  product_category
  order_date
  total_amount
```
Выигрыш: один запрос без JOIN.
Цена: избыточность, сложнее обновлять.


### Когда использовать денормализацию

- OLAP-системы: аналитические запросы, где JOIN дороги
- Read-heavy нагрузка: чтение в 100+ раз чаще записи
- Высокие требования к latency: миллисекунды критичны
- Кэширование не помогает: данные уникальны для каждого запроса

### Когда НЕ использовать денормализацию

- Write-heavy нагрузка: стоимость поддержки копий слишком высока
- Строгие требования к целостности: риск рассинхронизации
- Данные часто обновляются: аномалии обновления


### Стратегии поддержания целостности при денормализации

**1. Триггеры на уровне БД:**
При обновлении `customers.name` автоматически обновлять
`orders.customer_name`.

**2. Приложение управляет согласованностью:**
Сервис при обновлении клиента явно обновляет и связанные записи
в таблице заказов.

**3. Событийная синхронизация:**
При изменении данных клиента публикуется событие `CustomerUpdated`,
подписчики обновляют свои денормализованные копии.

**4. Eventual consistency:**
Принимаем временную несогласованность. Фоновый процесс периодически
синхронизирует данные.

 

## Data Ownership (Владение данными)

**Назначение:** Определение, кто отвечает за качество, целостность
и эволюцию данных.

 

### Принципы data ownership

**1. Одна сущность — один владелец**
- Каждая бизнес-сущность (Customer, Order, Product) имеет
  единственного владельца
- Владелец определяет схему, валидацию, бизнес-правила
- Изменение схемы согласуется только с владельцем

**2. Владелец = команда, а не индивид**
- Команда отвечает за данные коллективно
- Избегаем single point of failure
- Документация и знания распределены внутри команды

**3. Границы владения = границы сервисов**
- Микросервис владеет своими данными
- Другие сервисы обращаются через API, а не напрямую к БД
- Прямой доступ к чужой БД — архитектурный долг

 

### Паттерны организации данных

**Монолитная БД:**
```
Одна БД для всего приложения
Владелец: DBA team или platform team
```
- Плюсы: простота, транзакции между таблицами
- Минусы: конфликты схем, блокировки, сложность масштабирования

**Database-per-service:**
```
Каждый микросервис имеет свою БД
Владелец: команда сервиса
```
- Плюсы: автономия, изоляция, независимое масштабирование
- Минусы: нет JOIN между сервисами, нужна eventual consistency

**Shared database (антипаттерн):**
```
Несколько сервисов пишут в одну БД
```
- Проблемы: тесная связанность, конфликты схем, каскадные сбои
- Изменение одной таблицы ломает несколько сервисов

 

### Data Governance (Управление данными)

**Data Steward:**
- Отвечает за качество данных
- Определяет стандарты именования
- Документирует бизнес-термины и глоссарий

**Data Catalog:**
- Инвентаризация всех данных в организации
- Метаданные: владелец, описание, lineage
- Примеры: Amundsen, DataHub, Alation, OpenMetadata

**Data Lineage:**
- Отслеживание происхождения данных
- От источника до конечного потребителя
- Помогает в аудите, отладке и compliance

### Пример из практики

**E-commerce платформа:**

**Customer data:**
- Владелец: Customer team
- БД: PostgreSQL (customer_db)
- Доступ: только через API `/api/customers`
- Другие сервисы не пишут напрямую

**Order data:**
- Владелец: Order team
- БД: PostgreSQL (order_db)
- Доступ: только через API `/api/orders`
- Денормализация: `customer_name` в `orders` для производительности
- Синхронизация: через событие `CustomerUpdated`

**Product data:**
- Владелец: Catalog team
- БД: MongoDB (product_catalog) — гибкая схема для атрибутов
- Доступ: только через API `/api/products`
- Кэш: Redis для быстрого чтения популярных товаров

**Результат:**
- Чёткие границы ответственности
- Команды автономны в эволюции своих данных
- Нет конфликтов схем между командами
- Легко масштабировать и поддерживать
