# Глоссарий курса

Словарь ключевых терминов, используемых в материалах курса по архитектуре программных систем.

## Архитектура и проектирование

- **System Design (Проектирование системы)** — процесс определения архитектуры, компонентов, модулей, интерфейсов и данных для системы с целью удовлетворения требований.
- **Enterprise Architecture (Корпоративная архитектура)** — стратегическое планирование ИТ-инфраструктуры и процессов организации для согласования с бизнес-целями.
- **Solution Architecture (Архитектура решения)** — описание структуры и поведения конкретного решения для бизнес-задачи, включая компоненты и их взаимодействие.
- **Business-IT Alignment (Выравнивание бизнеса и ИТ)** — стратегический процесс обеспечения соответствия ИТ-инициатив бизнес-целям организации.
- **Architecture Driver (Архитектурный драйвер)** — ключевое требование или ограничение, которое существенно влияет на архитектурные решения (например, высокая доступность или низкая задержка).
- **Stakeholder (Заинтересованное лицо)** — любое лицо или группа, влияющая на систему или находящаяся под её влиянием (заказчики, пользователи, разработчики).
- **C4 Model** — модель визуализации архитектуры ПО на четырех уровнях: Context, Container, Component, Code.
- **System Context Diagram (Диаграмма контекста)** — уровень C4, показывающий систему как единый блок и её взаимодействие с внешними пользователями и системами.
- **Container Diagram (Диаграмма контейнеров)** — уровень C4, детализирующий систему до основных технологических блоков (приложения, БД, микросервисы).
- **Domain-Driven Design (DDD, Предметно-ориентированное проектирование)** — подход к разработке, фокусирующийся на глубоком понимании предметной области и отражении её в коде.
- **Ubiquitous Language (Убиквитарный язык)** — общий строгий язык, используемый разработчиками и экспертами предметной области для устранения недопонимания.
- **Bounded Context (Ограниченный контекст)** — граница внутри модели DDD, в которой определенная модель данных и логика имеют четкий смысл и не пересекаются с другими моделями.
- **Context Map (Карта контекстов)** — диаграмма, отображающая связи и способы интеграции между различными ограниченными контекстами.

## Требования и качество

- **Functional Requirement (Функциональное требование)** — описание того, *что* система должна делать (функции, возможности).
- **Non-Functional Requirement (Нефункциональное требование)** — описание того, *как* система должна работать (производительность, безопасность, надежность).
- **Quality Attribute Scenario (Сценарий атрибута качества)** — конкретная ситуация, используемая для проверки выполнения нефункционального требования (источник, стимул, артефакт, среда, отклик, мера).

## Архитектурные стили

- **Monolith (Монолит)** — архитектурный стиль, при котором все компоненты приложения упакованы и развертываются как единое целое.
- **Modular Monolith (Модульный монолит)** — монолитное приложение, внутренне разделенное на четко определенные модули с минимальной связностью.
- **Microservices (Микросервисы)** — архитектурный стиль, при котором система состоит из набора небольших независимых сервисов, общающихся через сеть.
- **Event-Driven Architecture (Событийно-ориентированная архитектура)** — стиль, где компоненты взаимодействуют асинхронно через производство и потребление событий.
- **Serverless (Серверless-архитектура)** — модель исполнения, где облачный провайдер динамически управляет выделением ресурсов, а код выполняется в ответ на события.

## Данные и хранение

- **Conceptual Data Model (Концептуальная модель данных)** — высокоуровневое описание данных и их связей с точки зрения бизнеса, без технических деталей.
- **Logical Data Model (Логическая модель данных)** — детальное описание структур данных, атрибутов и связей, независимое от конкретной СУБД.
- **Physical Data Model (Физическая модель данных)** — реализация логической модели для конкретной СУБД с учетом типов данных, индексов и партиционирования.
- **ERD (Entity-Relationship Diagram)** — диаграмма «сущность-связь», визуализирующая структуру данных системы.
- **Normalization (Нормализация)** — процесс организации данных в БД для уменьшения избыточности и улучшения целостности.
- **ACID** — набор свойств транзакций (Atomicity, Consistency, Isolation, Durability), гарантирующих надежность обработки данных.
- **BASE** — модель согласованности (Basically Available, Soft state, Eventual consistency), часто используемая в распределенных NoSQL системах.
- **CAP Theorem (Теорема CAP)** — утверждение, что в распределенной системе невозможно одновременно обеспечить Согласованность (Consistency), Доступность (Availability) и Устойчивость к разделению (Partition tolerance); можно выбрать только два из трех.
- **OLTP (Online Transaction Processing)** — системы, оптимизированные для выполнения большого количества коротких транзакций записи/чтения в реальном времени.
- **OLAP (Online Analytical Processing)** — системы, оптимизированные для сложных аналитических запросов и чтения больших объемов исторических данных.
- **Polyglot Persistence (Полиглотное хранение)** — использование различных типов хранилищ данных (SQL, NoSQL, Cache) в рамках одной системы для решения разных задач.
- **Source of Truth (Источник истины)** — единственное авторитетное хранилище данных, содержащее актуальную и достоверную информацию.
- **Derived Store (Производное хранилище)** — хранилище, данные в котором получены путем преобразования или агрегации данных из источника истины (например, кэш или витрина данных).

## Интеграция и сообщения

- **Message Queue (Очередь сообщений)** — механизм асинхронной передачи сообщений, где сообщение обрабатывается одним потребителем и удаляется из очереди.
- **Message Broker (Брокер сообщений)** — промежуточное ПО, управляющее передачей сообщений между отправителями и получателями (например, RabbitMQ).
- **Event Streaming (Потоковая передача событий)** — технология обработки непрерывных потоков данных, где события сохраняются и могут быть прочитаны многократно (например, Apache Kafka).
- **Pub/Sub (Publish/Subscribe)** — паттерн обмена сообщениями, где отправители (publishers) рассылают сообщения темам, а подписчики (subscribers) получают их.
- **Dead Letter Queue (DLQ, Очередь недоставленных сообщений)** — очередь для хранения сообщений, которые не удалось обработать после нескольких попыток.
- **Retry Queue (Очередь повторных попыток)** — временное хранилище для сообщений, обработка которых временно невозможна и будет повторена позже.
- **Idempotency (Идемпотентность)** — свойство операции, при котором многократное выполнение дает тот же результат, что и однократное.
- **Transactional Outbox (Транзакционный исходящий ящик)** — паттерн надежной публикации событий, при котором событие сохраняется в БД в той же транзакции, что и бизнес-данные.
- **Inbox Pattern (Паттерн входящего ящика)** — паттерн надежной обработки входящих событий с сохранением статуса обработки в БД для гарантии идемпотентности.
- **CDC (Change Data Capture)** — механизм отслеживания изменений в базе данных и передачи их в другие системы в реальном времени.

## Надежность и эксплуатация

- **SLA (Service Level Agreement)** — соглашение об уровне сервиса, юридический договор между провайдером и клиентом о гарантиях доступности и качества.
- **SLO (Service Level Objective)** — целевые показатели уровня сервиса, внутренние цели команды для выполнения SLA.
- **SLI (Service Level Indicator)** — метрика, измеряющая фактический уровень обслуживания (например, процент успешных запросов).
- **RTO (Recovery Time Objective)** — максимально допустимое время восстановления системы после сбоя.
- **RPO (Recovery Point Objective)** — максимально допустимая потеря данных (во времени) при восстановлении после сбоя.
- **Circuit Breaker (Автоматический выключатель)** — паттерн для предотвращения каскадных сбоев, временно блокирующий вызовы к недоступному сервису.
- **Bulkhead (Переборка)** — паттерн изоляции ресурсов, предотвращающий распространение сбоя из одной части системы на другую.
- **Rate Limiting (Ограничение частоты запросов)** — механизм контроля количества запросов от клиента за единицу времени для защиты системы от перегрузки.

## Экономика и управление

- **TCO (Total Cost of Ownership)** — совокупная стоимость владения системой, включающая затраты на покупку, внедрение, поддержку и вывод из эксплуатации.
- **CapEx (Capital Expenditure)** — капитальные затраты на приобретение активов (серверы, лицензии), амортизируемые со временем.
- **OpEx (Operational Expenditure)** — операционные затраты на текущую деятельность (аренда облака, зарплаты, подписки).
- **Technical Debt (Технический долг)** — дополнительные затраты на будущую доработку системы, возникшие из-за выбора быстрого, но неоптимального решения сейчас.
- **ADR (Architecture Decision Record)** — документ, фиксирующий принятое архитектурное решение, контекст и последствия.
- **ATAM (Architecture Tradeoff Analysis Method)** — метод анализа архитектурных компромиссов для оценки качества архитектуры.

## Облачные технологии

- **Cloud Native (Облачно-нативный подход)** — методология создания и запуска приложений, использующая преимущества облачных вычислений (контейнеры, оркестрация, микросервисы).
- **IaaS (Infrastructure as a Service)** — модель облака, предоставляющая виртуальную инфраструктуру (серверы, сети, диски).
- **PaaS (Platform as a Service)** — модель облака, предоставляющая платформу для разработки и запуска приложений без управления инфраструктурой.
- **SaaS (Software as a Service)** — модель облака, предоставляющая готовое программное обеспечение через браузер.
- **Managed Database (Управляемая база данных)** — облачный сервис БД, где провайдер берет на себя администрирование, бэкапы и масштабирование.
- **FinOps** — практика управления облачными финансами, направленная на максимизацию бизнес-ценности при оптимизации затрат на облако.
