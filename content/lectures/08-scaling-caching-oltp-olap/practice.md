# Практика — Лекция 8: секция «Стратегия масштабирования» итогового Blueprint

**Этап:** practice · **База:** templates/practice.md, practice-contract, draft.md §5–6 · **Формат:** индивидуальная работа над своим кейсом курса + обсуждение

## Цель практики
Добавить в свой итоговый Architecture Blueprint (из Л7) раздел «Стратегия масштабирования»: карта горячих/тёплых/холодных данных, схема кэширования с политикой инвалидации, топ запросов с обоснованием индексов, эскиз ETL-потока для аналитики. Оформить ключевой выбор как ADR-013.

## Формат и время
- Аудиторная мини-практика: 4 мин (классификация датасетов из §6 draft) + разбор.
- Домашняя работа: 60–90 мин индивидуально; обсуждение на следующем занятии перед защитой Blueprint v2.

## Задание (по шагам)
1. **Профилирование (WHAT-уровень).** Опишите top-5 операций вашей системы по нагрузке: тип (чтение/запись), частота [примерно], чувствительность к latency. Обоснуйте приоритет оптимизаций.
2. **Карта температуры.** Разнесите основные датасеты по классам hot/warm/cold; для каждого — носитель (класс решения), срок «остывания», связь с retention-политикой (Л4) и комплаенсом копий (Л6). Отметьте PII-риски перемещения.
3. **Схема кэширования.** Для самой «болящей» операции чтения выберите стратегию (Cache-Aside / Read-Through / Write-Through / Write-Behind) и заполните карточку: что кешируем, как инвалидируем (событие/TTL/комбинация), что происходит при потере кэша, метрика успеха (hit ratio, p95). Явно укажите: источник истины остаётся OLTP-СУБД.
4. **Матрица индексов.** Таблица: запрос → предлагаемый индекс (состав на уровне WHAT) → ожидаемая польза → цена (write amplification, место) → решение. Добавьте минимум один «удаляемый/не добавляемый» индекс с обоснованием отказа.
5. **Аналитический контур.** Нарисуйте поток: источник (primary или реплика — обоснуйте) → извлечение (batch/CDC, лаг) → staging → модель (витрина) → BI. Выберите ETL vs ELT с trade-off. Укажите, какие данные НЕ уходят в DWH и почему (PII/резиденция).
6. **ADR-013.** Оформите главный выбор (обычно «разделение OLTP/OLAP» или «кэш + инвалидация») по критериям валидного ADR из Л7: контекст, решение, альтернативы (минимум 2, включая «ничего не менять»), последствия.

## Шаблоны артефактов
**Карточка кэша:** ключ/значение | стратегия | инвалидация | TTL+риск устаревания | поведение при промахе/падении | метрика.
**Матрица индексов:** запрос | индекс (колонки, порядок) | польза | цена | вердикт.
**Карта температуры:** датасет | класс | носитель | lifecycle-правило | retention/PII-заметка.
**ADR-013:** заголовок → статус → контекст → решение → альтернативы → последствия (формат `knowledge/system-design/ADR.md`).

## Критерии оценки (100)
| Критерий | Баллы | Что засчитывается |
|---|---|---|
| Карта hot/warm/cold с привязкой к retention/комплаенсу | 20 | все датасеты классифицированы, правила перехода явны |
| Схема кэша с осознанной инвалидацией и derived-дисциплиной | 25 | стратегия выбрана через trade-off, описаны промах/падение/устаревание |
| Матрица индексов с ценой (не только «добавить») | 20 | есть обоснованный отказ/удаление |
| ETL-поток без нагрузки на primary, с обоснованием лага и ETL/ELT | 20 | источник, стадии, границы PII показаны |
| ADR-013 валиден по Л7 | 15 | контекст/альтернативы/последствия, связь с NFR и бюджетом |

Уровни: Н (не принято) / С (средний) / П (профессиональный) — как в практике Л7.

## Подсказки (открывать после попытки)
- Сначала спросите «где болит» (метрики), потом выбирайте механизм — Д1.
- Кэш без инвалидации = рассинхронизированное состояние; проверьте себя вопросом «что увидит клиент через минуту после изменения?» — Д3/Д4.
- Если отчёт можно «просто» пустить по реплике — посчитайте объём истории: реплика лечит конкуренцию нагрузок, но не физику сканирования — Д6.
- Лаг ETL — предмет договорённости с бизнесом, а не техническая деталь — Д7.
- Источники: `knowledge/databases/oltp-olap.md`, `storage-selection.md`, `system-design/trade-offs.md`, `nfr.md`.

## Типичные ошибки
1. «Кэшируем всё» без hit-ratio метрики и политики инвалидации.
2. Индексы «на будущее» без строки цены в матрице.
3. Аналитика на primary «потому что реплика одна» — без обсуждения рисков (Л6).
4. Перенос в DWH персональных данных без обезличивания (нарушение рамки Л4).
5. Копирование архитектуры Netflix/Uber без проверки контекста (масштаб x10 ≠ масштаб x10000).
