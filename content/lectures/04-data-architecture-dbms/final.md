# Лекция 4. История, эволюция и виды СУБД. Транзакции, PACELC и Data Governance

> Статус: кандидат в final. Причина: ожидает human review / human fact-check. Источник истины темы: specs/syllabus.md, Лекция 4.

## Цель занятия

Научиться выбирать класс СУБД под конкретную задачу и паттерн доступа: понимать ландшафт систем хранения через призму их эволюции, анализировать распределённые базы с помощью теорем CAP и PACELC, осознанно работать с гарантиями транзакций (ACID, уровни изоляции), разделять OLTP- и OLAP-нагрузки в полиглотном стеке с явным источником истины и проектировать базовую стратегию Data Governance (защита PII, GDPR/152-ФЗ, crypto-shredding).

## Learning Objectives

По окончании лекции студенты смогут:
1. **Различать** основные классы СУБД (реляционные, key-value, документные, wide-column, графовые, time-series, поисковые движки, векторные, объектные хранилища, DWH/lakehouse, event streaming) и связывать каждый класс с исторической задачей, которую он решал.
2. **Применять** Storage Selection Matrix для обоснования выбора класса СУБД по критериям NFR: тип нагрузки, объём, read/write ratio, latency, consistency, retention, compliance, стоимость и экспертиза команды.
3. **Анализировать** поведение распределённой БД через CAP и PACELC: предсказывать реакцию на сетевое разбиение и описывать компромисс «латентность ↔ согласованность» в штатном режиме.
4. **Объяснять** свойства ACID, механизмы Commit/Rollback, уровни изоляции SQL и аномалии конкурентного доступа (Dirty Read, Non-repeatable Read, Phantom Read, Lost Update, Deadlock); подбирать уровень изоляции под бизнес-операцию.
5. **Оценивать** компромиссы Polyglot Persistence: различать Source of Truth и Derived Store, отделять OLTP от OLAP, не подменять хранилище состояния очередями и streaming-логами.
6. **Создавать** фрагмент стратегии Data Governance: классификация PII, меры защиты (маскирование, токенизация, шифрование at rest/in transit), исполнение права на удаление (GDPR, 152-ФЗ, crypto-shredding).

## Hook

**История-предупреждение** (обобщённый учебный пример, композитная история, не привязан к реальной компании; совпадения с реальными брендами случайны).

Молодая сервисная компания писала систему бронирования и платежей в документной СУБД. Аргумент на архитектурном комитете звучал так: «NoSQL масштабируется лучше, реляционные таблицы — это прошлый век». Через полгода:

1. В час пик два клиента одновременно забронировали один автомобиль. Приложение прочитало статус «свободен», оба записали «занят» — классический **Lost Update**: без транзакционных гарантий схема из трёх таблиц не спасает.
2. Ежедневный отчёт о выручке перестал сходиться с банковской выпиской: аналитику считали по репликам с eventual consistency, где данные «догоняли» с задержкой — для финансов это неприемлемо.
3. Одна база обслуживала и транзакции, и телеметрию автомобилей, и аналитические сканирования: тяжёлый отчёт ложился поверх OLTP-блокировок, пользовательская latency прыгала в разы (порядок ухудшения — учебная иллюстрация; точные значения зависят от окружения и профиля нагрузки).

Преподаватель задаёт вопросы аудитории:
- Можно ли было предсказать провал **до** написания кода — одними требованиями и таблицей критериев?
- Что должна была ответить система при обрыве канала между дата-центрами: ждать или принимать запись? Кто принимал это решение и задокументировал ли его?
- Помогла бы смена уровня изоляции транзакций, не меняя СУБД? А чего она стоила бы?

Мостик из Лекции 3: «Мы спроектировали логические модели в 3НФ и оставили вопрос „где это жить будет?“. Сегодня каждый контекст каршеринга получает технологический дом — и мы учимся выбирать его по критериям, а не по моде».

## Теоретический блок

### Часть 1. Эволюция СУБД: почему «зоопарк» вообще существует (5 мин)

Каждая волна технологий хранения — ответ на конкретную нерешённую проблему, а не «просто новая мода».

| Период | Модель / поколение | Примеры (как иллюстрация эпохи) | Какую проблему решали | Какая новая проблема осталась |
|---|---|---|---|---|
| 1950–60-е | Файловые системы | плоские файлы | хранение | дублирование, нет целостности, нет конкурентного доступа |
| 1960-е | Иерархическая | IBM IMS (1968) | централизованное управление | жёсткое дерево, связи M:N |
| 1960-е | Сетевая | CODASYL | связи многие-ко-многим | сложность навигации и программирования |
| 1970 | Реляционная модель | работа Э. Кодда; затем SQL | декларативность, математическая строгость, целостность | стоимость enterprise-решений, масштаб |
| 1980–90-е | Коммерческие RDBMS | Oracle (1979), DB2 (1983), SQL Server (1989) | зрелость, транзакции, стандарт SQL (ANSI SQL-86/92) | лицензии, вертикальный потолок |
| 1990–2000-е | Открытые RDBMS | MySQL (1995), PostgreSQL (1996), SQLite (2000) | доступность, сообщество | тот же вертикальный масштаб |
| 2009–2014+ | Облачные СУБД | Amazon RDS (2009), Azure SQL (2010), Aurora (2014) | снятие операционной рутины | vendor lock-in, data residency |
| 2008–2010-е | NoSQL («Not Only SQL») | MongoDB (2009), Redis (2009), Cassandra (2008), Neo4j (2007) | горизонтальный масштаб, гибкая схема, специализация | ослабленные гарантии, зоопарк операций |
| 2020-е | Векторные / AI-native | Pinecone (2021), Qdrant (2022), pgvector | семантический поиск, RAG, embeddings | ниша: только similarity-задачи |

Годы и последовательность — по `knowledge/databases/dbms-history.md`.

**Как читать таймлайн (методология, а не даты).** Даты релизов — не предмет запоминания; предмет — повторяющийся цикл, в котором каждая волна возникает по одной из трёх причин:
1. **Новая форма данных** не помещается в прежнюю модель (граф поездок и связей — сетевая модель; JSON-агрегаты заказа — документные; поток меток времени — time-series; эмбеддинги — векторные).
2. **Новый масштаб нагрузки** пробивает потолок прежнего движка (веб-масштаб конца 2000-х → NoSQL; Petabyte-аналитика → колоночные DWH).
3. **Новая операционная модель** меняет экономику владения (облако сняло операционную рутину — и добавило lock-in и вопросы юрисдикции данных).

Проверочное упражнение для аудитории: возьмите любую современную специализированную СУБД и назовите, какой из трёх драйверов её породил. Если не можете — вероятно, перед вами маркетинг, а не технология (это прямая связь с анти-паттерном Resume-Driven Development ниже).

Историческая оптика полезна и как инструмент прогнозирования: если вы понимаете, какая нерешённая проблема стоит за текущим поколением систем, вы можете предсказать следующий расщепление. У волны 2020-х (векторные БД, AI-native хранилища) уже видна «оставшаяся проблема»: семантические индексы живут отдельно от транзакционных данных, и согласование «документ обновлён → эмбеддинг устарел» сегодня решается кустарно. Это учебная экстраполяция, не прогноз рынка.

**Три сквозных урока эволюции** (полезны на экзамене и на защите blueprint):
- Урок 1. **Модель данных тянет за собой язык запросов.** Иерархическая модель — навигационный вызов «идти по дереву»; реляционная — декларативный SQL; документная — агрегатные конвейеры; графовая — языки обхода связей. Выбирая модель, вы выбираете, каким языком будет говорить ваша команда с данными три года.
- Урок 2. **Гарантии нельзя «дописать потом».** Реляционные системы продавали транзакции «из коробки»; NoSQL-волна осознанно от них отказалась ради масштаба; частично вернуть пришлось через multi-document транзакции и кворумы — то есть компромисс был пересобран заново, но уже дороже. Проектируя систему сегодня, фиксируйте требуемые гарантии в ADR, а не «включите ACID когда понадобится».
- Урок 3. **Каждая волна ошибалась в крайности.** «Реляционные — это прошлый век» (Hook), «NoSQL не нужен, всё в Postgres», «аналитика прямо в продакшен-реплике» — все три фразы переживали десятилетия. Ни одна универсальная ставка не выдерживала проверку нагрузкой; устойчивой оказалась только методология выбора по критериям (Часть 3).

**Вывод части:** вопрос «какая СУБД лучшая?» методологически неверен. Верный вопрос: «какая проблема у нас сейчас и какие гарантии мы готовы покупать ценой сложности и денег?»

### Часть 2. Классы СУБД и их trade-offs (8 мин)

Обзор по `knowledge/databases/dbms-types.md`. Технологии — примеры одного из вариантов, не стандарты.

| Класс | Модель данных | Транзакции | Масштабирование | Типовой паттерн доступа | Когда НЕ использовать |
|---|---|---|---|---|---|
| Реляционные (например, PostgreSQL, MySQL, Oracle) | таблицы, связи FK | полные ACID | преимущественно вертикальное | точечные, диапазоны, JOIN | нестабильная схема, сотни узлов, экстремальный write-поток |
| Key-value (например, Redis, DynamoDB) | ключ → значение | как правило нет | горизонтальное | доступ строго по ключу | сложные запросы, фильтрация по полям |
| Документные (например, MongoDB, CouchDB) | JSON/BSON-документы | чаще на уровне документа; multi-doc зависит от версии/конфигурации (см. `knowledge/databases/dbms-types.md`) | горизонтальное | агрегат целиком | множество JOIN, строгая регуляторная схема |
| Wide-column (например, Cassandra, HBase, ClickHouse*) | колоночные семейства | ограниченные | линейное горизонтальное | запись потоком, чтение по ключу/диапазону | частые точечные обновления, сложные ad-hoc JOIN |
| Графовые (например, Neo4j, Neptune) | узлы, рёбра, свойства | зависит от БД | зависит от БД | обход связей на N уровней | простые CRUD без глубоких связей |
| Time-series (например, InfluxDB, TimescaleDB, Prometheus) | точки (timestamp, value) | ограниченные | горизонтальное |записи-тяжёлый поток (write-heavy), окна агрегаций | данные без временной природы, ACID-бизнес-операции |
| Поисковый движок (например, Elasticsearch, OpenSearch) | инвертированный индекс | нет (вторичная копия) | горизонтальное | полнотекст, фасеты, ранжирование | как основное хранилище истины |
| Векторная БД (например, Qdrant, Pinecone, pgvector) | эмбеддинги | нет | горизонтальное | k-NN / ANN similarity | exact-match CRUD, низкая latency точечных выборок |
| Объектное хранилище (например, S3, MinIO, Ceph) | объекты + метаданные | нет (immutable объекты) | практически неограниченное | файлы, архивы, бэкапы | частые обновления, транзакции, низколатентный доступ к миллионам мелких объектов |
| DWH / Lakehouse (например, BigQuery, Snowflake, Redshift; Databricks/Iceberg) | колоночные таблицы, star/snowflake | нет классических OLTP-транзакций | горизонтальное | OLAP-агрегации по истории | OLTP-нагрузка, real-time < секунды |
| Event streaming (например, Kafka, Pulsar, Kinesis) | журнал событий (лог) | guarantees on delivery/order, не бизнес-ACID | горизонтальное | append + replay потока | **не замена БД состояния**; не для ad-hoc запросов и JOIN |

\* ClickHouse — колоночная OLAP-СУБД, соседствует с wide-column по хранению, но целевая ниша — аналитика (см. Лекцию 8).

Три правила чтения таблицы:
1. Класс определяет **паттерн доступа**, ради которого оптимизированы физическая структура и протоколы.
2. Ослабление одной гарантии (например, транзакционной) — это не «дефект», а плата за другое свойство (масштаб, гибкость схемы).
3. Очередь/streaming-лог передаёт и журналирует события, но не заменяет СУБД как хранилище бизнес-состояния (запрет контракта курса).

### Часть 2b. Мини-карточки классов: как класс звучит в диалоге с вендором (8 мин)

Сводная таблица даёт скелет; на защите blueprint от вас будут ждать живого разговора. Ниже — по классу: одна типовая задача, один честный разговор о гарантиях и один вопрос, который обнажает непонимание. Технологии указаны как примеры класса; их возможности зависят от версии и конфигурации (см. реестр fact-check Лекции 4).

**Реляционные.** Задача кейса: бронирование автомобиля. Сильная сторона — декларативный запрос плюс ограничения целостности, исполняемые движком (PK/UNIQUE/FK из Лекции 3 работают буквально). Честный разговор: «вертикальный потолок» — миф и правда одновременно: современные системы читают с реплик и партиционируют таблицы, но распределённые JOIN остаются дорогими; планировать надо не «когда умрём», а «какой объём на одном узле комфортен» [порядок величин зависит от оборудования — учебная иллюстрация]. Вопрос-обнажалка: «Покажите запрос, который вы не сможете написать эффективно». Если ответа нет — класс выбран по привычке, а не по анализу.

**Key-value.** Задача: сессии, счётчики лимитов, горячий кэш карточек авто. Разговор: доступ строго по ключу — всё остальное придётся строить поверх, и тогда вы платите за неудобство вместо того чтобы получить простоту. Отдельная ловушка: in-memory-хранилище с персистентностью (снимки + журнал операций) — это не durability уровня СУБД с ACID-транзакциями; гарантия переживаемости сбоя зависит от настроек fsync и может стоить латентности. Вопрос-обнажалка: «Как найти все активные брони клиента, если ключ — идентификатор брони?» Правильный ответ включает «никак, для этого нужен другой класс или второй индекс-проекция».

**Документные.** Задача: агрегат заявки на аренду с вариативными полями (разные тарифы, разные пакеты услуг). Разговор: гибкость схемы — это не «схемы нет», это «схема в приложении»: валидация переезжает в код и деградирует со временем; регуляторно значимые поля лучше держать под явной схемой. Multi-document транзакции существуют в современных версиях, но имеют цену (блокировки, ограничения по кластерам) — изучайте их условия до того, как на них положиться. Вопрос-обнажалка: «Что у вас будет, если через год поле `car_id` начнут писать то числом, то строкой?» Ответ должен содержать план миграции данных, а не надежду на типизацию драйвера.

**Wide-column.** Задача: телеметрия парка при росте узлов. Разговор: модель запроса проектируется *до* записи — каждая точка входа требует своей физической раскладки (denormalization by query), ad-hoc отчёты — чужая территория. Консистентность настраивается на уровне запроса (кворум чтения/записи): можно купить сильную согласованность ценой латентности и части узлов — то есть CAP здесь не абстракция, а параметр вызова. Вопрос-обнажалка: «Покажите ваш clustering key и объясните, какие запросы он обслуживает и какие делает невозможными».

**Графовые.** Задача: расследование мошенничества — связи клиентов, водителей, устройств, платёжных инструментов на N уровней. Разговор: этот класс покупается ради обхода связей; если ваши запросы — «найти строку по id», вы платите за граф зря. Масштабирование графовых систем сложнее, чем key-value: горячие узлы («суперзвёзды» с миллионами рёбер) ломают балансировку. Вопрос-обнажалка: «Насколько глубокий обход вам реально нужен и какова его стоимость в p95?»

**Time-series.** Задача: GPS-точки и метрики состояния авто. Разговор: автоматическое удаление старых данных по TTL и непрерывные агрегаты — то, за что в реляционной базе пришлось бы писать крон-задачи; но бизнес-операции (штраф, оплата) здесь жить не должны. Вопрос-обнажалка: «Гарантируете ли вы, что данные за последний час никогда не потеряются при падении узла?» Ответ про буферизацию и репликацию — и про RPO (Лекция 6).

**Поисковый движок.** Задача: «свободно рядом», фасеты, ранжирование. Разговор: это инвертированный индекс, то есть производная копия; источник истины остаётся в ядре, синхронизация — CDC/события, лаг — метрика. Пытаться использовать его как основное хранилище — самый частый способ потерять данные без возможности восстановления. Вопрос-обнажалка: «Что произойдёт с выдачей поиска, если канал синхронизации упадёт на 30 минут?»

**Векторная БД.** Задача: семантический поиск по обращениям в поддержку, RAG по документации правил сервиса. Разговор: приближённый (approximate) поиск по эмбеддингам — это другая математика и другие гарантии: результат зависит от модели эмбеддинга, её версии и нормализации; обновление модели означает пересчёт всех векторов. Хранить здесь бизнес-состояние нельзя; проверять точность нужно метриками recall@k, а не «на глаз похоже». Вопрос-обнажалка: «Как вы обнаружите, что новый эмбеддер ухудшил качество выдачи?»

**Объектное хранилище.** Задача: архив треков поездок, экспорты отчётности, бэкапы (Лекция 6). Разговор: immutable-объекты, дешёвые ёмкости, практически неограниченный масштаб — и почти непригодный доступ к миллионам мелких файлов с низкой латентностью; отсутствие транзакций компенсируется версионированием и жизненными политиками. Вопрос-обнажалка: «Как вы удалите персональные данные клиента из архивных объектов?» — прямая связь с crypto-shredding (Часть 7).

**DWH / lakehouse.** Задача: выручка, утилизация парка, когорты. Разговор: колоночное хранение плюс пакетная перезапись истории; OLTP-нагрузка сюда не входит ни при каких настройках; схема проектируется звёздами/снежинками, а не 3НФ (детали — Лекция 8). Вопрос-обнажалка: «Откуда берется факт и кто отвечает, если DWH расходится с ядром?»

**Event streaming.** Задача: доставка событий «Поездка завершена» подписчикам, replay истории. Разговор: гарантии доставки и порядка — не бизнес-ACID; состояние приложения всё равно должно жить в СУБД, иначе восстановление после сбоя превращается в археологию по журналу. Вопрос-обнажалка: «Где хранится текущий статус поездки и что случится, если консьюмер обработает событие дважды?» (идемпотентность — тема Лекции 5/6).

**Как пользоваться мини-карточками.** На семинаре каждый студент тянет класс и за 60 секунд обязан назвать: задачу, гарантию, которую класс ослабляет, и запрет применения. Это формирует язык, нужный в Части 3.

### Часть 3. Критерии выбора: Storage Selection Matrix (4 мин)

По `knowledge/databases/storage-selection.md`. Восемь осей оценки для каждого компонента/контекста:

1. **Тип нагрузки:** OLTP / OLAP / streaming / specialized (граф, гео, поиск, вектор).
2. **Объём и рост:** текущий + прогноз на 2–3 года (<100 GB — любая; 1–100 TB — wide-column/distributed SQL/OLAP; 100 TB+ — data lake).
3. **Read/Write ratio:** read-heavy → кэш/OLAP/search; write-heavy → time-series/wide-column/streaming; balanced → реляционные/документные.
4. **Latency (p95/p99):** <1 мс — in-memory; 1–10 мс — реляционные/документные с индексами; 100+ мс — допустимо для аналитики.
5. **Consistency:** strong (деньги, инвентарь) / causal / eventual (ленты, логи, телеметрия).
6. **Retention:** TTL-кэш vs активные данные vs архив на годы (compliance).
7. **Compliance:** GDPR/152-ФЗ (PII, локализация), PCI DSS (платежи), HIPAA и др.
8. **Cost & экспертиза:** лицензии, инфраструктура, эксплуатация (DBA), наличие навыков в команде (TCO целиком, не только «цена коробки»).

Red flags (выбор почти наверняка ошибочен): OLTP-база для аналитики; NoSQL для финансовых транзакций без понимания гарантий; файлы в реляционной БД; «одна СУБД для всего»; выбор потому что «модная» (Resume-Driven Development — антипаттерн из глоссария).

### Часть 3b. Работа с матрицей: как считать оси и что делать при конфликте (6 мин)

Матрица превращается из таблицы в инструмент, когда известно, **чем заполняется каждая ячейка**. Разберём источники значений — это то, чего не хватает в 90% студенческих работ.

| Ось | Откуда берётся значение | Кто владелец значения | Типовая ошибка заполнения |
|---|---|---|---|
| Тип нагрузки | Из паттерна доступа требования: сколько точек входа, какие запросы (Лекция 2, FR + события домена) | Аналитик | «OLTP и OLAP одновременно» — значит, два дома, а не один компромисс |
| Объём и рост | Метрики текущей системы или оценка от NFR пользователя (см. калькуляцию ниже) | Владелец продукта / инфраструктура | Указание текущего объёма без прогноза: через год решение уже неверно |
| Read/Write ratio | Логи, метрики, либо честная оценка «на пальцах» с пометкой [оценка] | Разработка | Игнорирование пиков: среднее 70/30 может быть 5/95 в час пик |
| Latency | SLO/SLA из Лекции 1, причём в нужном перцентиле | Product Owner | Требование «быстро» вместо p95 ≤ 300 мс на операцию поиска |
| Consistency | Бизнес-цена ошибки факта (двойная бронь vs устаревшая лента) | Владелец бизнеса | Единое «strong» на всю систему из осторожности |
| Retention | Регуляторные сроки + продуктовые решения об архиве | DPO / юрист | «Храним всё» — растущая стоимость и неисполнимое право на удаление |
| Compliance | Классификация данных (PII, платёжные), юрисдикции пользователей | DPO | Забытая телеметрия: треки тоже могут быть персональными данными |
| Cost & экспертиза | TCO: подписка + эксплуатация + дежурства + обучение; наличие навыков | Руководитель команды | Сравнение «цены коробки»: self-hosted дешевле только при наличии DBA |

**Пример калькуляции оси «объём и рост» для Телематики** (учебная прикидка уровня Лекции 1; все параметры — условные значения сквозного кейса, требуют проверки):

```
200 автомобилей × 1 событие каждые 10 с = 20 событий/с на авто
Итого: 4 000 событий/с ≈ 345,6 млн событий/сутки
При ~120 байт на точку (timestamp + координаты + скорость + id):
≈ 41 ГБ/сутки сырых данных ≈ 1,2 ТБ/месяц ≈ 15 ТБ/год
```

Вывод из одной строки расчёта: за три года MVP упирается в десятки терабайт — это территория time-series/wide-column плюс выгрузка холодных слоёв в объектное хранилище, а не «посмотрим». Второй вывод важнее первого: **если вы не можете назвать порядок величины объёма, вы не можете выбрать класс**; поэтому в ADR колонка «Объём и рост» обязательна даже с оценкой, помеченной как оценка.

**Разрешение конфликтов осей.** В реальных проектах оси противоречат друг другу — вот три типовых конфликта и способ их снимать:
1. **Latency vs Consistency** (поиск «рядом» должен отвечать быстро, но занятость авто должна быть точной). Разрешение: разделить ответственность — быстрый derived store для показа, гарантированная проверка в ядре для подтверждения. Конфликт исчезает, когда перестаёт быть одним решением.
2. **Cost vs Compliance** (архив платежей нужен 5 лет, горячее хранение дорогое). Разрешение: многоуровневое хранение — горячий слой в ядре, холодный в объектном хранилище; соответствие обеспечивается шифрованием и политиками доступа, а не типом носителя.
3. **Consistency vs Availability** (при сетевом разделе). Разрешение — PACELC-формулировка в ADR (Часть 4): не искать «правильный ответ», а явно назначить цену отказа.

**Вес осей не одинаков.** Методика для курса: compliance и consistency — оси-ограничители (нарушение исключает кандидата); latency, объём, R/W — оси-фильтры (сужают класс); cost & экспертиза — ось-предпочтение (выбирает среди равных). Такой порядок применим и к выбору между managed и self-hosted, и к выбору облака.

### Часть 4. Распределённые системы: CAP и PACELC (5 мин)

**CAP** (Э. Брюэр, 2000; доказательство Джилберт–Линч, 2002): распределённая система не может одновременно гарантировать более двух свойств:
- **C**onsistency — все узлы видят одни данные в один момент;
- **A**vailability — каждый запрос получает ответ (не таймаут);
- **P**artition tolerance — система работает при потере связи между узлами.

Важное уточнение уровня WHY: сети ненадёжны, поэтому P в геораспределённой системе не «опция», а факт жизни — реальный выбор при разделе всегда **C или A**:
- **CP** — при разделе меньшинство отказывает в обслуживании ради согласованности (примеры класса решений: ZooKeeper, etcd);
- **AP** — при разделе обе стороны продолжают писать, конфликты разрешаются позже (примеры класса: Cassandra, DynamoDB);
- «CA» — по сути single-node СУБД вне кластера: при первой же сетевой проблеме иллюзия рассыпается.

**Критика CAP:** раздел — редкое событие, а латентность — ежедневная реальность. Отсюда **PACELC** (Д. Абади, 2010):

```
Если Partition (P):    выбираем Availability (A) или Consistency (C)
Else (штатный режим):  выбираем Latency (L) или Consistency (C)
```

| Обозначение | Поведение | Примеры (типовая конфигурация; зависит от версий и настроек — см. `knowledge/databases/cap-pacelc.md`) |
|---|---|---|
| PA/EL | доступна при разделе; в норме жертвует согласованностью ради скорости | Cassandra, DynamoDB (eventual), Redis Cluster |
| PA/EC | доступна при разделе; в норме согласованна | MongoDB с writeConcern majority, Cassandra с QUORUM |
| PC/EL | при разделе — согласованность; в норме — низкая задержка | Spanner (требует точных часов — редкая комбинация) |
| PC/EC | согласованность всегда | PostgreSQL single-node / synchronous replication, etcd |

Как применять архитектору: для каждой критичной операции записать в ADR пару «при разделе — X; в норме платим Y». Фразы вендора «наша система и консистентна, и доступна» проверяются одним вопросом: «что происходит при partition и что при normally-high-latency?»

### Часть 4b. PACELC на трёх сквозных примерах: один сценарий — три решения (5 мин)

Одна и та же история из Hook («оборвался канал между площадками») разбирается трижды — для трёх разных контекстов каршеринга. Цель упражнения: увидеть, что класс системы не «хороший/плохой», а дорогой или дешёвый **для конкретной бизнес-операции**.

**Пример 1. Бронирование (PC/EC).** Ядро — реляционное, репликация синхронная в пределах региона. При разделе: узлы меньшинства отказывают в записи (возвращают ошибку, клиент видит «попробуйте через минуту»). В штатном режиме: запись ждёт подтверждения реплик — плюс единицы–десятки миллисекунд к латентности COMMIT [учебная иллюстрация; зависит от расстояния между ЦОД и настроек]. Цена раздела: часть клиентов не сможет забронировать несколько минут. Почему выбираем это: двойная броня одного автомобиля = конфликт в поддержке, возврат денег, репутационный ущерб; временный отказ = неприятность, легко измеримая. Формулировка для ADR: «При partition жертвуем доступностью меньшинства; в норме платим латентностью записи ради того, что факт „авто занято“ существует ровно в одном экземпляре».

**Пример 2. Телеметрия (PA/EL).** Time-series/wide-column-класс с локальной записью и последующей конвергенцией. При разделе: каждый узел принимает GPS-пакеты и буферизует их локально; после восстановления канала потоки сведения расходятся по времени, но не теряются (окно расхождения — минуты [учебная иллюстрация]). В штатном режиме: запись без ожидания кворума — минимальная латентность приёмной точки. Цена: «история движения» временно несогласованна. Почему это приемлемо: бизнес-решения (штраф, блокировка) принимаются не по телеметрии напрямую, а по транзакционному ядру; телеметрия — доказательственная база, где допустима реконструкция. Если бы мы поставили сюда PC/EC, потеряли бы приём данных при любом сетевом дрожании — то есть купили бы гарантию, которая никому не нужна.

**Пример 3. Поиск свободных рядом (derived store, AP по построению).** Индекс — проекция ядра. При разделе: отдаёт устаревшую картину («свободно» может оказаться «занято»). В штатном режиме: отвечает быстро, потому что не участвует в согласованных записях вообще. Цена: ложноположительные выдачи. Почему приемлемо: финальная проверка занятости выполняется в CP-ядре при подтверждении брони; UX обязан корректно обрабатывать «авто только что заняли» (предложить ближайшее). Ключевая архитектурная фраза: «индекс поиска — не источник истины о занятости».

**Что из этого следует методологически.** Три примера дают правило формулирования: **PACELC-пары назначаются не системе целиком, а каждой критичной операции**. В одной платформе сосуществуют PC/EC (деньги), PA/EL (поток) и «устаревшее чтение с проверкой» (проекция). Вопрос экзаменатора «какая у вас CAP-конфигурация?» методологически некорректен — некорректен ровно так же, как «какая у вас лучшая СУБД»; корректный вопрос — «что делает операция X при разделе и чем вы платите в норме».

**Мини-таблица для защиты blueprint** (заполняется студентами по своему кейсу):

| Операция | Поведение при partition | Плата в штатном режиме | Бизнес-обоснование цены |
|---|---|---|---|
| Подтверждение брони | Отказ меньшинства | +латентность COMMIT | Двойная бронь дороже отказа |
| Приём GPS-точки | Локальный буфер, сведение позже | — | Данные не должны теряться |
| Выдача поиска | Устаревшая картина | — | Проверка в ядре спасает исход |
| Проведение оплаты | ? | ? | Заполнить самостоятельно |

Последняя строка оставлена незаполненной намеренно: на семинаре студенты заполняют её и защищают перед аудиторией (ответ ожидаемого типа — PC/EC с явным указанием RPO, см. Лекцию 6).

### Часть 5. Транзакции: ACID, изоляция, конкурентный доступ (5 мин)

**Транзакция** — логическая единица работы с БД: либо все операции зафиксированы (COMMIT), либо все отменены (ROLLBACK). Пример уровня WHAT: перевод между счетами = списание + зачисление как единое целое; бронирование = «проверить свободно → занять → создать запись» как единое целое.

**ACID** (по `knowledge/databases/transactions-acid.md`, Gray & Reuter 1993):

| Свойство | Гарантия | Механизм (концептуально) |
|---|---|---|
| **A**tomicity | нет частичных обновлений | COMMIT / ROLLBACK |
| **C**onsistency | БД переходит из корректного состояния в корректное | ограничения из Лекции 3: PK/FK/UNIQUE/CHECK, бизнес-правила |
| **I**solation | параллельные транзакции не мешают друг другу | блокировки (S/X), MVCC |
| **D**urability | закоммиченное переживает сбой питания | WAL (журнал предзаписи), fsync; дальше — репликация и бэкапы (Лекция 6) |

**Аномалии конкурентного доступа:**
- **Dirty Read** — чтение незакоммиченных изменений другой транзакции;
- **Non-repeatable Read** — повторное чтение той же строки даёт другие значения;
- **Phantom Read** — повтор диапазона видит «призрачные» новые строки;
- **Lost Update** — две транзакции прочитали и изменили одни данные, одна перезаписала другую (герой нашего Hook);
- **Deadlock** — взаимное ожидание блокировок; СУБД обнаруживает цикл и откатывает одну из транзакций — приложение обязано уметь повторять.

**Уровни изоляции SQL — таблица компромиссов:**

| Уровень | Dirty | Non-repeatable | Phantom | Конкурентность |
|---|---|---|---|---|
| Read Uncommitted | возможен | возможен | возможен | максимальная |
| Read Committed | нет | возможен | возможен | высокая |
| Repeatable Read | нет | нет | возможен* | средняя |
| Serializable | нет | нет | нет | минимальная |

\* по формальному стандарту; конкретные СУБД реализуют по-разному (например, PostgreSQL на уровне Repeatable Read подавляет фантомы за счёт MVCC-правил и предикатных блокировок — детали зависят от версии; сверяйте с официальной документацией PostgreSQL). Значения по умолчанию популярных СУБД — см. базу знаний `knowledge/databases/transactions-acid.md`; проверять по документации конкретной версии.

**Управленческий смысл:** изоляция — это страховка, priced per transaction (страховка, цена которой начисляется на каждую транзакцию). Для горячего инвентаря (одно авто — много заявок) Serializable безопасен, но дорог: падает пропускная способность. Часто достаточно уровня Read Committed + условного обновления строки («занять, только если ещё свободен») — решение фиксируется в ADR вместе с тестом на Lost Update.

### Часть 5b. SQL-демо: аномалии конкурентного доступа руками (6 мин)

Формальные определения запоминаются плохо; одна демонстрация в двух параллельных сессиях — хорошо. Демонстрация учебная: синтаксис приведён для диалекта PostgreSQL и **не является рекомендацией по продакшен-конфигурированию**; поведение конкретных СУБД и версий различается (см. реестр fact-check, пункты про уровни изоляции по умолчанию).

Исходная таблица из модели Лекции 3 (уровень WHAT):

```sql
CREATE TABLE car (
    id          BIGINT PRIMARY KEY,
    status      TEXT NOT NULL CHECK (status IN ('free','reserved','in_use')),
    version     INT  NOT NULL DEFAULT 0
);
INSERT INTO car (id, status) VALUES (42, 'free');
```

**Демо 1. Dirty Read (Read Uncommitted).** Сессия A меняет статус и не коммитит; сессия B читает его.

```sql
-- Сессия A
BEGIN;
UPDATE car SET status = 'reserved' WHERE id = 42;   -- COMMIT ещё не выполнен

-- Сессия B
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT status FROM car WHERE id = 42;               -- увидит 'reserved' до фиксации A
```

Если затем A выполнит ROLLBACK, решение B основано на факте, которого никогда не существовало. Практический вывод: уровень Read Uncommitted в бизнес-код не допускается ни при каких обоснованиях «нужно быстрее».

**Демо 2. Non-repeatable Read (Read Committed).** То же начало, но B читает дважды:

```sql
-- Сессия B (Read Committed)
SELECT status FROM car WHERE id = 42;   -- 'free'
-- ... Сессия A делает COMMIT ...
SELECT status FROM car WHERE id = 42;   -- 'reserved': повторное чтение той же строки изменилось
```

Последствия для приложения: логика «прочитал — проверил — принял решение» внутри одной транзакции ненадёжна, если данные могут меняться под ней. Отсюда правило: проверка и действие должны быть атомарны (см. Демо 4), а не разделены двумя запросами.

**Демо 3. Phantom Read.** B работает с диапазоном:

```sql
-- Сессия B
SELECT count(*) FROM car WHERE status = 'free';   -- например, 7
-- Сессия A: INSERT INTO car (id, status) VALUES (99, 'free'); COMMIT;
SELECT count(*) FROM car WHERE status = 'free';   -- 8: «призрачная» новая строка
```

Важное уточнение уровня HOW: в реализациях с Snapshot Isolation (например, PostgreSQL на уровне Repeatable Read) фантомы подавляются за счёт правил видимости снимка — то есть формальный стандарт SQL и поведение конкретных движков расходятся; сверяйте с документацией вашей версии (пункт P-5 в `fact-check.md`).

**Демо 4. Lost Update — наш Hook, решённый одним запросом.** Неправильно (две операции, гонка):

```sql
-- Так делать нельзя: между SELECT и UPDATE другой клиент успевает занять
SELECT status FROM car WHERE id = 42;              -- оба видят 'free'
UPDATE car SET status = 'reserved' WHERE id = 42;  -- оба пишут — второй перезаписывает
```

Правильно — условное занятие (атомарная операция, «compare-and-set» на уровне строк):

```sql
UPDATE car SET status = 'reserved', version = version + 1
WHERE id = 42 AND status = 'free';
```

Приложение проверяет число затронутых строк: 1 — бронь ваша; 0 — кто-то успел первым, предлагаем ближайшее авто. Работает при обычном Read Committed, конкурентность не убивается.

Правильно — оптимистичная блокировка версией (для случаев низкой коллизии):

```sql
UPDATE car SET status = 'reserved', version = 8
WHERE id = 42 AND version = 7;   -- 0 строк => версия ушла, перечитать и повторить
```

**Демо 5. Deadlock и обязательный retry.** Две транзакции занимают два автомобиля в противоположном порядке:

```sql
-- Сессия A                      -- Сессия B
BEGIN;                           BEGIN;
UPDATE car SET status='reserved' UPDATE car SET status='reserved'
WHERE id = 42;                   WHERE id = 43;
UPDATE car SET status='reserved' UPDATE car SET status='reserved'
WHERE id = 43;                   WHERE id = 42;   -- взаимное ожидание
```

СУБД обнаруживает цикл и откатывает одну транзакцию с ошибкой deadlock. Архитектурные следствия: (1) любой код, пишущий в несколько строк/агрегатов, обязан обрабатывать откат и повторять операцию; (2) упорядочивание ресурсов (всегда занимать id по возрастанию) снижает вероятность цикла; (3) retry без backoff превращает единичный конфликт в шторм — это тема идемпотентности (Лекция 5) и нагрузок (Лекция 8).

**Мини-паттерн для конспекта:** четыре способа закрыть гонку — повысить изоляцию, сделать операцию атомарной (условное обновление), добавить версию (оптимистичная блокировка), вынести ресурс в единственный writer (одна очередь/шард на объект). Первые три показаны выше; четвёртый — архитектурный, разбирается в Лекции 8.

### Часть 5c. Как выбирать уровень изоляции: процедура и критерии (4 мин)

Студенты часто отвечают на вопрос «какой уровень лучше» словами «Serializable, потому что надёжнее». Процедура выбора выглядит иначе — через цену ошибки:

| Вопрос | Ответ «дорогая ошибка» (деньги, безопасность, юридическая значимость) | Ответ «дешёвая ошибка» (UX, статистика) |
|---|---|---|
| Что стоит на кону при неверном чтении? | Возврат средств, штраф не тому клиенту | Показ устаревшего статуса |
| Кто заметит проблему? | Регулятор, аудит, бухгалтерия | Пользователь, метрики |
| Можно ли исправить задним числом? | Часто нет | Да, пересчётом |
| Рекомендуемая стартовая позиция | Атомарная операция + strong-гарантия на запись | Read Committed + принятый лаг |

Три правила вывода:
1. **Начинайте с уровня по умолчанию вашей СУБД** (у популярных систем он разный; уточняйте по документации версии) и повышайте только под конкретную операцию, а не глобально.
2. **Глобальное повышение изоляции — красный флаг.** Оно почти всегда означает, что вместо локального решения (условное обновление, идемпотентность) выбрано «замазать всё».
3. **Решение фиксируется в ADR с тестом.** Без теста на Lost Update/Deadlock под реальной конкуренцией утверждение «у нас безопасно» — вера, а не гарантия.

Практическое упражнение (2 минуты, индивидуально): для операции «начислить штраф по данным телеметрии» определите, какая аномалия возможна, если две службы начисления работают одновременно по одному нарушению; предложите закрытие из четырёх паттернов Части 5b. Ожидаемый ответ класса: риск двойного начисления → уникальный индекс на (нарушение_id, штраф) либо идемпотентный ключ операции; уровень изоляции сам по себе задачу не решает, потому что конфликт между разными транзакциями служб.

### Часть 6. BASE, OLTP vs OLAP, Polyglot Persistence (2 мин)

**BASE** (по `knowledge/databases/acid-base.md`) — профиль распределённых AP-систем: **B**asic **A**vailability, **S**oft **S**tate, **E**ventual Consistency. Это не «плохой ACID», а другая точка компромисса: окно несогласованности измеряется единицами–десятками миллисекунд и может доходить до секунд и больше (учебная иллюстрация; зависит от топологии и настроек). Промежуточные модели: causal consistency (комментарий раньше ответа), read-your-writes (пользователь видит своё обновление сразу).

**OLTP vs OLAP** (по `knowledge/databases/oltp-olap.md`): конфликт четырёх измерений — хранение (строки против колонок), схема (3НФ против деденормализованных схем «звезда»/«снежинка»), нагрузка (тысячи коротких против единичных сканирующих), обновления (точечные против пакетных). Поэтому аналитику не ведут по производственной базе: строят выгрузку ETL/ELT в отдельное хранилище (полно — Лекция 8).

**Polyglot Persistence** (по `knowledge/databases/dbms-types.md`, `storage-selection.md`): разные классы СУБД для разных контекстов в одной системе. Ключевой принцип курса: **Source of Truth — один на каждый бизнес-факт; всё остальное — Derived Store (проекция)**, синхронизируемая предсказуемым механизмом (CDC/ETL/события). Правила гигиены:
- derived store никогда не становится «параллельной правдой» (иначе — рассинхрон и аудиторские дыры);
- направление потока явно: SoT → проекции, обратная запись только по явному правилу;
- задержка синхронизации — измеряемая метрика (lag), а не неизвестность.

### Часть 7. Целостность данных и Data Governance (1 мин; развитие — в кейсе)

**Целостность** (по `knowledge/databases/transactions-acid.md`): доменная (типы, CHECK), сущностная (PK/UNIQUE), ссылочная (FK), пользовательская (правила на уровне логики/триггеров). Это продолжение ограничений, спроектированных в Лекции 3, — теперь с требованием «СУБД обязана их исполнять».

**Data Governance** (по `knowledge/databases/data-governance.md`): процессы, политики и роли управления данными — качество, безопасность, соответствие регуляторам, жизненный цикл.

PII — категории: прямые идентификаторы (ФИО, паспорт, ИНН), контакты, биометрия, онлайн-идентификаторы, финансовые и медицинские данные.

Регуляторы (формулировки — по базе знаний `knowledge/databases/data-governance.md`; требуют сверки с актуальной редакцией закона на момент преподавания; курс не является юридической консультацией):
- **GDPR (ЕС, 2018):** права на доступ, исправление, удаление («право на забвение»), переносимость; уведомление об утечках в течение 72 часов; штрафы до 4% мирового оборота или 20 млн евро;
- **152-ФЗ (РФ, 2006):** согласие на обработку, локализация данных граждан РФ на территории РФ, уведомление Роскомнадзора, требования к защите, право отозвать согласие;
- отраслевые: PCI DSS (картежные данные), HIPAA (медданные США), SOC 2.

**Паттерны защиты PII:** маскирование (`+7 (9**) ***-**-45`), токенизация (реквизиты → токен, оригинал в защищённом хранилище), шифрование at rest (TDE и аналоги) и in transit (TLS), и особенно — **crypto-shredding**: PII каждого субъекта шифруется его персональным ключом, ключ живёт в KMS; по запросу на удаление удаляется ключ → данные во всех копиях (таблицы, реплики, бэкапы) становятся нечитаемыми. Это архитектурный ответ на вопрос «как удалить то, что растеклось по десяти системам».

## Case Study (20 мин) — «Каршеринг: каждому контексту — свой дом»

Контекст сквозного кейса (наследует Лекции 1–3): ~200 автомобилей, 3 города, MVP за 3 месяца, команда 8 человек; NFR: p95 поиска свободных авто — порядка сотен миллисекунд [уточнить целевое значение], недопустимость двойного бронирования, сохранность платёжных данных. Логические модели в 3НФ построены на Лекции 3.

### Шаг 1. Постановка задачи выбора (2 мин)

Инструктор напоминает «мостик» Лекции 3: транзакционность бронирования, GPS-телеметрия каждые ~10 секунд на автомобиль (учебная иллюстрация; реальная частота зависит от тарифа телематики и требований к детализации трека), поиск «свободно рядом», отчётность по выручке, поддержка с обращениями. Один движок на всё или разные дома?

### Шаг 2. Заполняем Storage Selection Matrix (6 мин, мини-практика в аудитории)

Для каждого контекста — по восьми осям (сокращённо, на доске/в таблице шаблона):

| Контекст | Нагрузка | R/W | Consistency | Latency | Retention | Compliance | Кандидаты классов (примеры) |
|---|---|---|---|---|---|---|---|
| Бронирование | OLTP | ~50/50 | Strong | ~десятки мс | активные данные | PII (клиент) | реляционные (например, PostgreSQL) |
| Оплата | OLTP + аудит | ~60/40 | Strong | ~десятки–сотни мс | годы (регуляторно) [уточнить срок] | PCI DSS-подобные, PII | реляционные + токенизация реквизитов |
| Телематика (GPS) | streaming/write-heavy | ~1/99 | Eventual допустима для истории | приём — важна доступность записи | горячие недели → холодные месяцы→архив | треки — чувствительные данные | time-series / wide-column (например, TimescaleDB, Cassandra) + object storage для архива |
| Поиск свободных авто рядом | read-heavy | >90/10 | Допустима небольшая lag | p95 ≤ нескольких сотен мс [целевое — требует проверки] | короткий TTL | — | search/geo как **derived store** (например, PostGIS-индекс или внешний поисковый движок) |
| Аналитика выручки | OLAP | read-сканирование | задержка секунды–минуты приемлема | секунды | годы | анонимизация PII | DWH/OLAP через ETL (например, ClickHouse/BigQuery-класс) |
| Поддержка/штрафы | OLTP смешанный | ~70/30 | Strong для статусов, causal для переписки | ~десятки мс | годы (споры) | PII | реляционные (можно в том же кластере, что Бронирование — обсуждение границ Bounded Context) |

Обсуждение trade-off «зоопарк vs консолидация»: для MVP командой в 8 человек лишняя СУБД — это операционный налог (экспертиза, мониторинг, бэкапы). Разумная стартовая позиция: максимум два-три дома (например, реляционное ядро + time-series для телеметрии; поиск — расширение ядра или отдельный движок по мере роста), а не пять с первого дня. **Решение — по TCO и экспертизе, не по красоте диаграммы.**

### Шаг 3. PACELC-анализ выбранного стека (4 мин)

- **Ядро бронирования (реляционное, CP-профиль, PC/EC):** при разделе между площадками — меньшинство отказывает в записи. Цена: часть клиентов не сможет забронировать несколько минут. Обоснование цены: двойное бронирование дороже для репутации и поддержки, чем кратковременный отказ. В штатном режиме: синхронная репликация добавляет латентность (порядок величины — единицы–десятки миллисекунд; учебная иллюстрация, точные значения зависят от окружения и расстояния между ЦОД); альтернатива — асинхронная с риском потери последних транзакций (тема RPO — Лекция 6).
- **Телеметрия (AP/PA-EL):** при разделе каждый узел принимает GPS-пакеты локально и буферизует; после восстановления — сведение (окно расхождения — минуты). В штатном режиме: локальная запись без ожидания кворума — минимальная латентность. Цена: «история движения» временно несогласованна — бизнес это принял, потому что для блокировки автомобиля по факту нарушения используется транзакционное ядро, а не телеметрия.
- **Поиск (derived store):** при разделе отдаёт устаревшую картину «свободно рядом» (минуты). Цена приемлема, потому что финальная проверка доступности выполняется в CP-ядре при подтверждении брони. Фиксируем: «индекс поиска — не источник истины о занятости».

Итог шага — черновик **ADR-008 «Классы СУБД и профили согласованности по контекстам»**: Context (модели Лекции 3 + NFR), Decision (матрица выше), Consequences (цены: недоступность при разделе в ядре, lag в проекциях, операционная стоимость второго движка).

### Шаг 4. Изоляция и двойное бронирование (4 мин)

Разбор с Hook на нашей схеме: транзакция «найти свободное авто на интервал → создать бронь». Варианты предотвращения Lost Update (уровень WHAT):
1. Повышение изоляции до Serializable — гарантирует отсутствие аномалий, но режет конкурентность горячего интервала (час пик);
2. Условное занятие строки/ресурса («перехватить, только если статус ещё свободен») при обычном Read Committed — одна атомарная операция решает задачу, конкурентность сохраняется;
3. Оптимистичная блокировка версией (version/check) — подходит при низкой коллизии.

Выбор для кейса: вариант 2 + мониторинг deadlock-ов с повтором транзакций. Управленческая формулировка: «мы купили безопасность операции за одну атомарную проверку, а не за глобальную сериализацию всей системы».

### Шаг 5. Стратегия Data Governance (4 мин)

Карта PII кейса: клиент (ФИО, телефон, документы) — контексты Бронирование/Поддержка; водитель (ФИО, права) — Штрафы/Оплата; геотреки поездок — Телематика (чувствительные данные: маршруты раскрывают образ жизни [оценка чувствительности — требует проверки юристом]).

Меры по слоям:
- **Минимизация:** PII живёт только там, где необходима; в телеметрии — идентификатор поездки вместо привязки к человеку напрямую;
- **Хранение:** шифрование at rest в ядре; TLS in transit; платёжные реквизиты — токенизация, оригиналы вне основного контура;
- **Проекции:** в поисковый индекс и DWH PII не копируется; в аналитике — маскирование/агрегация;
- **Удаление:** отзыв согласия/право на забвение → crypto-shredding: персональные данные клиента шифруются его ключом, удаление = уничтожение ключа в KMS; действует на реплики и бэкапы (физическое удаление позже или не требуется при нечитаемости);
- **Локализация (152-ФЗ):** инфраструктура с данными россиян — на территории РФ; при выборе managed-облака — проверять региональность дата-центров и договор. Формулировка требует сверки с актуальной редакцией закона на момент преподавания; курс не является юридической консультацией.

### Шаг 6. Разбор типичных ученических решений (3 мин, встроен в обсуждение)

Ниже — четыре варианта, которые реально появляются в студенческих работах. Задача преподавателя — не «зачеркнуть», а вместе с аудиторией найти, на какой оси матрицы решение сломается.

**Вариант А. «Всё в MongoDB: там теперь есть транзакции, и масштабируется лучше».**
Что выглядит правдоподобно: единый движок, гибкая схема, многодокументные транзакции в современных версиях.
Где ломается: ось «consistency + compliance». Условия действия multi-document транзакций зависят от конфигурации кластера и версии; регуляторная строгость схемы (платежи, штрафы) требует исполняемых ограничений, а не соглашения в коде; JOIN по аналитике выручки между коллекциями будет дорогим. Итог: решение допустимо как стартовое для MVP при явном ADR-риске «мы покупаем гарантии у движка, которого не контролируем полностью» — но не как «правильный ответ по умолчанию».

**Вариант Б. «Одна PostgreSQL на всё, включая телеметрию и аналитику, с партиционированием».**
Плюсы честные: один дом, одна экспертиза, ACID везде, знакомые инструменты.
Где ломается: оси «объём и рост» + «cost». Из калькуляции Части 3b видно: ~15 ТБ/год только сырой телеметрии плюс индексная нагрузка; при 200 авто это ещё терпимо, при 2 000 — уже вопрос к модели хранения. Отдельный конфликт: аналитические сканирования поверх OLTP-нагрузки (наш Hook, эпизод 3) — лечится read-репликой под отчёты, то есть архитектурно мы всё равно приходим к разделению, просто позже и дороже. Вывод для аудитории: «консолидация — тоже законное решение, если она записана как решение с планом расщепления по метрикам, а не как случайность».

**Вариант В. «Kafka как основная база: события же сохраняются, можно проиграть историю».**
Где ломается: запрет контракта курса — streaming-лог не заменяет хранилище бизнес-состояния. Практические последствия: ad-hoc запрос «сколько активных броней сейчас» требует агрегации всего журнала; изменение бизнес-правил заставляет перестраивать проекции с нуля; retention-политики журнала противоречат требованиям регулятора к точному удалению PII. Правильная роль Kafka в этом кейсе — транспорт событий между ядром и проекциями, не источник истины.

**Вариант Г. «Сделаем strong consistency везде, чтобы не думать».**
Где ломается: оси «latency» и «cost». Синхронное согласование на глобально распределённой записи добавляет сетевые обходы к каждой операции; для телеметрии это означает потерю приёма при сетевых проблемах — ровно то, чего нельзя допустить. Управленческая формулировка ошибки: «мы купили страховку на предмет, который не является дорогим».

### Управленческие выводы (Product Owner / ИТ-менеджер)

- **Выбор СУБД — бизнес-решение с ценой владения.** Каждая дополнительная СУБД — лицензия/облако, дежурства, бэкапы, обучение: TCO растёт нелинейно. Для MVP оправдан консервативный стек с планом «расщепления» по метрикам роста.
- **Гарантии согласованности можно и нужно продавать клиентам и регулятору.** Формулировка «при сетевом разделе мы сознательно жертвуем доступностью меньшинства» — признак зрелости архитектуры; её отсутствие — источник аварийных «сюрпризов».
- **Штрафы за PII — материализованный риск архитектуры.** Crypto-shredding и минимизация данных дешевле расследования утечки и отзыва пользователей; GDPR-санкции оцениваются в процентах от оборота (точный размер санкций зависит от компании и обстоятельств дела — см. `knowledge/databases/data-governance.md`; курс не является юридической консультацией).
- **Время выхода на рынок.** Managed-сервисы снимают операционную нагрузку (плюс к скорости), но добавляют lock-in и вопросы юрисдикции данных. Self-hosted — контроль и экспертиза in-house. Компромисс фиксируется в ADR.
- **Незаметный SLA-убийца — чужая нагрузка в вашем движке.** Аналитический запрос поверх OLTP превращает SLO в лотерею; разделение OLTP/OLAP — не «архитектурная игрушка», а защита конверсии.

## Связка с управленческими решениями

*(Развёрнутые выводы по кейсу — в конце Case Study; здесь — сводка для плана занятия, блок 4.)*

- **Выбор СУБД = решение о бюджете, а не о технологиях.** Каждая СУБД в стеке — лицензия/облако, бэкапы, дежурства, обучение: TCO растёт нелинейно (детали и расчёт — в «Управленческих выводах» кейса).

- **Managed vs self-hosted** — компромисс скорость/контроль/lock-in; фиксируется в ADR так же, как выбор движка.
- **Разделение OLTP/OLAP защищает SLO:** аналитический запрос поверх операционной базы превращает время ответа в лотерею.

## Anti-pattern

**«Одна модная СУБД для всего» (One-Size-Fits-All Persistence).** Комбинация двух ошибок из Hook: выбор технологии по тренду/резюме вместо критериев задачи и попытка обслуживать одной базой транзакции, телеметрию, поиск и аналитику.

Почему это ошибка: каждая СУБД оптимизирована под свой паттерн доступа; чужая нагрузка неизбежно оплачивается деградацией (аналитика ломает OLTP-latency, high-throughput поток ломает гарантии транзакций или наоборот). Последствия: двойные брони и финансовые расхождения, непредсказуемые SLO, тупики миграций («нам нужно было ACID, а мы уже в ...»), штрафы за PII, раздутый TCO на переделку.

Как распознать: в репозитории решений нет Storage Selection Matrix; фраза «мы используем X, потому что X повсюду»; аналитические отчёты выполняются на реплике продакшена «временно, уже третий квартал».

Лечение: матрица выбора по контекстам; явное разделение Source of Truth и derived stores; ADR с PACELC-формулировкой «что делаем при разделе и чем платим в норме»; пересмотр выбора по метрикам роста, а не по хайпу.

Второй анти-паттерн дня: **«Eventual consistency по умолчанию везде»** — копирование AP-настроек из телеметрии в денежный контур «потому что так быстрее». Согласованность выбирается по бизнес-ценности факта, а не по удобству разработчика.

## Типичные вопросы студентов (FAQ)

**1. «Так какая СУБД лучше — реляционная или NoSQL?»**
Ни одна. Корректный вопрос: «какой класс оптимизирован под паттерн доступа этого контекста». В одном проекте сосуществуют реляционное ядро, time-series для потока и поисковая проекция; если ответ на ваш проект — «одна», проверьте, не является ли он следствием выбора технологии «сверху».

**2. «CAP получается отменяет ACID?»**
Нет, это разные оси. ACID описывает гарантии одной транзакции внутри узла/кластера; CAP — поведение реплицированной системы при сетевом разделе. Реляционная система с синхронной репликацией — CP/PC-EC: у неё есть и ACID, и сознательная жертва доступностью меньшинства.

**3. «Если eventual consistency допустима, зачем вообще платить за strong?»**
Потому что цена ошибки разная. Устаревшая лента поиска — неудобство; двойная бронь одного авто — конфликт, возврат денег, репутация. Правило: strong там, где факт имеет юридическую или финансовую силу; eventual — там, где данные доказательственные или аналитические.

**4. «Можно ли просто всегда ставить Serializable и не думать?»**
Технически можно, экономически — часто нельзя: падает пропускная способность, растут блокировки и ожидания. Кроме того, Serializable не защищает от ошибок проектирования (двойное начисление штрафным сервисом лечится идемпотентностью, а не уровнем изоляции — см. упражнение Части 5c).

**5. «ORM же сам всё делает транзакционным, зачем мне думать об изоляции?»**
ORM управляет запросами, но не семантикой конкурентности. Классическая ловушка — «прочитать объект, изменить в памяти, сохранить»: между чтением и записью строку мог изменить кто-то другой (Lost Update). Поэтому в курсовой работе мы явно указываем стратегию занятия ресурса (условное обновление/версия), даже если код пишет ORM (детали — Лекция 5).

**6. «Разве нельзя держать аналитику на реплике продакшена? Это же бесплатно».**
Read-реплика снимает нагрузку с мастера, но не превращает OLTP-движок в OLAP: сканирующие запросы по строковой 3НФ-модели деградируют, схема меняется под нужды транзакций, а не отчётов. Как временная мера — приемлемо; как план на три года — источник конфликта интересов внутри одной базы (полно — Лекция 8).

**7. «Crypto-shredding удаляет данные? Юрист согласится?»**
Формально данные перестают быть персональными, когда они нечитаемы без уничтоженного ключа. Это распространённая архитектурная практика ответа на право на удаление, но юридическая достаточность зависит от юрисдикции и регулятора — обязательна сверка с юристом/DPO (курс не даёт юридических консультаций).

**8. «А векторная БД нам нужна? Все сейчас про AI пишут».**
Только если есть задача семантического поиска (обращения в поддержку, подбор похожих инцидентов). Для каршеринга MVP такая задача отсутствует — и добавление векторного движка было бы Resume-Driven Development в чистом виде. Отказ от технологии по причине «нет задачи» — такое же обоснованное решение, как выбор.

## Практическое задание (аудиторная мини-версия, 10–15 мин)

## Вопросы преподавателя к студенту на защите — с эталонными ответами

**В1. «Почему Бронирование живёт в реляционном ядре, а Телеметрия — нет?»**
Ожидаемый ответ: потому что операция бронирования требует атомарного занятия уникального ресурса (гарантия на уровне движка + условное обновление), а телеметрия — write-heavy поток, где критичен приём и допустима реконструкция истории; в терминах PACELC — PC/EC против PA/EL. Плюс разные профили хранения: точечные транзакционные чтения против диапазона по времени.

**В2. «Что произойдёт, если канал CDC между ядром и поисковым индексом упадёт на час?»**
Ожидаемый ответ: индекс начнёт отдавать устаревшую картину; пользователи увидят «свободно» там, где уже занято; финальная проверка в ядре защитит корректность брони; UX обязан обработывать отказ при подтверждении; лаг должен быть метрикой с алертом; при длительном простое — стратегия (показать «статус может быть неполным» / ограничить выдачу). Плохой ответ: «ничего страшного, у нас eventual consistency».

**В3. «Докажите, что ваша система не потеряет платёж при сбое.»**
Ожидаемый ответ уровня лекции: Durability через WAL и fsync, далее — репликация и бэкапы; количественно обязательство формулируется как RPO/RTO (детальный разбор — Лекция 6). Студент должен назвать механизм, а не полагаться на «там надёжно».

**В4. «Куда вы денете PII клиента, который отозвал согласие, и почему один DELETE не спасает?»**
Ожидаемый ответ: PII растеклись по ядру, репликам, бэкапам, поисковому индексу, DWH и объектному архиву; физическое вычищение всех копий хрупко; crypto-shredding (персональный ключ в KMS → удаление ключа) делает копии нечитаемыми; плюс минимизация данных и маскирование в производных копиях.

**В5. «Почему вы выбрали managed-сервис, а не self-hosted? Что вы приобрели и что потеряли?»**
Ожидаемый ответ: приобрели скорость и сняли операционную нагрузку (экспертиза, дежурства, патчинг); потеряли часть контроля, добавили lock-in и обязаны проверить региональность дата-центров (152-ФЗ) и условия обработки данных. Решение должно быть в ADR с Consequences, а не «так удобнее».

## Anti-pattern

Для контекста «Штрафы» кейса «Каршеринг» (вход — логическая модель Лекции 3):
1. Заполните 8 осей Storage Selection Matrix для этого контекста (часть значений — оценочные, помечайте «[требует уточнения]»).
2. Выберите класс СУБД (не конкретный продукт — класс!) и обоснуйте через read/write ratio, consistency и compliance.
3. Опишите поведение выбранного дома по PACELC: что при partition, чем платим в штатном режиме.
4. Найдите в контексте PII-элементы и предложите одну меру защиты на хранение и одну — на удаление (crypto-shredding/токенизация/маскирование).

Расширенная домашняя версия (15–20 мин, полный формат — в `practice.md`): то же для контекста «Телематика» + черновик ADR-008 по стеку + мини-план миграции данных из «единой базы» в полиглотный стек (Expand and Contract из Лекции 3 как инструмент).

**Результат:** заполненная матрица + ADR-фрагмент + стратегия PII — артефакты входят в итоговый Architecture Blueprint (см. module-map, Лекция 4).

## Мостик к следующей лекции

Мы выбрали классы СУБД и зафиксировали гарантии. Но приложение «разговаривает» с выбранным хранилищем ежедневно — и на этом канале живут свои архитектурные решения и уязвимости:
- пулы соединений: почему «открывать соединение на каждый запрос» убивает latency и исчерпывает лимиты СУБД;
- Raw SQL vs ORM: импеданс-мисматч, соблазн удобства и проблема N+1 (почему ORM иногда делает 1+N запросов там, где нужен один JOIN);
- безопасность: SQL-инъекции и подготовленные выражения, хранение секретов подключения (Vault) — связь с нашей PII-стратегией;
- инструменты: DBeaver/DataGrip — навигация по схеме, ER-диаграммы из метаданных.

**Лекция 5** («Взаимодействие приложений с СУБД, уязвимости и инструменты разработчика») реализует подключение к СУБД, выбранной и проанализированной сегодня: схема взаимодействия приложения с БД, параметры подключения и обоснование способа доступа (ORM vs Raw SQL) — снова через trade-offs и ADR.
