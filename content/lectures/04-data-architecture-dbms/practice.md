# Практика к Лекции 4. История, эволюция и виды СУБД. Транзакции, PACELC и Data Governance

> Тема и требования — по `specs/syllabus.md` и `specs/lessons/lesson-04.spec.md`. Формат — по `templates/practice.md` и `specs/content-contracts/practice-contract.md`. Технологии в подсказках — примеры классов решений, а не стандарты.

## Цель практики

Отработать навык **обоснованного выбора хранилища под контекст**: заполнить Storage Selection Matrix для двух контекстов сквозного кейса, проанализировать выбор через CAP/PACELC и уровни изоляции транзакций, спроектировать фрагмент стратегии Data Governance (PII) и оформить результат как ADR. Создаваемый артефакт: **«Storage & Consistency Decision Record» (ADR-008)** + заполненная матрица + карта PII.

## Кейс

**Компания:** сервис каршеринга «Каршеринг» (сквозной проект курса; наследует контекст Лекций 1–3): ~200 автомобилей, 3 города, MVP за 3 месяца, команда разработки 8 человек.

**Текущая ситуация:** на Лекции 3 построены логические модели в 3НФ (Клиент, Автомобиль, Бронирование, Поездка, Оплата, Штраф, Телеметрия). Архитектурный спор не закрыт: часть команды настаивает на «одной современной документной СУБД для всего» («NoSQL масштабируется»), часть — на реляционном ядре. Дополнительный давление-фактор: история из Hook лекции (двойное бронирование, расхождение отчётов, деградация OLTP под аналитикой) рассматривается как реальный риск нашего MVP.

**Проблема:** решение «на глазке» не задокументировано; гарантии согласованности, поведение при сетевом разделе и обращение с PII (клиенты РФ — 152-ФЗ; клиенты ЕС — GDPR) нигде не зафиксированы. Без артефактов выбора команда не сможет ни защитить решение перед стейкхолдерами, ни пройти аудит.

## Входные данные

- Логическая модель 3НФ контекстов «Телематика» и «Штрафы» — итог `content/lectures/03-data-modeling-normalization/practice.md`;
- Карточка NFR и бизнес-ограничения (Лекция 2): p95 поиска — порядка сотен миллисекунд [целевое значение уточняется], недопустимость двойного бронирования, сохранность платёжных данных, бюджет облака MVP [сумма — требуется проверка], срок MVP 3 мес., команда 8 чел.;
- Таблица классов СУБД и trade-offs (draft Лекции 4, Часть 2);
- Восемь осей Storage Selection Matrix (draft, Часть 3);
- Шаблоны ниже в этом файле.

## Задание

Выполняется индивидуально или в парах; два контекста — «Телематика (GPS-поток)» и «Штрафы и претензии».

1. **Анализ текущего состояния.** Для каждого контекста выпишите из входных данных: тип нагрузки, ожидаемый объём и рост (каждую оценку помечайте как оценочную), read/write ratio, требования к latency и consistency, retention, применимые регуляторы (GDPR/152-ФЗ/отраслевые).
2. **Выявление проблемных зон.** Найдите в гипотезе «одна документная СУБД для всего» три конкретные точки отказа: одну через PACELC (поведение при partition), одну через аномалии конкурентного доступа (для операции «выписать штраф за завершённую поездку» или «принять пакет телеметрии и обновить состояние авто»), одну через Data Governance (право на удаление/geotracking-чувствительность).
3. **Проектирование решения.** Заполните Storage Selection Matrix (8 осей × 2 контекста). Выберите **класс** СУБД для каждого контекста (не продукт!) и альтернативу; обоснуйте выбор через trade-offs и контекст (NFR, бюджет, экспертиза команды, масштаб). Опишите механизм синхронизации derived-проекций (Source of Truth → проекции, lag-метрики).
4. **Гарантии и изоляция.** Для транзакционного контекста «Штрафы»: выберите уровень изоляции и способ предотвращения Lost Update (три варианта из Части 5 draft) с формулировкой «что покупаем, чем платим». Для «Телематики»: зафиксируйте PACELC-пару («при разделе — X; в норме платим Y»).
5. **Стратегия PII.** Постройте карту PII обоих контекстов (элемент → классификация → где живёт → куда проецируется) и предложите меры: минимум по одной на хранение (шифрование at rest/TLS/токенизация/маскирование) и на удаление (crypto-shredding с KMS-ключом субъекта; опишите, что происходит с бэкапами и репликами).
6. **Оформление артефакта.** Соберите ADR-008 по шаблону `templates/adr.md` (Context / Decision / Consequences + альтернативы с причинами отказа).

**Ожидаемый результат:** файл-пакет «ADR-008 + Storage Selection Matrix + Карта PII» — готовый фрагмент итогового Architecture Blueprint (module-map, Лекция 4).

## Критерии оценки

| Критерий | Вес | Описание |
|----------|-----|----------|
| Полнота анализа | 20% | Все 8 осей матрицы заполнены для обоих контекстов; оценки помечены как оценочные; связи с NFR из Л2 явны |
| Обоснованность решений | 30% | Выбор класса через trade-offs и контекст; PACELC-пара сформулирована для каждого дома; есть rejected alternatives с аргументами |
| Соответствие ограничениям | 20% | Учтены бюджет MVP, размер команды (операционный налог каждой СУБД), retention/compliance; нет «зоопарка ради зоопарка» |
| Качество артефакта | 20% | ADR-008 читаем, структура полна; матрица и карта PII аккуратны; термины согласованы с глоссарием |
| Связь с бизнес-целями | 10% | Явно указано, какие бизнес-риски снижает решение (двойное бронирование, штрафы регулятора, SLO поиска) |

## Подсказки

- 💡 Начинайте с вопроса «какой паттерн доступа?», а не «какая СУБД?». Телеметрия — write-heavy поток с редким чтением истории; штрафы — транзакционный OLTP со смешанным доступом и юридической значимостью записей.
- 💡 Типовой паттерн для write-heavy телеметрии — time-series/wide-column-класс с разделением горячих и холодных данных (hot/cold) и выгрузкой архива в объектное хранилище; но проверяйте по осям 5–8: если команда не готова эксплуатировать второй движок — честнее временно жить в расширении ядра (например, таблица с партиционированием) с планом «расщепления» по метрикам роста.
- 💡 Для защиты от Lost Update сравните три цены: Serializable (безопасно, режет конкурентность), условное обновление одной строки («занять/записать, только если ещё актуально») при Read Committed, оптимистичная блокировка версией. См. `knowledge/databases/transactions-acid.md`, `cap-pacelc.md`, `storage-selection.md`, `data-governance.md`.
- 💡 Crypto-shredding проверяйте вопросом: «удалён ключ — стали ли нечитаемыми ВСЕ копии: таблицы, реплики, поисковые индексы, бэкапы, DWH?» Если какая-то копия хранит PII открытым текстом — это дыра стратегии, а не деталь.

## Типичные ошибки

- ❌ Выбор конкретного продукта («берём MongoDB, потому что…») до заполнения матрицы — сначала класс и паттерн доступа, продукт — иллюстрация.
- ❌ «Eventual consistency везде, потому что быстрее» — перенос AP-настроек телеметрии в денежный/юридический контур без оценки цены.
- ❌ Игнорирование операционного налога: пятая СУБД в команде из 8 человек без DBA — скрытый срыв сроков MVP.
- ❌ Derived store без указания источника истины и механизма синхронизации — будущий «параллельный правдой» склад.
- ❌ Карта PII без связки «элемент → все места копирования» — тогда право на удаление неисполнимо, и стратегия фиктивна.
- ❌ ADR без секции Consequences: решение без перечисления цен невозможно оспорить и пересмотреть при росте.
