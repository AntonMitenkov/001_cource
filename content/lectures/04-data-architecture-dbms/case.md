# Кейс: Каршеринг — «Каждому контексту свой дом» (Лекция 4)

> Формат — по `templates/case.md`. Кейс развивает сквозной проект курса (Лекции 1–3); в лекционной части он встроен в `draft.md` (раздел Case Study, 20 мин), здесь дан в развёрнутом виде для семинара/домашней работы. Все количественные оценки помечены; технологии — примеры классов решений, не стандарты.

## Контекст

Сервис каршеринга: ~200 автомобилей, 3 города, MVP за 3 месяца, команда разработки 8 человек (без выделенного DBA). На Лекции 3 спроектированы логические модели в 3НФ: Клиент, Автомобиль, Бронирование, Поездка, Оплата, Штраф, Телеметрия. На архитектурном комитете открыт вопрос: **в какой СУБД каждая модель будет жить**. Часть команды предлагает «одну современную документную СУБД для всего — NoSQL масштабируется»; история из Hook лекции (двойное бронирование одного авто, расхождение отчёта о выручке с банковской выпиской, деградация OLTP-latency под аналитическим запросом) воспринимается как реальный прогноз, а не страшилка.

## Бизнес-цель

Зафиксировать к концу спринта проектирования обоснованный выбор классов хранилищ по контекстам так, чтобы:
- исключить двойные бронирования (операционная гарантия на уровне транзакции);
- обеспечить p95 поиска свободных автомобилей порядка сотен миллисекунд [целевое значение — уточняется владельцем продукта];
- сохранить исполнимые обязательства по PII (GDPR / 152-ФЗ) при росте числа копий данных;
- уложиться в бюджет и экспертизу команды MVP: операционный налог каждой дополнительной СУБД контролируем [бюджет облака — требуется проверка].

## Участники

- **Заказчик:** владелец продукта каршеринга — интересы: скорость выхода на рынок, отсутствие публичных инцидентов двойных броней, прохождение аудита данных.
- **Пользователи:** клиенты (бронирование, поиск «свободно рядом»), операционисты поддержки (штрафы, споры), аналитики (выручка, утилизация парка).
- **Команда разработки:** 8 человек, бэкенд + фронтенд + один «случайный» энтузиаст баз данных; DBA нет; готовность дежурить по новым движкам ограничена.
- **Стейкхолдеры:** юрист/DPO (согласия, локализация данных граждан РФ), финансовый контролёр (расходимость отчётности), инфраструктурный вендор (региональность дата-центров).

## Текущая проблема

Единая СУБД «на всё» создаёт четыре конфликта:
1. **Транзакционный:** операция «проверить свободно → занять → создать бронь» без полных ACID-гарантий порождает Lost Update (см. Диаграмму 7 в `diagrams.md`).
2. **Нагрузочный:** GPS-телеметрия (~событие каждые ~10 секунд на автомобиль — оценка [требуется проверка]) — write-heavy поток; аналитика — сканирующие чтения; оба ложатся поверх OLTP и ломают SLO.
3. **Согласованностный:** отчётность по репликам с eventual consistency расходится с банковскими выписками; бизнес не определил, где допустимо окно несогласованности, а где нет.
4. **Регуляторный:** PII (клиенты, водители) и геотреки копируются в проекции «как есть»; право на удаление физически неисполнимо без стратегии (crypto-shredding, минимизация).

## Ограничения

- **Бюджет:** облако MVP; каждая дополнительная СУБД — лицензии/подписка + эксплуатация + обучение [точные суммы — требуется проверка]; приоритет managed-сервисов над self-hosted обсуждается (lock-in vs контроль).
- **Время:** MVP 3 месяца; миграции без простоя — инструмент Expand and Contract (Лекция 3).
- **Технологии:** запретов нет; требование курса — решения через Storage Selection Matrix и ADR, а не через моду; streaming/очереди не используются как хранилище бизнес-состояния.
- **Комплаенс:** данные граждан РФ — 152-ФЗ (согласие, локализация, Роскомнадзор) [актуальные редакции — требуется проверка]; клиенты ЕС — GDPR (права субъекта, уведомление об утечках за 72 часа, штрафы до 4% оборота / 20 млн евро — сверить); платёжный контур — PCI DSS-подобные требования (токенизация реквизитов).

## Архитектурный вопрос

**Как распределить контексты каршеринга по классам хранилищ так, чтобы каждый бизнес-факт имел ровно один Source of Truth, профили согласованности (CAP/PACELC) были явно заданы по цене риска, а стратегия удаления PII оставалась исполнимой во всех копиях — при бюджете и экспертизе команды из 8 человек?**

## Ожидаемое решение

Ожидается не «правильный список СУБД», а оформленное решение уровня WHAT/WHY:
- заполненная Storage Selection Matrix (8 осей) по контекстам: Бронирование/Оплата/Штрафы (транзакционное реляционное ядро), Телематика (time-series/wide-column-класс + архив в объектное хранилище), Поиск и Аналитика — как **derived stores** (geo-индекс/поисковый движок; DWH через ETL), с явным lag-бюджетом каждого;
- PACELC-формулировки: «при разделе ядро жертвует доступностью меньшинства; телеметрия пишет локально; поиск отдаёт устаревшую картину, финальная проверка занятости — в ядре»;
- защита операции бронирования от Lost Update (условное занятие ресурса при Read Committed либо оптимистичная блокировка версией; Serializable — как отвергнутая альтернатива с обоснованием цены);
- консервативный старт MVP (2–3 дома вместо пяти) с планом «расщепления» по метрикам роста;
- карта PII + меры по слоям (минимизация, шифрование at rest/TLS, токенизация платежей, маскирование в проекциях) и crypto-shredding через KMS;
- всё упаковано в ADR-008 с Consequences и rejected alternatives.

## Вопросы для обсуждения в аудитории

1. Где проходит граница «strong consistency обязана» vs «eventual приемлема»? Назовите бизнес-факт кейса с каждой стороны и объясните цену ошибки.
2. Команда отказалась от второй СУБД ради скорости MVP. Какие метрики роста заставят пересмотреть решение, и что произойдёт с планом миграции, если тянуть с ней?
3. Поисковый индекс показывает автомобиль свободным, а ядро — занятым. Кто прав и как это должно быть сформулировано в UX и в ADR?
4. Субъект отозвал согласие. Перечислите все носители, куда успели попасть его PII, и проверьте: ваш план удаления покрывает каждый?
5. Managed-облако против self-hosted для ядра: чем именно мы платим в каждом варианте (lock-in, юрисдикция данных, время выхода, дежурства)?
