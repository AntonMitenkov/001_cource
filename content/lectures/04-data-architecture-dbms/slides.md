## Слайд 5. Hook: три провала одной базы на всё

- Документная СУБД выбрана «потому что NoSQL масштабируется»
- Провал 1: двойное бронирование одного авто — Lost Update без транзакционных гарантий
- Провал 2: отчёт выручки не сходится с выпиской — eventual consistency в финансовом контуре
- Провал 3: аналитика поверх OLTP — пользовательская latency деградирует в разы
- Вопрос: можно ли было предсказать это ДО кода? (Да — требованиями и матрицей критериев)

## Слайд 6. Эволюция СУБД: каждая волна — ответ на проблему (Д1)

- 1950–60-е: файлы → дублирование, нет целостности
- 1970+: реляционная модель (Кодд) → декларативность, строгость, SQL
- 1990–2000-е: открытые RDBMS → доступность, но вертикальный потолок
- 2008+: NoSQL → горизонтальный масштаб и специализация ценой гарантий
- 2020-е: векторные/AI-native → семантика и RAG
- Вывод: вопроса «какая СУБД лучшая?» не существует — есть вопрос «какая проблема у нас?»

## Слайд 7. Классы СУБД: карта trade-offs (Д2)

- Реляционные: полные ACID, JOIN; масштаб вертикальный
- Key-value: сверхбыстро по ключу; без сложных запросов
- Документные: гибкая схема; транзакции — по конфигурации
- Wide-column / time-series / search / vector / object / DWH / streaming — каждый под свой паттерн доступа
- Ослабленная гарантия — не дефект, а плата за другое свойство
- [Д2] Сводная таблица: модель данных × транзакции × масштаб × «когда НЕ использовать»

## Слайд 8. Storage Selection Matrix: 8 осей (Д3)

- Тип нагрузки: OLTP / OLAP / streaming / specialized
- Объём и рост; Read/Write ratio; Latency (p95/p99)
- Consistency: strong / causal / eventual
- Retention; Compliance (GDPR, 152-ФЗ, PCI DSS); Cost & экспертиза команды
- Red flag: выбор без матрицы = Resume-Driven Development
- [Д3] Дерево принятия решения по осям

## Слайд 9. CAP: при разделе выбираешь C или A

- C — согласованность, A — доступность, P — толерантность к разделу
- Сети ненадёжны: P — не опция, а факт жизни геораспределённой системы
- CP: меньшинство отказывает в обслуживании (ZooKeeper-класс, etcd-класс)
- AP: пишем обеим сторонам, конфликты разрешаем позже (Cassandra/DynamoDB-класс)
- «CA» = одиночный узел: иллюзия рассыпается при первом сетевом сбое

## Слайд 10. PACELC: латентность — ежедневная реальность (Д4)

- Partition: A или C; Else (в норме): L или C
- PA/EL — быстрая несогласованность; PC/EC — согласованность всегда
- Классификации продуктов зависят от версий и настроек (оговорка обязательна)
- Правило проверки вендора: два вопроса — «что при partition?» и «чем платите в норме?»
- Ответ архитектора фиксируется в ADR парой «при разделе — X; в норме платим Y»

## Слайд 11. Транзакции и ACID (Д7)

- Транзакция: всё или ничего (COMMIT / ROLLBACK)
- A — атомарность; C — корректность состояний (Constraints из Л3); I — изоляция (locks/MVCC); D — долговечность (WAL)
- Аномалии: Dirty Read, Non-repeatable Read, Phantom Read, Lost Update, Deadlock
- Lost Update — герой нашего Hook: прочитали «свободен» — оба записали «занят»

## Слайд 12. Уровни изоляции — страховка с ценой (Д5)

- Read Uncommitted → Read Committed → Repeatable Read → Serializable
- Чем выше изоляция — тем меньше аномалий и ниже конкурентность
- Реализации СУБД различаются (оговорка по версиям — fact-check)
- Для горячего инвентаря часто достаточно RC + условное занятие («взять, если ещё свободно»)
- Выбор уровня — архитектурное решение, живёт в ADR вместе с тестом на Lost Update

## Слайд 13. BASE, OLTP vs OLAP

- BASE: Basic Availability, Soft State, Eventual Consistency — не «плохой ACID», другая точка компромисса
- Окно расхождения — измеряемая величина, а не слепая зона
- OLTP: тысячи коротких точечных операций; OLAP: редкие сканирующие агрегации
- Конфликт хранения/схемы/нагрузки/обновлений → аналитику не ведут по производственной базе
- ETL/ELT в отдельное хранилище (подробно — Лекция 8)

## Слайд 14. Polyglot Persistence: Source of Truth vs Derived Store (Д6)

- Разным контекстам — разные дома; но у каждого бизнес-факта — ОДИН источник истины
- Всё остальное — проекции (search, DWH, кэш), синхронизируемые явным механизмом (CDC/ETL/события)
- Hygiene: проекция не становится «параллельной правдой»; lag — метрика
- Streaming/очереди передают события, но НЕ заменяют хранилище состояния
- [Д6] Схема стека каршеринга: SoT → CDC → derived stores

## Слайд 15. Data Governance: PII и регуляторы

- Целостность: доменная, сущностная, ссылочная, пользовательская (продолжение Л3)
- PII: идентификаторы, контакты, биометрия, финансы, геотреки (чувствительность — оценка юриста)
- GDPR: права субъекта, 72 часа на уведомление, штрафы до 4% оборота / 20 млн евро
- 152-ФЗ: согласие, локализация в РФ, Роскомнадзор, право отзыва
- Меры: минимизация, маскирование, токенизация, шифрование at rest/in transit

## Слайд 16. Crypto-shredding: как удалить то, что растеклось (Д8)

- Проблема: PII в таблицах, репликах, бэкапах, проекциях — физическое удаление везде недостижимо
- Решение: данные каждого субъекта шифруются его персональным ключом (KMS)
- Запрос на удаление = уничтожение ключа → копии становятся нечитаемыми
- Это архитектурное требование, а не «галочка юристов»: проектируется с первого ADR

## Слайд 17. Кейс: контексты каршеринга (Д6)

- Бронирование → реляционное ядро (strong, ACID)
- Оплата → реляционное + токенизация реквизитов (PCI DSS-подобные требования)
- Телематика → time-series/wide-column (write-heavy, AP-профиль) + объектное хранилище архива
- Поиск рядом → derived store (geo/search), финальная проверка — в ядре
- Аналитика → DWH через ETL; Поддержка/Штрафы → реляционные в границах своего контекста

## Слайд 18. Кейс: цена решений по PACELC

- Ядро (PC/EC): при разделе меньшинство не бронирует — несколько минут недоступности
- Цена оправдана: двойное бронирование дороже кратковременного отказа
- Телеметрия (PA/EL): пишет локально, сходится после восстановления (окно — минуты)
- Поиск: отдаёт устаревшую картину — безопасно, т.к. занятость подтверждает CP-ядро
- Итог: черновик ADR-008 «Классы СУБД и профили согласованности по контекстам»

## Слайд 19. Кейс: зоопарк против консолидации

- Команда 8 человек, MVP 3 месяца: каждая лишняя СУБД — операционный налог
- Стартовая позиция: 2–3 дома (реляционное ядро + time-series), не пять с первого дня
- Расширение — по метрикам роста, с планом миграции (Expand and Contract из Л3)
- Критерий — TCO и экспертиза, а не красота диаграммы

## Слайд 20. Управленческие выводы

- Выбор СУБД — бизнес-решение: TCO растёт нелинейно с числом движков
- Гарантии согласованности продаются клиентам и регулятору — формулируйте явно
- Штрафы за PII — материализованный риск архитектуры; минимизация данных дешевле расследования
- Managed vs self-hosted: скорость против контроля и lock-in — фиксировать в ADR
- Чужая нагрузка в вашем движке — незаметный убийца SLA

## Слайд 21. Анти-паттерны лекции

- «Одна модная СУБД для всего» (One-Size-Fits-All Persistence): мода вместо критериев
- Признаки: нет матрицы в ADR-репозитории; «X, потому что X повсюду»; аналитика на проде «временно»
- «Eventual consistency по умолчанию везде»: AP-настройки переезжают в денежный контур
- Лечение: матрица по контекстам; SoT/проекции; PACELC-формулировка в каждом ADR

## Слайд 24. Резюме

- Каждая СУБД — ответ на историческую проблему; выбираем под паттерн доступа
- 8 осей матрицы превращают спор мнений в проверяемое решение
- При разделе платим C или A; в норме платим L или C — и записываем цену в ADR
