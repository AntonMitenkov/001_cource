# План Лекции 4

## Тема
История, эволюция и виды СУБД. Транзакции, PACELC и Data Governance

## Цель
Научить студентов выбирать класс СУБД под задачу и паттерн доступа: читать ландшафт СУБД через призму их истории, анализировать распределённые базы через CAP/PACELC, объяснять ACID, уровни изоляции и аномалии конкурентного доступа, разделять OLTP/OLAP, строить полиглотный стек с явным Source of Truth и проектировать базовую стратегию Data Governance (PII, GDPR/152-ФЗ, crypto-shredding).

## Learning Objectives
По окончании лекции студенты смогут:
1. **Различать** основные классы СУБД (relational, key-value, document, wide-column, graph, time-series, search, vector, object storage, warehouse/lakehouse, event streaming) и связывать каждый класс с задачей, которую исторически он решал.
2. **Применять** Storage Selection Matrix: обосновывать выбор класса СУБД по критериям NFR (нагрузка, объём, consistency, latency, retention, cost, compliance, экспертиза команды).
3. **Анализировать** поведение распределённой БД через CAP и PACELC: предсказывать, что произойдёт при сетевом разбиении и в штатном режиме, и переводить это в требования SLO.
4. **Объяснять** свойства ACID, Commit/Rollback, уровни изоляции SQL и аномалии конкурентного доступа (Dirty Read, Non-repeatable Read, Phantom Read, Lost Update, Deadlock); выбирать уровень изоляции под бизнес-операцию.
5. **Оценивать** компромиссы Polyglot Persistence: разделять Source of Truth и Derived Store, отличать OLTP-нагрузку от OLAP; не подменять хранилище состояния очередями/streaming-логами.
6. **Создавать** фрагмент стратегии Data Governance: классификация PII, меры защиты (маскирование, токенизация, шифрование), исполнение права на удаление (GDPR/152-ФЗ, crypto-shredding).

*(Формулировки соответствуют acceptance criteria `specs/lessons/lesson-04.spec.md` и блоку 4 `specs/learning-outcomes.md`.)*

## Последовательность блоков

### 1. Hook (5 мин)
- История-предупреждение (обобщённая, композитная, без имени компании): команда выбрала документную СУБД «потому что NoSQL масштабируется лучше», перевела туда бронирования и платежи → двойное бронирование одного авто (lost update), расхождение отчёта о выручке с платёжной выпиской; параллельно аналитический запрос лёг поверх OLTP-транзакций и «положил» пользовательский опыт.
- Разбираем три ошибки заранее: (1) выбор без критериев; (2) одна БД для всех нагрузок; (3) игнорирование гарантий согласованности.
- Провокационные вопросы: «Можно ли было предсказать провал до написания кода? Что бы показал PACELC при обрыве меж ДЦ?»
- Связь с Лекцией 3: у нас есть логические модели в 3НФ по пяти контекстам — сегодня каждый контекст получает «дом хранения».

### 2. Теоретический блок (30 мин)

**Часть 2.1. Эволюция СУБД: почему «зоопарк» вообще существует (5 мин)**
- Файловые системы → иерархические (IBM IMS, 1968) → сетевые (CODASYL) → реляционная модель (Кодд, 1970) → коммерческие RDBMS (Oracle, DB2, SQL Server) → открытые (MySQL, PostgreSQL, SQLite) → облачные (RDS, Aurora) → NoSQL (MongoDB, Redis, Cassandra) → векторные и AI-native (Pinecone, Qdrant, pgvector).
- Каждая волна отвечала на конкретную проблему: связи M:N и навигация → декларативность и целостность → доступность/стоимость → горизонтальный масштаб и гибкая схема → семантический поиск.
- Вывод-мостик: «СУБД — ответ на проблему, а не на моду». Таблица-таймлайн как визуальный якорь.

**Часть 2.2. Классы СУБД и их trade-offs (8 мин)**
- Обзор 11 классов (spec): relational, key-value, document, wide-column, graph, time-series, search engine, vector DB, object storage, data warehouse/lakehouse, event streaming platform.
- Для каждого: модель данных, транзакционные гарантии, тип масштабирования, «когда использовать / когда не использовать», примеры технологий (как примеры, не стандарты).
- Сводная сравнительная таблица; red flags из knowledge/storage-selection.md («OLTP для аналитики», «файлы в реляционной БД», «одна БД для всего»).
- Отдельное предупреждение контракта курса: event streaming платформа — журнал событий, а не замена БД состояния.

**Часть 2.3. Критерии выбора: Storage Selection Matrix (4 мин)**
- Восемь осей: тип нагрузки (OLTP/OLAP/streaming), объём и прогноз роста, read/write ratio, latency (p95/p99), consistency (strong/causal/eventual), retention, compliance, стоимость и экспертиза команды.
- Дерево решений (шаги 1–6 из knowledge/storage-selection.md); шаблон таблицы для практики.

**Часть 2.4. Распределённые системы: CAP и PACELC (5 мин)**
- CAP (Brewer 2000; доказательство Gilbert & Lynch 2002): C/A/P; при partition выбор CP vs AP; CA — иллюзия для распределённой системы (single-node RDBMS вне кластера).
- Критика CAP: partition редок, а латентность — каждый день → PACELC (Abadi 2010): P→A/C, Else→L/C.
- Таблица классификации примеров систем (PA/EL, PC/EC и т.д.) — с оговоркой: поведение зависит от конфигурации [требуется проверка конкретных версий при ревью].
- Как применять: формулировать в ADR, что система делает при разделе и чем платит в норме.

**Часть 2.5. Транзакции: ACID, изоляция, конкурентный доступ (5 мин)**
- Транзакция, COMMIT/ROLLBACK, состояния; A/C/I/D и механизмы (constraints, блокировки/MVCC, WAL).
- Аномалии: Dirty Read, Non-repeatable Read, Phantom Read, Lost Update, Deadlock (+S/X-блокировки).
- Таблица уровней изоляции SQL × аномалии; defaults популярных СУБД (PostgreSQL — Read Committed, MySQL/InnoDB — Repeatable Read) [по состоянию знаний базы курса; проверять по документации версий]; компромисс «изоляция ↔ конкурентность».
- Пример уровня WHAT: бронирование автомобиля — операция, где Lost Update недопустим; как его предотвращают на уровне логики (условное обновление/блокировка строки — концептуально, без кода).

**Часть 2.6. BASE, OLTP vs OLAP, Polyglot Persistence (2 мин)**
- BASE: Basic Availability, Soft State, Eventual Consistency; промежуточные модели (causal, read-your-writes).
- OLTP vs OLAP: конфликт требований (строковое vs колоночное хранение, нормализация vs денормализация, точечные vs сканирующие запросы) → разделение через ETL/ELT (детально — Лекция 8).
- Polyglot Persistence + принцип «Source of Truth один на факт; derived store — проекция» (схема: SoT → CDC/ETL → поиск/кэш/DWH).

**Часть 2.7. Целостность данных и Data Governance (1 мин + развитие в кейсе) (1 мин)**
- Виды целостности (доменная, сущностная, ссылочная, пользовательская) — связь с constraints Лекции 3.
- PII и регуляторы: GDPR (право на удаление, штрафы до 4% оборота или 20 млн евро — по тексту регламента), 152-ФЗ (согласие, локализация, Роскомнадзор) [формулировки — по базе знаний; актуальную редакцию проверять].
- Паттерны: маскирование, токенизация, шифрование at rest/in transit, crypto-shredding (удаление ключа в KMS).

### 3. Case Study (20 мин) — сквозной кейс «Каршеринг»
**Шаг 1 (3 мин).** Вход: пять контекстов и 3НФ-модели Лекции 3 + NFR из Лекции 1 (доступность, latency p95, бюджет MVP 3 мес., команда 8 чел.).
**Шаг 2 (6 мин).** Заполняем Storage Selection Matrix по контекстам:
- Бронирование (OLTP, strong consistency, нельзя забронировать авто дважды) → реляционный класс (пример: PostgreSQL);
- Оплата (OLTP + PCI DSS-подобные требования, аудит) → реляционный + токенизация платежных реквизитов;
- Телематика (write-heavy GPS-поток, eventual допустима для истории, time-window агрегаты) → time-series/wide-column класс (примеры: TimescaleDB, InfluxDB, Cassandra — как варианты);
- Поиск свободных машин рядом → search/geo-индекс как derived store поверх SoT (примеры: Elasticsearch, PostGIS);
- Аналитика выручки → OLAP/DWH через ETL (детально — Лекция 8).
**Шаг 3 (4 мин).** PACELC-анализ выбранного стека: что делает ядро бронирования при разделе сети между ЦОД (CP: отказ записи меньшинству — цена: недоступность части пользователей); что делает телеметрия (AP/PA-EL: принимаем данные локально, сведём позже). Фиксируем в черновике ADR-008 «Классы СУБД по контекстам».
**Шаг 4 (4 мин).** Изоляция и конкурентный доступ на примере двойного бронирования: какой уровень и какая логика обновления предотвращают Lost Update; почему Serializable «безопасно, но дорого» для горячего инвентаря; где нужен deadlock-менеджмент.
**Шаг 5 (3 мин).** Стратегия PII: карта данных (где живут ФИО/телефон/паспорт/треки), минимизация (PII — только в контексте Клиента), шифрование at rest, маскирование в логах и аналитике, право на удаление → crypto-shredding (персональный ключ в KMS; удаление ключа вместо «вычёркивания» из бэкапов). Проверка 152-ФЗ: локализация данных граждан РФ [требует проверки актуальной редакции и трактовки].
**Управленческие выводы (встроены):** TCO зоопарка vs одной СУБД (лицензии, эксплуатация, экспертиза); риск-цена штрафа за PII; время выхода на рынок (managed-сервисы vs self-hosted); язык переговоров с вендором через PACELC.

### 4. Резюме и мостик к Лекции 5 (10 мин)
- 5 ключевых выводов: (1) класс СУБД = ответ на паттерн доступа; (2) CAP/PACELC — рабочий инструмент формулирования гарантий; (3) ACID и изоляция — контракт, который надо выбирать осознанно; (4) один источник истины на факт, остальное — проекции; (5) governance-ограничения влияют на выбор стека до покупки лицензии.
- Артефакт: заполненная матрица + ADR-008 + фрагмент стратегии Data Governance → часть Architecture Blueprint.
- Мостик: «Стек выбран. Но как приложение с ним разговаривает? Пулы соединений, ORM vs Raw SQL, проблема N+1 и SQL-инъекции» — **Лекция 5** «Взаимодействие приложений с СУБД, уязвимости и инструменты разработчика».
- Вопросы для самопроверки (5).
