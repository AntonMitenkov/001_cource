# Кейс Лекции 7 — «Шесть правильных решений без архитектуры: сборка Blueprint каршеринга»

## Название
Финальная сборка: от слоёв к Architecture Blueprint, через Peer-Review к защите.

## Контекст
Сервис каршеринга из сквозного кейса курса (параметры унаследованы из Л1–Л6: ~200 автомобилей, 3 города, MVP за 3 месяца, команда 8 человек). К началу Лекции 7 существуют все проектные слои, но они живут в отдельных документах:
- Л1–Л2: NFR, цена простоя, карта стейкхолдеров;
- Л2–Л3: bounded contexts, доменная модель, логическая модель 3НФ;
- Л4: полиглотный стек и ADR-008, стратегия Data Governance (PII, retention, crypto-shredding);
- Л5: схема взаимодействия приложения с БД и ADR-010 (каналы доступа, prepared statements, роли);
- Л6: стратегия репликации и бэкапов с RPO/RTO по контекстам и ADR-011.

За три недели до демо дня заказчик требует показать «единую архитектуру», а внешний рецензент анонсировал получасовую проверку решения перед стартом разработки.

## Бизнес-цель / проблема
Команда умеет защищать каждое решение по отдельности, но не может ответить на системные вопросы: как компоненты связаны, что произойдёт при отказе одного узла схемы, где конфликтуют профили нагрузки, какие компромиссы вообще не зафиксаны. Три конкретных инцидента ревью (см. Hook): декоративная очередь без потребителя; поиск, читающий из OLTP-таблицы бронирования; «ADR» про микросервисы без альтернатив и последствий. Риск: старт разработки по несогласованному проекту → переделки, срыв MVP, потеря доверения.

## Участники и их позиции
- **Product Owner:** хочет срок MVP и предсказуемую стоимость изменений; раздражён «археологией по шести документам».
- **Tech Lead / архитектор команды:** знает все решения, но не формализовал связи; боится, что полный CQRS/ES «выпросят» модные инвесторы.
- **Backend-разработчики:** хотят ясных границ и каналов данных (кто пишет, кто читает, какой лаг допустим).
- **DBA (приёмщик ТЗ следующего семестра):** требует полноты модели, governance и планов надёжности — иначе оценка работ невозможна.
- **Внешний рецензент (peer reviewer):** оценивает связность, а не список технологий; задаёт вопрос «какое NFR нарушается?».
- **DPO/финансовый контролёр (опционально):** проверяет, что копия, кэш и аналитика не нарушают стратегию PII (Л4/Л6).

## Проблема детально (что именно нужно собрать)
1. Единая схема уровня C4 Container со всеми подписанными потоками.
2. Обоснование каждого компонента (Primary Storage, Cache, Queues, Analytics) — или его удаление.
3. Решение конфликта профилей «поиск vs бронирование» — через паттерны сборки (CQRS-lite) с фиксацией в новом ADR.
4. Осознанные «не делаем» (Event Sourcing, шардирование) — тоже оформленные ADR.
5. Процедура Peer-Review по рубрике до защиты, а не вместо неё.

## Ограничения
- **Бюджет:** облачный бюджет MVP [точная сумма — требуется проверка]; каждый новый компонент увеличивает CAPEX/OPEX и поверхность резервирования (Л6).
- **Время:** 3 недели до демо; команда 8 человек, выделенного архитектора нет.
- **Технологии:** стек зафиксирован ADR-008; новые СУБД/брокеры только через ADR с альтернативами.
- **Комплаенс:** геоданные и персональные данные покрыты стратегией Л4; любые копии/проекции наследуют требования retention.
- **Команда:** опыт с реляционными СУБД есть, опыта эксплуатации ES/шардирования нет — это ограничение выбора, а не мнение.

## Архитектурный вопрос
Как собрать существующие решения в единую связную архитектуру (Blueprint), закрыть конфликт профилей чтения/записи минимально достаточным паттерном и пройти внешнее ревью так, чтобы итоговый документ был пригоден как ТЗ для реализации?

## Ожидаемое решение (без готового ответа — ориентиры для разбора на занятии)
Студенты должны:
- построить C4 Container-схему и подписать потоки (правила c4-model.md);
- применить упражнение «почему этот ящик здесь?» ко всем компонентам; удалить/обосновать спорные;
- выбрать между: единая таблица (конфликт профилей), полный CQRS+ES (цена выше пользы MVP), CQRS-lite на уже существующем derived store (обосновать выбор через NFR: целостность броней > секундная свежесть поиска);
- оформить ADR-012 (принятое решение) и ADR об отказе от ES/шардирования («не делать — тоже решение»);
- провести взаимное рецензирование по рубрике (5 критериев × 3 уровня) с замечаниями формата «наблюдение → следствие → предложение»;
- подготовить структуру 10-минутной защиты с anticipated questions.

## Артефакты студентов по итогам кейса
1. Architecture Blueprint v1 (C4 Container + легенда потоков + раздел Failure Modes со ссылками на Л6).
2. Реестр ADR-008…012+ (включая «отказные» ADR).
3. Заполненная рубрика Peer-Review чужого Blueprint + реакции автора.
4. План защиты: каркас 10 минут, топ-5 anticipated questions с ответами-ссылками на ADR/NFR.

## Вопросы для обсуждения
1. Какой из трёх инцидентов Hook опаснее всего и почему — декоративный компонент, конфликт профилей или «модный» ADR?
2. Почему «мы НЕ делаем Event Sourcing» стоит задокументировать? Что произойдёт без такой записи через полгода?
3. На каком измеримом основании команда откажется от шардирования сегодня и при каком сигнале вернётся к нему? (Связь с Л8.)
4. Какие пункты чек-листа отчёта ваш Blueprint сейчас проваливает? Проверьте по трассировке «NFR → решение → ADR».
5. Если бизнес требует x10 роста через квартал — какой контейнер схемы сломается первым и что это меняет в ADR? (Мостик к Л8.)

## Связь с другими лекциями
- **Л4:** derived stores и Source of Truth — фундамент «CQRS-lite»; PACELC объясняет объявленный лаг проекции.
- **Л5:** outbox/каналы — механизм доставки событий в проекцию; роли доступа к Primary Storage.
- **Л6:** путь проекции становится критической зависимостью → попадает в RPO/RTO-план; копия ≠ кэш.
- **Л8:** рост x10 нагружает Blueprint: кэш-стратегии, индексы, OLTP/OLAP-разделение — следующий шаг после сборки.

## Примечания честности
Числовые параметры (p95, лаг, бюджет) — учебные или помечены [требуется проверка]; рубрика и чек-лист — методическая разработка курса.
