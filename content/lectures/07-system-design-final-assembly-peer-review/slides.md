## Слайд 6. Тезис: архитектура = связность
- Каждое решение привязано к NFR, зафиксировано в ADR, видно на схеме
- Проверка проходит ДО защиты, а не вместо неё
- Переходим к инвентаризации компонентов (Д1)

## Слайд 7. Теория A: четыре класса компонентов (Д1)
- Primary Storage — источник истины, всегда есть, один на контекст
- Cache — только при измеренной горячей точке; данные можно пересчитать
- Queues — только с consumer'ом; очередь ≠ хранилище (правило Л4)
- Analytics — derived store, отделён от OLTP, лаг объявлен

## Слайд 8. Упражнение «почему этот ящик здесь?» (Д2)
- Формула: «присутствует, потому что <NFR/проблема>, без него <что сломается>»
- Нет ответа → компонент кандидат на удаление
- Декоративный ящик = CAPEX/OPEX + мониторинг + бэкапы (Л6) + governance (Л4)

## Слайд 9. Теория B: CQRS — драйв и цена (Д3)
- Драйв: профили чтения и записи конфликтуют
- Суть: команда пишет в одну форму, запрос читает из проекции
- Цена: два пути кода, eventual lag, риск рассинхронизации
- Не надо: MVP, простой CRUD, одна команда

## Слайд 10. CQRS ≠ Event Sourcing (Д4)
- ES — события как источник истины, состояние = проекция
- Драйв ES: аудит, переигровка «как было на дату», богатый жизненный цикл
- Цена: эволюция схемы событий, рост хранилища, дорогая отладка
- Независимые паттерны: квадранты «CQRS без ES» и «ES без CQRS» легитимны

## Слайд 11. Каршерингу MVP: CQRS-lite, отказ от ES
- Поиск уже derived-store проекция (ADR-008, Л4) — половина CQRS легитимна
- Полный ES — over-engineering; фиксируем «не делаем» отдельным ADR
- ADR об отказе — полноценный ADR (Д5: квадрант применения)

## Слайд 12. Шардирование — последняя ступень (Д6)
- Драйв: измеренный упор одного узла после всей лестницы
- Три цены: cross-shard транзакции, hot key, rebalancing на живой системе
- Лестница: профилировать → индексы → кэш → read replicas → шарды
- В Blueprint ~200 авто шардов нет — и это записанное решение

## Слайд 13. Теория C: что делает ADR валидным (Д7)
- Контекст с фактами (NFR/бюджет/команда), а не с модой
- ≥1 альтернатива с причиной отказа; отрицательные последствия обязательны
- Статус и связи между ADR; реестр без противоречий
- ADR-декларация = незаполненный документ

## Слайд 14. Чек-лист финальной проверки отчёта (Д8)
- 7 групп: прослеживаемость NFR→решение→ADR; обоснование схемы; согласованность данных Л3↔Л4↔Л5
- Надёжность (RPO/RTO, отказные сценарии Л6) и governance (PII в копиях/кэше)
- Реестр ADR и ТЗ-пригодность для следующего семестра
- Методическая разработка курса, проверяем ДО комиссии

## Слайд 15. Теория D: Peer-Review — правила
- Цель: найти дыры, пока за них не платит продакшн; рецензируем артефакт, не автора
- Факт, не мнение; привязка к критерию/NFR; предложение, не приказ
- Формат записи: Наблюдение → Следствие → Предложение

## Слайд 16. Рубрика Peer-Review (5×3)
- Связность NFR→решения · Обоснованность компонентов · Полнота ADR
- Надёжность и governance · Читаемость схемы
- Уровни: черновик / рабочий / защищаемый
- Автор принимает или отклоняет с записью причины (мини-ADR на реакцию)

## Слайд 17. Теория E: две аудитории защиты
- CTO/архитекторы: trade-offs, ADR, failure modes
- Бизнес/финансы: стоимость, риск, time-to-market
- Один контент — разные языки; критерий успеха: оспоримо только новыми фактами

## Слайд 18. Каркас защиты 10 минут

## Слайд 20. Case Study: проверка обоснований и ADR-012 (шаги 3–4)

## Слайд 22. Управленческие выводы
- Цена дыры растёт со временем: ревью — часы, провал защиты — доверие и сроки, продакшн — авария
- Заказчик проверяет связность «деньги ↔ NFR ↔ решения ↔ риски»
- Незадокументированный компромисс = скрытое обязательство (долг неизвестного размера)
- Quality of Handoff: Blueprint становится ТЗ для курса «Базы данных»
