# Практика Лекции 7 — «Сборка Blueprint + Peer-Review + подготовка защиты»

## Тип
Индивидуально с парным Peer-Review (обмен артефактами). Итоговый артефакт входит в Architecture Blueprint учебного проекта курса.

## Формулировка задания
По своему учебному кейсу (не каршеринг — он разобран на лекции):
1. Собрать **Architecture Blueprint v1**: единая C4 Container-схема, объединяющая ваши слои Л1–Л6 (NFR, домен/модель, стек и governance, каналы доступа, надёжность). Все потоки подписаны: кто инициирует, какие данные, синхронно/асинхронно.
2. Провести для каждого компонента упражнение **«почему этот ящик здесь?»** (одна фраза: проблема/NFR + что сломается без него). Компонент без ответа — удалить или записать как planned с ADR-черновиком.
3. Оформить **один новый ADR** уровня сборки: принятое решение связности (например, проекция для чтения / очередь событий / кэш) **или осознанный отказ** («не делаем Event Sourcing/шардирование, потому что…»). Требования валидности: контекст с фактами, ≥1 альтернатива с причиной отказа, отрицательные последствия, статус.
4. Обменяться Blueprint с коллегой; рецензент заполняет **рубрику Peer-Review** (бланк — `templates/peer-review.md`; 5 критериев × 3 уровня из draft §D) и формулирует **≥3 замечания** в формате «Наблюдение → Следствие → Предложение». Автор фиксирует по каждому: принято / отклонено с причиной.
5. Подготовить **3-минутный pitch защиты** по каркасу 10-минутной защиты (сжатая версия): проблема+NFR → схема → 1 ключевой ADR с ценой → риск/open question → просьба. Плюс топ-3 anticipated questions с ответами-ссылками на ADR/NFR.

## Шаги выполнения
| Шаг | Действие | Время (аудиторно) |
|---|---|---|
| 1 | Инвентаризация слоёв Л1–Л6 вашего кейса (список артефактов и решений) | 10' |
| 2 | Сборка C4 Container-схемы + легенда потоков | 20' |
| 3 | Упражнение «почему ящик здесь?» + чистка декоративных компонентов | 10' |
| 4 | Новый ADR (решение или отказ) | 15' |
| 5 | Обмен и заполнение рубрики, замечания Н→С→П | 15' |
| 6 | Реакции автора + правки Blueprint v1.1 | 10' |
| 7 | Pitch 3' + anticipated questions | 10' |

## Шаблоны результатов
**Шаблон A. Легенда компонента:**
```
Компонент: <название, тип: Primary Storage / Cache / Queue / Analytics>
Присутствует, потому что: <проблема/NFR со ссылкой>
Без него: <что сломается / деградирует>
Связанные ADR: <номера>
```
**Шаблон B. Структура нового ADR** — по knowledge/system-design/ADR.md (Статус/Контекст/Решение/Последствия ±). Для «отказного» ADR в поле «Решение»: «Не используем X, пока не наступит сигнал Y».

**Шаблон C. Замечание Peer-Review:**
```
[Н] Наблюдение (факт из схемы/отчёта, ссылка на элемент):
[С] Следствие (какое NFR/пункт чек-листа нарушается, чем рискуем):
[П] Предложение (вариант + его цена; право выбора за автором):
Реакция автора: принято → ADR-___ / отклонено, причина: ___
```
**Шаблон D. Рубрика (краткая форма):** пять критериев (связность NFR→решения; обоснованность компонентов; полнота ADR; надёжность и governance; читаемость схемы), оценка 1–3, обязательное обоснование каждой оценки одной строкой.

## Критерии оценки (100 баллов)
- Blueprint: полнота слоёв и подписи потоков, отсутствие необоснованных компонентов — **30**
- Новый ADR соответствует тесту валидности (альтернативы, цена, статус) — **20**
- Рубрика заполнена полностью, ≥3 замечаний формата Н→С→П, без оценочных суждений о личности — **20**
- Реакции автора зафиксированы (принято/отклонено+причина) — **10**
- Pitch: укладывается в 3', есть open questions, ответы со ссылками на ADR/NFR — **20**

## Подсказки
- Если компонент «на грани» — решайте через объявленный риск, а не удалением молча: ADR «живёт, но под наблюдением» тоже валиден.
- Отказной ADR проверяйте вопросом: «кто следующий инженер прочитает его и не захочет "доделать" просто так?»
- Замечание «всё хорошо» = незаполненная рубрика. Ищите дыру по чек-листу §C: трассировка NFR → решение → ADR обрывается где-то почти всегда.
- Pet-peeve ревьюеров: схема без стрелок деградации (что работает частично при отказе брокера/реплики) — опора на Failure Modes Л6.

## Типичные ошибки студентов
1. Перерисовали «модную» целевую архитектуру вместо сборки принятых решений (нарушение шага 1).
2. ADR без отрицательных последствий («решение идеально») — невалиден.
3. Peer-Review превращается в спор о вкусах: нет ссылки на NFR/чек-лист.
4. Pitch на 10 минут за 3 минуты — попытка «вместить всё»; лечится выбором одного ключевого ADR.
5. Забыли, что Blueprint — ТЗ для следующего семестра: нет владельца таблиц, retention, RPO/RTO на схеме.

## Связь с итоговым проектом
Blueprint v1.1 после Peer-Review — основа итоговой сдачи курса; рубрика и реакции входят в приложение к отчёту; pitch репетирует защиту. Следующая лекция (Л8) добавит в Blueprint раздел «Стратегия масштабирования» — сохраняйте версию схемы, которую сможете нагрузить x10 мысленно уже сейчас (anticipated question «что сломается первым?» вернётся).
