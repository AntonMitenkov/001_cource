# Лекция 7. System Design: финальная сборка, Peer-Review и защита отчета

> Статус: кандидат в final. Причина: ожидает human review / human fact-check. Источник истины темы: specs/syllabus.md, Лекция 7.

## Цель занятия
Собрать все проектные слои курса (требования, домен, модель данных, СУБД, каналы доступа, надёжность) в единый Architecture Blueprint; научиться обосновывать паттерны сборки через trade-offs; освоить процедуру Peer-Review по рубрике и структуру защиты архитектурного решения перед технической и бизнес-аудиторией.

## Learning Objectives
1. Разложить систему на компоненты System Design (Primary Storage, Cache, Queues, Analytics) с обоснованием каждого и ссылкой на NFR/ADR.
2. Объяснить CQRS, Event Sourcing и шардирование через trade-offs и контекст применения; называть ситуации, где паттерн не нужен.
3. Провести финальную проверку архитектурного отчёта по чек-листу (прослеживаемость NFR → решение → ADR, полнота ADR, покрытие отказных сценариев и governance).
4. Дать конструктивную обратную связь чужому Blueprint по формату «наблюдение → следствие → предложение» и заполнить рубрику Peer-Review.
5. Построить структуру защиты: два слоя изложения, тайминг, anticipated questions, опора на ADR/NFR в ответах.
6. Сформулировать передачу итогового Blueprint как технического задания курсу «Базы данных».

## Hook (5 мин)

Команда каршеринга приходит на защиту MVP с папкой «лучших решений»: PostgreSQL для OLTP (Л4), пулы соединений (Л5), полусинхронная репликация и PITR (Л6). Всё по отдельности — грамотно. Но единой схемы нет.

Внешний рецензент за три вопроса вскрывает дыры:
1. На схеме очередь стоит между мобильным клиентом и БД телеметрии. Вопрос: «кто потребитель?» — ответа нет. Ящик нарисован «для красоты».
2. Поиск свободных машин читает из той же таблицы и индексов, куда пишет бронирование. Конфликт профилей нагрузки не решён, ADR нет.
3. В отчёте: «используем микросервисы, потому что современно». Альтернатив нет, последствий нет — это не ADR, а декларация моды.

**Вопрос залу:** чем «набор правильных решений» отличается от «архитектуры»? *(Ответ, к которому придём: архитектурой их делает связность — каждое решение привязано к NFR, зафиксировано с компромиссами и проходит проверку чужими глазами до, а не после защиты.)*

## Теоретический блок (35 мин)

### A. Компоненты System Design: четыре типа «ящиков», у которых должно быть право стоять на схеме (8 мин)

Итоговая схема уровня C4 Container (см. knowledge/system-design/c4-model.md) типично собирается из четырёх классов компонентов. Это классификация для учебного разбора, а не отраслевой стандарт.

| Компонент | Роль | Откуда у нас | Правило появления |
|---|---|---|---|
| **Primary Storage** | Источник истины (Source of Truth), состояние бизнеса | Л4 (ADR-008), Л3 (модель 3НФ) | Всегда есть; один на контекст |
| **Cache** | Ускорение повторяющегося чтения; временное, потерянно-безопасное | Глоссарий: Cache-Aside, Write-Through, Write-Behind | Только при измеренной горячей точке чтения; данные можно пересчитать |
| **Queues** | Асинхронная развязка producer↔consumer, сглаживание пиков | knowledge/integrations/brokers.md, queues.md | Только когда есть consumer и допустимая задержка; очередь — не хранилище (правило Л4) |
| **Analytics** | OLAP-проекция для отчётов и решений | Л4 (derived store, CDC/ETL) | Отделена от OLTP; обновляется с лагом, лаг объявлен |

**Упражнение «почему этот ящик здесь?»** — для каждого компонента схемы отвечаете одной фразой: «присутствует, потому что <NFR/проблема>, без него <что сломается>». Не можете ответить — компонент кандидат на удаление. Декоративные компоненты стоят денег: их надо развернуть, мониторить, зарезервировать копированием (Л6) и покрыть governance (Л4).

### B. Паттерны сборки: CQRS, Event Sourcing, шардирование (10 мин)

#### CQRS (Command Query Responsibility Segregation)
- **Драйв:** профили чтения и записи конфликтуют — запись требует нормализации и целостности (Л3), чтение хочет денормализованную удобную форму (Л3, denormalization.md; Л4, derived store).
- **Суть:** разделить модели: команда пишет в одну форму, запрос читает из другой (проекции). Обновление проекции — асинхронное ⇒ появляется Replication-style Lag (Л4/Л6): «последняя позиция машины может отставать на N секунд» — это объявленное решение, а не баг.
- **Цена:** два пути кода вместо одного; согласованность eventual (Л4); риск рассинхронизации проекций.
- **Когда НЕ надо:** MVP с малой нагрузкой, простой CRUD, одна команда разработки. Полный CQRS для каршеринга MVP — over-engineering; достаточно «CQRS-lite»: поиск уже является derived-проекцией (ADR-008, Л4) — фактически половина паттерна у нас есть легитимно.

#### Event Sourcing
- **Драйв:** нужна полная история изменений (аудит, переигровка состояния «как было на дату», сложные домены с богатым жизненным циклом).
- **Суть:** хранить последовательность событий как источник истины, текущее состояние — проекция из событий (термин глоссария).
- **Цена:** события — часть контракта (эволюция схемы событий, Л3 schema-evolution); «переписать историю» дорого; непривычная модель отладки; хранилище растёт неограниченно (retention! Л4/Л6).
- **Когда НЕ надо:** если аудит делается дешевле (audit-log таблица, outbox events Л5); состояние простое. **Каршерингу MVP полный ES не требуется** — фиксируем как ADR с обоснованием «не делаем, потому что…». ADR об отказе от паттерна — полноценный ADR.

#### Шардирование (horizontal partitioning)
- **Драйв:** измеренный упор одного узла: объём или write throughput, которые нельзя решить вертикальным масштабированием и чтением с реплик (Л6).
- **Три цены:** (1) **Cross-shard транзакции** — ACID-граница рвётся (Л4); (2) **Hot key** — шард с «звёздной» машиной/городом перегружен, остальные простаивают; (3) **Rebalancing** — переезд данных между шардами на живой системе.
- **Правило порядка (лестница):** профилировать → индексы (будет Л8) → кэш → read replicas → только потом шарды. В Blueprint каршеринга (~200 авто) шардирования нет — и это должно быть *записано* как осознанное решение, иначе следующий инженер «доделает».

> Паттерны CQRS и Event Sourcing определены в `knowledge/glossary.md` (строки 20, 33); исторически их популяризация связывается с сообществом DDD (Мартин Фаулер — общая атрибуция без точных цитат;human fact-check не выполнен — статус pending-human).

### C. Фиксация компромиссов и чек-лист финальной проверки отчёта (6 мин)

**Что делает ADR валидным** (по шаблону knowledge/system-design/ADR.md):
1. Контекст с числами/фактами (NFR, бюджет, команда), а не с модой;
2. Минимум одна рассмотренная альтернатива и причина отказа;
3. Последствия — обязательно отрицательные/риски; «решений без цены» не бывает (Л1, trade-offs.md);
4. Статус и связь: какие ещё ADR зависят/заменяются.
ADR без альтернатив или без отрицательных последствий = незаполненный документ. ADR «мы НЕ делаем X» — легитимен и полезен.

**Чек-лист финальной проверки отчёта** (методическая разработка курса, 7 групп):
1. Прослеживаемость: каждое NFR (Л1–2) → минимум одно архитектурное решение; каждое решение → ADR.
2. Схема: все компоненты имеют обоснование (§A); потоки подписаны (кто инициирует, какие данные — правило c4-model.md).
3. Данные: модель Л3 ↔ физический выбор Л4 ↔ каналы доступа Л5 согласованы (нет «висячих» таблиц без владельца).
4. Надёжность: RPO/RTO по контекстам + отказные сценарии Л6 отражены на схеме (где реплики, где бэкапы).
5. Governance: PII-инвентарь и retention (Л4) покрывают копии и кэш (Л6 замечание: бэкапы содержат PII).
6. Реестр ADR: полнота (§C), нет противоречий между ADR.
7. Передаваемость: разделы написаны так, что DBA следующего семестра может реализовать без вопросов к автору (ТЗ-пригодность).

### D. Peer-Review: правила конструктивной обратной связи (6 мин)

**Цель ревью** — найти дыры, пока за них не платит продакшн. Рецензирует артефакт, не автора.

Три правила:
1. **Факт, не мнение:** «компонент Queue без потребителя» вместо «мне не нравится очередь».
2. **Привязка к критерию:** нарушение какого NFR/пункта чек-листа (§C)? Вопрос «какое NFR нарушается?» обязателен.
3. **Предложение, не приказ:** вариант + его цена; решение остаётся автору (Conway/ownership — см. knowledge/system-design/conway-law.md о коммуникациях).

**Формат записи замечания:** «Наблюдение → Следствие → Предложение».
Пример: «На: поиск читает из OLTP-таблицы. Сл: конфликт профилей, p95 поиска деградирует при росте writes. Пр: derived-проекция как в ADR-008 либо обоснование "рано" в новом ADR».

**Рубрика Peer-Review** (5 критериев × 3 уровня; методическая разработка курса, веса — для учебного процесса):

| Критерий | 1 — черновик | 2 — рабочий | 3 — защищаемый |
|---|---|---|---|
| Связность NFR→решения | NFR упомянуты, не связаны | частично прослежено | каждое ключевое NFR имеет решение+ADR |
| Обоснованность компонентов | декоративные ящики | вопросы закрыты текстом | каждый ящик имеет ссылку на проблему/ADR |
| Полнота ADR | декларации без цены | есть последствия | есть альтернативы, статусы, взаимосвязи |
| Надёжность и governance | отсутствует | общие слова | RPO/RTO по контекстам, PII-покрытие копий |
| Читаемость схемы | нет подписей/уровней C4 | читается с вопросами | внешняя аудитория понимает за 5 минут |

Рецензент заполняет рубрику + 3 замечания в формате Н→С→П; автор принимает/отклоняет с записью причины (мини-ADR на реакцию).

### E. Структура и критерии успешной защиты (5 мин)

**Две аудитории, один контент, разные языки:** техническая (CTO/архитекторы) хочет trade-offs, ADR, failure modes; бизнес (заказчик/финансы) — стоимость, риск, time-to-market. Каркас 10-минутной защиты:
1. Проблема и NFR (1') — язык бизнеса;
2. Solution overview: Blueprint одним слайдом (2');
3. Ключевые решения и их цена: 3 ADR max (3') — язык архитектуры;
4. Что может сломаться и план (2') — RPO/RTO, деградации;
5. Риски и open questions (1') — честный список;
6. Просьба/решение, которое нужно принять (1').

**Anticipated questions** — готовите заранее топ-5 атак: «почему не Х?», «что при росте x10?» (спойлер к Л8), «сколько стоит?», «что будет при отказе города?» (Л6), «почему не микросервисы?» (Л3/styles).

**Критерий успешной защиты:** решение можно оспорить только новыми фактами (другие NFR, другой бюджет), но не пробелами логики. «Об этом не подумали» — провал защиты даже при отличной схеме.

## Case Study (20 мин): сборка Blueprint каршеринга

Контекст унаследован: ~200 авто, 3 города, MVP 3 мес., команда 8 человек; ADR-008 (полиглотный стек, Л4), ADR-010 (каналы доступа, Л5), ADR-011 (репликация/бэкапы, Л6).

**Шаг 1. Инвентаризация слоёв.** Выписываем существующие артефакты Л1–Л6 в один список. Правило: ничего нового не изобретаем — собираем.
**Шаг 2. C4 Container.** Рисуем контейнеры: мобильное приложение, API-сервис, Бронирование/Оплата (Primary Storage, OLTP), Телеметрия (time-series), Поиск (derived store), Очередь событий поездок (broker), Аналитика (DWH через CDC/ETL), Кэш сессий. Каждый поток подписан (кто инициирует, что несёт).
**Шаг 3. Проверка обоснований (§A).** Очередь: consumer — проекция поиска и аналитика (легитимно, событие «поездка завершена»). Кэш сессий: драйвер — частое чтение профиля при p95 из Л1. Аналитика отделена: OLTP не читает отчёты (Л4).
**Шаг 4. Новые решения сборки → ADR-012.**
```
ADR-012: CQRS-lite для контекста «Поиск availability»
Статус: Принято
Контекст: Профиль чтения поиска (гео-запросы, высокий QPS) конфликтует с
профилем записи бронирования (ACID, низкий latency). NFR: p95 поиска — учебная иллюстрация (значение зависит от окружения),
целостность броней приоритетнее свежести поиска на секунды.
Альтернативы: (a) единая таблица с индексами — отказ: конфликт профилей;
(b) полный CQRS+Event Sourcing — отказ: цена выше пользы для MVP.
Решение: поиск остаётся derived-store проекцией (ADR-008), обновление через
очередь событий (outbox, Л5); лаг ≤ [примерно] единиц секунд — объявлен продукту.
Последствия: + eventual consistency для поиска (плюс: изоляция профилей);
минус: путь проекции — критическая зависимость, попадает в monitoring и в план Л6.
```
**Шаг 5. Мини-Peer-Review в парах (5 мин из блока).** Обмениваетесь Blueprint с соседом; заполняете рубрику (§D) на чужую схему; находите ≥3 замечания формата Н→С→П; автор фиксирует реакции.
**Финальный артефакт:** Blueprint v1 + реестр ADR-008…012 + заполненная рубрика + план 10-минутной защиты.

## Связка с управленческими решениями (10 мин)

- **Цена находки дыры растёт со временем.** Дефект обоснования, пойманный на внутреннем ревью — часы правки; на защите стейкхолдеров — пересборка доверения и перенос сроков; в продакшене — авария. Peer-Review — дешёвая страховка: организуйте его как обязательный gate перед защитой/разработкой.
- **Что проверяет заказчик/инвестор:** не «какие технологии», а связность «деньги ↔ NFR ↔ решения ↔ риски». Отчёт, прошедший чек-лист §C, отвечает на это без слов; декоративные компоненты — прямые CAPEX/OPEX (лицензии, инфраструктура, экспертиза поддержки).
- **Time-to-market vs полнота.** Для MVP-Blueprint допустимы осознанные «не делаем» (ES, шарды) — но они должны быть записаны как ADR, иначе превращаются в долг неизвестного размера. Незадокументированный компромисс = скрытое обязательство.
- **Передача в реализацию.** Итоговый отчёт курса становится ТЗ для курса «Базы данных» (следующий семестр): модель, ADR по хранению, стратегия надёжности и governance — то, по чему DBA считает стоимость работ. Качество передачи — критерий TPR (готовность к исполнению) в рубрике.

## Ключевые термины
- **Architecture Blueprint** — итоговая связная схема системы (уровень C4 Container) со сводным реестром ADR, покрывающая все спроектированные слои. *(предложение в глоссарий)*
- **CQRS** — паттерн разделения моделей чтения и записи (глоссарий — есть).
- **Event Sourcing** — хранение состояния как последовательности событий (глоссарий — есть).
- **Шард / Shard Key** — горизонтальный фрагмент данных и атрибут разбиения. *(предложение в глоссарий)*
- **Hot Key Problem** — дисбаланс нагрузки на один шард из-за «популярного» значения ключа. *(предложение)*
- **Cross-shard Transaction** — транзакция, затрагивающая несколько шардов; ACID-граница усложняется/рвётся. *(предложение)*
- **Peer-Review (архитектурный)** — процедура взаимной оценки артефакта по рубрике с замечаниями формата «наблюдение → следствие → предложение». *(предложение)*
- **TPR (Transparency for Realization / ТЗ-пригодность)** — пригодность отчёта для передачи в реализацию без уточнений автора. *(учебный термин курса)*

## Anti-patterns
1. **«Архитектура из моды»:** компонент/паттерн в схеме без ссылки на проблему и NFR («микросервисы, потому что современно»). Лечение: упражнение «почему этот ящик здесь?».
2. **«Шардируем заранее»:** горизонтальное разбиение до измеренного упора — оплачиваете cross-shard TX и ребалансировку за нагрузку, которой нет.
3. **«ADR-декларация»:** решение без альтернатив и отрицательных последствий. Такой ADR не защищает от пересмотра и не обучает организацию.
4. **«Riot-ревью»:** обратная связь «всё плохо / всё ок» без привязки к критериям рубрики и NFR. Ревью, не меняющее артефакт, — ритуал.
5. **«Защита без рисков»:** презентация, в которой нет ни одного open question. Комиссия сама найдёт дыру — уже на ваших глазах; честный список рисков усиливает позицию.

## Резюме (5 мин)
1. Архитектура = связность: NFR → решение → ADR → схема; декоративных компонентов нет.
2. CQRS ≠ Event Sourcing; оба — ответы на конкретные драйвы, и «не делаем» тоже пишется в ADR.
3. Шардирование — последняя ступень лестницы, не первая.
4. Чек-лист из 7 групп проверяет отчёт до того, как его проверит комиссия.
5. Peer-Review — страховка по цене часа, а не аварии.
