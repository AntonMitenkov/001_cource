# План Лекции 7 — System Design: финальная сборка, Peer-Review и защита отчета

## Цель занятия
Научиться собирать разрозненные проектные решения (Л1–Л6) в единый Architecture Blueprint, обосновывать сквозные паттерны сборки (CQRS, Event Sourcing, шардирование) через trade-offs, проводить конструктивный Peer-Review по рубрике и готовить защиту перед технической и бизнес-аудиторией.

## Learning Objectives
По завершении занятия студент способен:
1. **LO1.** Разложить систему на компоненты System Design (Primary Storage, Cache, Queues, Analytics) и для каждого привести обоснование «зачем он здесь» и ссылку на NFR/ADR; удалить декоративные компоненты из схемы. *(acceptance: собирает компоненты в единую схему)*
2. **LO2.** Объяснить CQRS, Event Sourcing и шардирование через trade-offs и контекст применения; для каждого назвать драйв внедрения и цену, и ситуации, где паттерн не нужен. *(acceptance: объясняет через trade-offs и контекст)*
3. **LO3.** Провести финальную проверку архитектурного отчёта по чек-листу: прослеживаемость NFR → решение → ADR, полнота ADR (контекст/альтернативы/последствия), покрытие отказных сценариев и governance. *(acceptance: фиксация компромиссов и проверка отчёта)*
4. **LO4.** Дать конструктивную обратную связь чужому Blueprint по формату «наблюдение → следствие → предложение» и заполнить рубрику Peer-Review без оценочных суждений о личности автора. *(acceptance: проводит Peer-Review по рубрике)*
5. **LO5.** Построить структуру защиты: два слоя изложения (технический/бизнес), тайминг, anticipated questions, опора на ADR и NFR при ответах. *(acceptance: защищает решение перед технической и бизнес-аудиторией)*
6. **LO6.** Сформулировать, как итоговый Blueprint становится техническим заданием для курса «Базы данных» (следующий семестр).

## Последовательность блоков (детализация)
1. **Hook (5')** — история из brief; вопрос залу: «чем набор правильных решений отличается от архитектуры?»
2. **Теория A (8')** — карта четырёх компонентов; упражнение «почему этот ящик здесь?» для 3 элементов схемы; связка Source of Truth (Л4).
3. **Теория B (10')** — CQRS: когда профили чтения и записи конфликтуют; Event Sourcing: аудит и переигровка, цена (хранилище событий, проекции, эволюция схемы событий); шардирование: три боли (cross-shard TX, hot key, ребалансировка); анти-паттерн «шардируем заранее».
4. **Теория C (6')** — anatomy ADR (по knowledge/system-design/ADR.md); тест «можно ли оспорить только фактами»; чек-лист отчёта: 7 групп проверок.
5. **Теория D (6')** — правила Peer-Review; примеры «деструктивно → конструктивно»; рубрика: 5 критериев × 3 уровня.
6. **Теория E (5')** — каркас защиты 10 минут: проблема→NFR→решение→компромиссы→риски→просьба; различие языка для CTO и для финансового директора.
7. **Case Study (20')** — шаги 1–5 (см. draft/case.md): сборка Blueprint каршеринга; оформление ADR-012; парный мини-Peer-Review по рубрике (5' из блока).
8. **Управление (10')** — стоимость находки дыры до/после защиты; ревью как страховка; KPI архитектора.
9. **Резюме (5')** — 5 выводов; опрос непонятного; мостик к Л8.

## Переходы между блоками
- Hook→A: «все три дыры — это отсутствующие обоснования компонентов; начнём с правил, по которым ящик имеет право быть на схеме».
- A→B: «компоненты есть — но как их связать, когда чтение и запись дерутся за один ресурс? Здесь появляются паттерны сборки».
- B→C: «любое "почему именно так" должно быть записано иначе оно потеряется — переходим к ADR и чек-листу».
- C→D: «чек-лист свой отчёт проверить легко; сложнее увидеть чужие дыры — для этого процедура Peer-Review».
- D→E: «рецензии пройдены, отчёт собран — остаётся продать решение двум аудиториям».
- E→Case: «применяем всё сразу: собираем, рецензируем и готовим защиту Blueprint каршеринга».

## Визуальные материалы (см. diagrams.md)
Д1 слои→Blueprint (C4 Container каршеринга); Д2 четыре компонента и правило обоснования; Д3 CQRS vs Event Sourcing (2×2 независимости); Д4 лестница масштабирования с шардированием как последней ступенью; Д5 анатомия валидного ADR; Д6 чек-лист отчёта (mindmap); Д7 рубрика Peer-Review (таблица) и формат обратной связи; Д8 каркас защиты 10 минут (два слоя аудитории).

## Практика (см. practice.md)
Индивидуально/в парах: собрать Blueprint своего учебного кейса (не каршеринга), оформить 1 новый ADR, обменяться с соседом и заполнить рубрику, подготовить 3-minute pitch защиты. Артефакты: Blueprint v1, заполненная рубрика, план защиты.

- Термины согласованы с glossary.md (CQRS, Event Sourcing, Cache-Aside уже там).
