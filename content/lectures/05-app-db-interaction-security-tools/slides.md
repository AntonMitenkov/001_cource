# Слайды к лекции 5: Взаимодействие приложений с СУБД, уязвимости и инструменты разработчика

> Краткая визуальная поддержка 80-минутной лекции (slides-contract: один слайд — одна мысль, 3–6 тезисов).
> Источник текста: `final.md`; диаграммы-источники: `diagrams.md` (номера Д1–Д8 указаны в скобках).
> Статус: кандидат до прохождения человеком review/fact-check (см. `review.md`, `fact-check.md`).

- Три вопроса канала: как подключаемся (пулы), чем говорим (SQL/ORM/процедуры), как защищаемся (инъекции, секреты, роли)

## Слайд 3. Learning Objectives

- Предотвращать SQL-инъекции: prepared statements + whitelist
- Проектировать least-privilege роли и контур секретов
- Использовать инструменты класса DBeaver/DataGrip для анализа схемы

## Слайд 4. План занятия

## Слайд 5. Hook: два инцидента на одном канале

- «Один ввод уложил базу»: строка поиска склеивала SQL с пользовательским текстом → чужие данные [учебный пример]
- «Тихий деградант»: ORM-листинг сделал ~1+N round-trip; маленький пул превратился в очередь в час пик [оценки требуют проверки]
- Вопрос: что дороже — дыра безопасности или неэффективный запрос? Кто отвечает за оба?

## Слайд 6. Клиент-серверная модель: запрос стоит денег (Д1)

- СУБД — сервер: TCP + авторизация + разбор запроса = фиксированная плата на обращение
- Connection String: адрес, база, креды, опции — конфигурация окружения, не константа кода
- Полиглотный стек Л4 = несколько connection string: по одному на хранилище

## Слайд 7. Пул соединений: зачем

- Переиспользование открытых соединений убирает стоимость handshake с горячего пути
- Рабочая модель: взять соединение → выполнить → вернуть
- Без пула каждый запрос платит установку и авторизацию заново

## Слайд 8. Trade-off размера пула (Д2)

- Мало: очередь за соединением → latency растёт раньше, чем нагрузка БД
- Много: конкуренция за ресурсы сервера, исчерпание лимита подключений
- Ориентир рассуждения: сумма пулов всех инстансов ≤ разумный предел сервера [эмпирика — требуется проверка]
- Горизонтальное масштабирование приложения линейно умножает соединения (мостик к Л8)

## Слайд 9. Три способа доступа (Д7)

- Raw SQL: полный контроль плана; цена — ручное сопровождение, диалекты, дисциплина защиты
- ORM: скорость CRUD и переносимость; цена — импеданс-мисматч и скрытые запросы
- Хранимые процедуры: один вызов вместо многих round-trip; цена — привязка к движку, сложный versioning
- Нет идеологии «везде X» — выбор по контексту фиксируется в ADR

## Слайд 10. Impedance Mismatch простыми словами

- Объекты приложения (графы, ссылки) ≠ таблицы БД (строки, ключи)
- ORM переводит с одного языка на другой — перевод не бесплатен
- Следствие для менеджера: удобство кода ≠ эффективность канала; нужны наблюдаемость и стандарты

## Слайд 11. N+1: видеть невидимое (Д3)

- Механизм: 1 запрос на список + N запросов на детали (ленивая загрузка)
- Диагностика: счётчик запросов на операцию + лог SQL в dev-среде
- Лечение: join-дозагрузка → батчинг → денормализованная проекция (Л3) → read-model (Л4)
- Метрика в бэклог качества: «число запросов к БД на пользовательскую операцию»

## Слайд 12. SQL-инъекция: механика и защита (Д4)

- Причина: пользовательские данные склеены с текстом запроса → меняется его структура
- Prepared statements: план компилируется до подстановки значений — данные никогда не становятся кодом
- Непараметризуемое (ORDER BY, имена таблиц) — только из whitelist
- Экранирование «вручную» — костыль, не линия обороны

## Слайд 13. Least Privilege: матрица ролей (Д4)

- Приложение: DML своих контекстов, без DDL и чужих данных
- Миграции: отдельная роль DDL по регламенту Expand/Contract (Л3)
- Аналитики: read-only к derived stores, SoT напрямую — нет (принцип Л4)
- Поддержка: маскированные представления PII; админ — отдельно, под аудитом
- Каждая лишняя привилегия = радиус взрыва при компрометации

## Слайд 14. Секреты подключения (Д6)

- Пароль в коде/репозитории компрометируется вместе с кодом
- Контур: secret storage (класс Vault) → env процесса → драйвер; TLS к серверу
- Ротация плановая + внеплановая при инциденте; разные креды dev/stage/prod
- Связь с Л4: украденные креды обходят шифрование «в покое» — роли второй эшелон

## Слайд 15. Кейс: карта каналов каршеринга (Д5)

- Booking → OLTP-ядро; Telemetry-ingest → time-series; Search → гео-профиль; Reporting → derived stores
- Fines/Поддержка — контексты практики (выбор студента)
- Каждый канал: профиль нагрузки, свежесть, размер пула, способ доступа, роль

## Слайд 16. Кейс: ADR-010 «Способы доступа»

- Контекст: команда 8 человек, MVP 3 месяца, стек ADR-008
- Решение: гибрид — ORM для CRUD + Raw SQL для критичных операций (перехват машины, гео-запросы, пакетная телеметрия)
- Последствия: два стиля кода, правила code-review, тестирование запросов, portability-оговорки
- Управленческий смысл: отказ от идеологии, осознанная цена

## Слайд 17. Инструменты разработчика и аналитика (Д8)

- Класс средств (DBeaver, DataGrip): навигация по каталогу, метаданные (DDL/ограничения/индексы)
- ER-диаграмма из реальной схемы — сверка «бумага vs прод» против модели Л3
- Лог запросов — диагностика N+1 и «дрейфа схемы»
- Правило: GUI читает и диагностирует, не правит прод в обход миграций

## Слайд 18. Управленческие выводы: цена решений канала

- Инцидент инъекции — провал процессов (стандарты, ревью), не «баг разработчика»: утечка PII → регуляторика [формулировки — требует проверки], репутация
- Производительность канала — часть SLA: дефекты проявляются в пик, починка дороже планирования
- Метрика «запросов на операцию» — измеримый критерий приёмки горячих сценариев

## Слайд 19. Управленческие выводы: TCO и процессы

- Способ доступа влияет на темп MVP, найм и сопровождение (ADR с Consequences, не мода)
- Секреты и роли — процессы: кто имеет prod-креды, ротация, увольнение сотрудника
- Аудит ролей — периодическая процедура в связке с Data Governance (Л4)

## Слайд 20. Анти-паттерн №1: «Строка-конструктор»

- Симптом: SQL собирается склейкой ввода («мы же экранируем»)
- Последствие: снятие фильтров, чужие данные, ущерб всей базе при широких правах
- Лечение: параметризация + whitelist + least privilege последним рубежом

## Слайд 21. Анти-паттерн №2: «ORM везде» без наблюдаемости

- Симптом: горячий листинг молча делает N round-trip; узнаём в час пик
- Плюс варианты: одна учётка superuser для всего; креды в git; правки схемы через GUI
- Лечение: метрика запросов на операцию, матрица ролей, secret storage, pipeline миграций

## Слайд 22. Мини-практика (аудиторно, в составе Case)

- Для контекста «Штрафы»: 3 строки карты каналов + выбор способа доступа с 2 критериями
- Одна точка ввода: слой защиты; две роли: что можно/нельзя
- Полная версия — practice.md (схема + фрагмент ADR-010 + матрица + чек-лист)

## Слайд 23. Резюме: пять идей

- Канал «приложение ↔ БД» — самостоятельный объект проектирования и ADR
- Пул: торгуем очередь против лимитов сервера
- Доступ: ORM/SQL/процедуры — по контексту, не по моде; N+1 делаем видимым
- Защита: структура запроса неизменна для данных; минимум прав; секреты вне кода
- Инструмент проверяет, что прод совпадает с моделью

## Слайд 25. Мостик к Лекции 6

- Канал построен — но у каждого дома одна стена: единственный узел = единая точка отказа
- Ошибочный DELETE из легитимного канала удалит данные — роли не спасут
- Л6: RPO/RTO, синхронная vs асинхронная репликация, Split-Brain/Quorum, бэкапы и PITR
- Следствие для нас: connection string станет адресом топологии, появится маршрутизация read/write
