## Цель занятия

Спроектировать безопасный и эффективный канал «приложение ↔ СУБД» для стека, выбранного на Лекции 4: понять физику клиент-серверного взаимодействия и пулов соединений, осознанно выбрать способ доступа (Raw SQL / ORM / хранимые процедуры) через trade-offs, распознавать проблему N+1, закрывать поверхность SQL-инъекций подготовленными выражениями, хранить секреты и проектировать роли по принципу наименьших привилегий, использовать инструменты разработчика/аналитика для проверки реальной схемы. Итоговый артефакт — схема взаимодействия приложения с БД учебного кейса + ADR по способу доступа (раздел «Интеграция с БД» Architecture Blueprint).

## Learning Objectives

1. Объясняет клиент-серверную модель работы с БД и назначение пула соединений; формулирует trade-off размера пула.
2. Сравнивает Raw SQL / ORM / хранимые процедуры через trade-offs в контексте; распознаёт импеданс-мисматч и проблему N+1, предлагает методы диагностики и решения.
3. Предотвращает SQL-инъекции подготовленными выражениями и whitelist-подходом; описывает безопасное хранение секретов подключения.
4. Проектирует роли БД по принципу Least Privilege для приложения, миграций, аналитиков и поддержки.
5. Ориентируется в инструментах класса DBeaver/DataGrip: навигация по БД, метаданные, ER-диаграммы из реальной схемы.
6. Фиксирует выбор способа доступа в ADR и оформляет схему взаимодействия с БД как артефакт проекта.

## Hook (5 мин)

Мостик из Лекции 4: «На прошлой неделе каждый контекст каршеринга получил свой „дом“ — транзакционное ядро, хранилище телеметрии, гео-поиск, аналитические копии. Сегодня проводим в эти дома электричество: приложение должно безопасно и быстро разговаривать с каждой СУБД. И именно на этом канале живут два очень дорогих типа инцидентов».

**Эпизод 1 — «один ввод уложил базу».** В приложении каршеринга форма «найти машину по госномеру» собирала SQL склейкой текста: пользовательский ввод подставлялся прямо в запрос. Проверочный ввод вида `' OR '1'='1` [условная учебная история, композитный пример — требует проверки] превратил фильтр в «вернуть всё»: клиент увидел чужие бронирования. Ничего не «упало» — просто перестала работать граница между данными и кодом.

**Эпизод 2 — тихий деградант.** Листинг «машины рядом», собранный через ORM с ленивой загрузкой, при выдаче из ~200 машин сделал примерно 1 + N сетевых round-trip к БД вместо одного JOIN [порядок оценки — требует проверки]. При вечернем пике маленький пул соединений превратился в очередь, и время ответа выросло лавинообразно.

Вопросы аудитории: что дороже — дыра безопасности или неэффективный запрос? Можно ли было обнаружить оба дефекта до продакшена? Какое решение должен был зафиксировать ADR, чтобы они были осознанными, а не случайными?

## Теоретический блок (30 мин)

### Т1. Клиент-серверная модель и параметры подключения (7 мин)

СУБД — сервер: приложение общается с ней по сети, даже если «рядом». Жизненный цикл обращения: установка соединения (TCP), авторизация, отправка запроса, разбор и планирование (parse/plan), исполнение, возврат строк. Первые два шага — фиксированная плата, не зависящая от полезной работы запроса; при «новое соединение на каждый запрос» мы платим её каждый раз.

**Connection String** — именованный набор параметров подключения: адрес хост/порт, имя базы, учётные данные, опции (таймауты, режим TLS, настройки драйвера). Архитектурно важно: это конфигурация окружения, а не константа кода; в полиглотном стеке Л4 их несколько — по одному на хранилище. Состав конкретных параметров зависит от СУБД и драйвера [детализация — требуется проверка по документации выбранного движка].

**Пул соединений** переиспользует готовые соединения: приложение берёт соединение из пула, работает, возвращает. Выигрыш — убираем стоимость установки/авторизации с горячего пути. Trade-off размера: маленький пул → очередь ожидания соединения → рост latency под пиком; большой пул → больше одновременных транзакций на сервере → конкуренция за ресурсы СУБД и исчерпание лимитов сервера (предельные значения зависят от СУБД, конфигурации и нагрузки — точных цифр не даём). Классическая ошибка — «пул на каждый микросервис без учёта суммарного лимита сервера»: сумма пулов всех сервисов не должна превышать разумное число активных подключений СУБД [эмпирические ориентиры — требуется проверка].

Отдельный нюанс: пул — это локальный ресурс процесса приложения; при горизонтальном масштабировании приложения число соединений к БД растёт линейно — скрытая архитектурная связь масштабов (мостик к Л8).

### Т2. Способы доступа: Raw SQL, ORM, хранимые процедуры (8 мин)

Три способа отправить работу СУБД — три профиля цены и риска (уровень WHAT/WHY):

| Критерий | Raw SQL | ORM | Хранимые процедуры |
|---|---|---|---|
| Контроль над запросом/планом | полный | опосредованный (генерируется) | полный, но внутри СУБД |
| Скорость разработки CRUD | ниже | выше (модель уже в объектах) | средняя |
| Переносимость между СУБД | диалекты ограничивают | высокая (абстракция) | низкая (привязка к движку) |
| Поверхность инъекций | выше при небрежном коде | ниже по умолчанию (параметризация из коробки) | ниже, если вход строго параметризован |
| Сетевой трафик/round-trip | один сложный запрос возможен | риск умножения запросов (N+1) | много логики — один вызов вместо многих операций |
| Сопровождение/versioning логики | в коде приложения, CI/миграции Л3 | в коде приложения | внутри СУБД — сложнее версионировать и тестировать [практики различаются — требуется проверка] |

**Impedance Mismatch** (термин глоссария): объектная модель приложения (графы, наследование, ссылки) не совпадает с реляционной (таблицы, ключи) — ORM берёт перевод на себя, и этот перевод не бесплатен.

Как выбирать в контексте: CRUD-домены со стабильной моделью и небольшой командой → ORM ускоряет; сложные аналитические/оптимизированные запросы (гео-поиск, агрегаты телематики) → Raw SQL там, где нужен контроль плана; часто-вызываемая составная операция с несколькими шагами внутри данных → кандидатом может быть хранимая процедура (меньше round-trip), но ценой переносимости. Правильный ответ для кейса — гибрид по контекстам, и он фиксируется в ADR (см. Case).

### Т3. Проблема N+1: диагностика и лечение (5 мин)

Механизм: ORM загружает список родителей одним запросом, а связанных детей — отдельно для каждого родителя, лениво, «когда попросят». Итог: 1 + N запросов там, где достаточно одного JOIN (термин глоссария). Опасность не в количестве запросов как таковом, а в непрозрачности: бизнес-код выглядит как одна строка «получить список», а канал к СУБД умножается на N.

Диагностика (WHAT): счётчик запросов на операцию + лог выполненных SQL-запросов в режиме разработки; ориентир — «сколько round-trip делает страница» как метрика, видимая и менеджеру. Лечение по нарастающей стоимости: eager-loading/join-дозагрузка (один запрос), батчинг (запрос на пачку родителей), денормализованная проекция для тяжёлых листингов (инструмент Л3, под контролем ADR), готовый read-model/derived store (Л4). Выбор метода — снова trade-off: свежесть vs сложность сопровождения копии.

### Т4. Безопасность канала: инъекции, секреты, Least Privilege (8 мин)

**SQL-инъекция** — эксплуатация смешения данных и кода: если пользовательский ввод попадает в *текст* запроса, он может изменить его *структуру*. Иллюстративная схема (не рабочий код): шаблон «... WHERE car_id = » + ввод `' OR '1'='1` превращает фильтр в тавтологию и снимает ограничение выборки. Последствия — чтение чужих данных, изменение, обход проверок; при широких привилегиях учётки — ущерб всей базе, а не одной таблице.

**Подготовленные выражения** (Prepared Statements, термин глоссария) — контракт: разработчик пишет структуру запроса с параметрами-местами, СУБД компилирует план *до* подстановки значений; пользовательские данные никогда не интерпретируются как код. Это базовая защита. Дополнительно: динамические части, которые нельзя параметризовать (имена столбцов сортировки, идентификаторы таблиц), берутся только из белого списка значений, а не из свободного ввода. «Санитайзеры»/экранирование «вручную» — костыли поверх нарушенного контракта, не основная линия защиты.

**Хранение секретов.** Пароль/ключ, зашитые в код или репозиторий, компрометируются вместе с кодом. Контур: секреты живут во внешнем хранилище секретов (Vault и аналоги — примеры класса решений, не стандарт), попадают в процесс как переменные окружения/смонтированные файлы, ротация периодическая и внеплановая при инциденте; отдельные учётные записи для dev/stage/prod. Связь с Л4: украденные креды обходят шифрование «в покое» — доступ идёт через легитимный канал, поэтому least privilege — второй эшелон обороны.

**Least Privilege — проект ролей**, а не одна учётка `app_user`:

| Роль | Разрешено | Запрещено |
|---|---|---|
| Приложение (OLTP-контексты) | DML (SELECT/INSERT/UPDATE) на таблицы своих контекстов | DDL, доступ к чужим контекстам, superuser |
| Миграционный инструмент | DDL по регламенту Expand/Contract (Л3) | ежедневный runtime-доступ |
| Аналитики | read-only к derived stores (Л4) | чтение SoT напрямую, DML |
| Поддержка | маскированные представления PII (связка с токенизацией глоссария) | сырые таблицы клиентов |
| Администрирование | отдельно, под аудитом [требования журналирования доступа к ПДн — требуется проверка по 152-ФЗ/GDPR] | использование приложением |

Каждая лишняя привилегия увеличивает радиус взрыва при компрометации любой точки канала.

### Т5. Инструменты разработчика и аналитика (2 мин)

Класс инструментов (примеры: DBeaver, DataGrip) закрывает разрыв «схема на бумаге vs схема в проде»: навигация по каталогам (базы→схемы→таблицы/представления/процедуры), просмотр метаданных (DDL, ограничения, индексы — проверка физической модели против логической Л3), генерация ER-диаграмм из реальной структуры, построение и запуск запросов с наблюдением количества round-trip (диагностика N+1 из Т3). Предостережение: правки через GUI «на живую» обходят процессы миграций — организационное правило важнее инструмента. Для лабораторных работ курса «Базы данных» этот слой — стандарт рабочего места.

## Case Study (20 мин) — «Каршеринг: канал к четырём домам»

Контекст: стек из ADR-008 (Л4) — OLTP-ядро (Бронирование/Оплата), write-heavy хранилище Телематики, гео-поиск, derived stores аналитики; команда 8 человек, MVP 3 месяца.

**Шаг 1. Инвентаризация каналов (4 мин).** Сервисы × хранилища: Booking-service → OLTP; Telemetry-ingest → time-series (частая запись пакетами); Search-service → гео-профиль; Reporting → только derived stores. Каждый канал получает: тип нагрузки, требуемую свежесть, владельца ролей. Доска Д5.

**Шаг 2. Выбор способа доступа по контекстам + ADR-010 (5 мин).** Бронирование/Оплата: ORM для CRUD + Raw SQL для операции «перехват свободной машины» (атомарная проверка статуса — продолжение шага 4 Л4, где нужен точный контроль запроса). Телеметрия: пакетная вставка без ORM-обвязки (write-heavy, экономия round-trip). Гео-поиск: нативный запрос движка поиска (диалект/расширения — Raw SQL, ORM здесь бессильна) [конкретные возможности движков — требуется проверка]. Итог — черновик **ADR-010 «Способы доступа к хранилищам»**: Context (нагрузки, команда), Decision (гибрид по контекстам), Consequences (два стиля кода, потребность в правилах code-review, тестирование процедур/запросов). Управленческий смысл: отказ от «ORM везде» или «SQL везде» как идеологии.

**Шаг 3. Разбор уязвимого поиска (4 мин).** Форма «поиск по госномеру/городу» — точка входа Hook. План защиты слоями: (1) параметризация всех значений через prepared statements; (2) сортировка/фильтры — из enum-whitelist; (3) роль search-app — SELECT только по нужным представлениям; (4) секреты — из хранилища, ротация; (5) code-review-правило «запрет конкатенации пользовательского ввода в текст SQL» [формулировка стандарта — предмет внутренней политики]. Проверяем: при компрометации учётки — что именно увидит атакующий? Ответ должен быть коротким списком представлений, не всей базой.

**Шаг 4. Пулы и N+1 на листинге «машины рядом» (4 мин).** Считаем round-trip: было 1+N ≈ сотни запросов на страницу; стало 1 (join-дозагрузка) + кешируемая проекция. Размер пула: суммарно по всем инстансам сервиса — меньше разумного лимита сервера; наблюдаемые симптомы малого пула — очередь ожидания соединения растёт раньше, чем CPU БД. Фиксируем как metric-пара для мониторинга (уровень WHAT).

**Шаг 5. Проверка схемы инструментом (3 мин).** В DBeaver/DataGrip-подобном интерфейсе: ER из метаданных OLTP-ядра → сверка с логической моделью Л3 → обнаруживаем «дрейф»: в проде колонка появилась без миграции (организационный анти-паттерн, см. ниже). Действие: вернуть изменения в pipeline миграций.

## Связка с управленческими решениями (15 мин)

Что должен понимать ИТ-менеджер / Product Owner:
- **Инцидент инъекции — это не «баг разработчика», а управленческий провал:** отсутствие стандартов доступа к БД и code-review-правила. Цена: утечка PII → регуляторные уведомления и штрафы (масштабы санкций GDPR/152-ФЗ — [точные формулировки и суммы — требуется проверка]), репутация, простой на разбирательство. Профилактика дешевле: параметризация как обязательный стандарт + least privilege как страховка.
- **Производительность канала — часть SLA продукта.** Дефекты N+1 и пулов проявляются именно в пик нагрузки (худшее время), а починка «на лету» дороже планирования. Практическая метрика для бэклога качества: «число запросов к БД на пользовательскую операцию» — измеримый критерий приёмки для горячих сценариев.
- **Выбор способа доступа влияет на TCO и найм:** ORM ускоряет MVP малой команды (наш кейс: 8 человек, 3 месяца), но требует компетенции диагностики скрытых запросов; хранимые процедуры концентрируют логику в СУБД — быстрее конкретная операция, медленнее эволюция схемы и сложнее versioning. Решение — ADR с consequences, а не мода.
- **Секреты и роли — вопрос процессов, а не инструментов:** кто имеет доступ к prod-кредам, как часто ротируются, что происходит при увольнении сотрудника. Аудит ролей — периодическая управленческая процедура, связанная с Data Governance из Л4.
- **Мини-голосование аудитории (часть блока):** принять ли ADR-010 в текущем виде или потребовать «ORM везде»? Обсуждение последствий обоих вариантов.

## Ключевые термины

- **Connection String** — именованный набор параметров подключения к СУБД (адрес, база, креды, опции); конфигурация окружения, не код.
- **Пул соединений** — механизм переиспользования открытых соединений к СУБД; размер — trade-off между очередью ожидания и нагрузкой на сервер.
- **Raw SQL** — прямое выполнение SQL-запросов из приложения без слоя маппинга.
- **ORM** — технология сопоставления объектов приложения с таблицами БД (примеры: SQLAlchemy, Hibernate).
- **Impedance Mismatch** — несоответствие объектной и реляционной моделей (термин глоссария).
- **N+1 проблема** — 1 запрос на список + N запросов на детали вместо одного JOIN (термин глоссария).
- **Хранимая процедура** — процедура, исполняемая на стороне СУБД; сокращает round-trip, связывает логику с движком.
- **SQL-инъекция** — атака через подстановку пользовательских данных в текст запроса, меняющая его структуру.
- **Prepared Statements** — подготовка плана запроса до подстановки параметров; основная защита от инъекций (термин глоссария).
- **Secret management / Vault** — класс решений централизованного хранения и ротации секретов (пример названия — HashiCorp Vault).
- **Least Privilege** — принцип наименьших привилегий: каждая роль получает минимум прав для своей задачи.
- **Метаданные / каталог СУБД** — данные о структуре базы (таблицы, колонки, ограничения, индексы); основа навигации и ER-диаграмм в инструментах.

## Anti-patterns

1. **«Строка-конструктор»**: сбор SQL конкатенацией пользовательского ввода (включая «мы же экранируем»). Правильно: параметризация + whitelist динамических частей + least privilege как последний рубеж.
2. **«ORM везде, потому что удобно»** без контроля скрытых запросов: горячий листинг молча делает N round-trip, а команда узнаёт об этом в час пик. Правильно: метрика «запросов на операцию» для критичных сценариев + диагностика инструментами.
3. **«Одна учётка со всеми правами для всего»**: приложение, миграции, аналитики и поддержка под одним superuser — максимальный радиус взрыва и нет разделения ответственности. Правильно: матрица ролей из Т4.
4. **«Пароль в конфиге в git»**: секрет в репозитории/артефакте — компрометация при любой утечке кода. Правильно: secret storage → env, ротация, отдельные креды окружений.
5. **«Правки схемы через GUI на проде»**: обход миграций (Л3) → дрейф схемы, неработоспособные environment parity. Правильно: только pipeline миграций, GUI — для чтения/диагностики.

## Мостик к следующей лекции

Мы построили канал: приложение умеет безопасно и эффективно говорить с *каждым* домом из стека Л4. Но пока у каждого дома одна стена: если единственный узел OLTP-ядра сгорит ночью — бронирований не будет до утра, а ошибочный `DELETE` из нашего же легитимного канала удалит историю платежей. Канал надёжен — данные ещё нет.

**Лекция 6** («Надежность данных: репликация, резервное копирование и восстановление») отвечает на вопросы: типы сбоев и метрики RPO/RTO; синхронная vs асинхронная репликация и Replication Lag (прямое продолжение PACELC из Л4); Split-Brain и quorum; стратегии бэкапов и Point-in-Time Recovery. Для сегодняшней темы следствие: connection string превращается из адреса одной машины в адрес топологии, а маршрутизация read/write добавляет новые trade-offs свежести (read-your-writes из Л4).
