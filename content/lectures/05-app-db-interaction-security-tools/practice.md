# Практика к лекции 5

## Цель практики

Отработать навык проектирования канала «приложение ↔ СУБД»: составить схему взаимодействия сервиса с выбранным хранилищем (параметры подключения, пулы), обосновать выбор способа доступа (ORM vs Raw SQL vs хранимая процедура) через trade-offs, построить план защиты от SQL-инъекций и матрицу least-privilege ролей. Артефакты: схема взаимодействия с БД + фрагмент ADR-010 — раздел «Интеграция с БД» итогового Architecture Blueprint (module-map, Лекция 5).

## Кейс

Сервис каршеринга из сквозного проекта (параметры — в `case.md`). Развёрнутая версия кейса с участниками и ограничениями — `content/lectures/05-app-db-interaction-security-tools/case.md`. Для самостоятельной работы каждый студент берёт **один контекст по жребию/выбору**: «Штрафы» (основной вариант, согласован с Hook лекции) или «Поддержка».

## Входные данные

- Логическая модель выбранного контекста в 3НФ (артефакт Лекции 3);
- Класс СУБД для контекста и профиль согласованности (ADR-008, Лекция 4);
- NFR по latency/доступности горячих сценариев (Architecture Brief, Лекции 1–2);
- PII-стратегия и субъекты доступа (Лекция 4);
- Перечень точек ввода пользовательских данных в сервисе (формулируются студентом по сценариям Event Storming, Лекция 2).

## Задание

1. **Анализ профиля канала.** Опишите операции контекста (чтение/запись/агрегаты), ожидаемую частоту [оценки — «примерно», допустимы любые разумные при обосновании], требования свежести; заполните строку карты каналов «сервис × хранилище».
2. **Выявление проблемных зон прототипа.** Найдите в описании все точки, где пользовательский ввод попадает в запрос; отметьте потенциальные места N+1 (списки с деталями); зафиксируйте текущие дефекты секретов/ролей как риски.
3. **Проектирование решения.** Выберите способ доступа для каждой группы операций с обоснованием через минимум два критерия trade-off таблицы Д7; задайте параметры подключения на уровне классов (что конфигурация окружения, что — код) и политику пула (обоснуйте размер связью с лимитами сервера и числом инстансов).
4. **План защиты.** По каждой точке ввода: параметризация / whitelist / валидация типа; контур секретов (хранилище → env, ротация); матрица least-privilege ролей (субъекты: приложение, миграции, аналитики, поддержка).
5. **Инструментальная сверка.** Составьте чек-лист проверки реальной схемы в инструменте класса DBeaver против модели Л3 (не менее 5 пунктов).
6. **Оформление артефакта.** Соберите схему взаимодействия + ADR-010 по шаблонам ниже.

**Ожидаемый результат:** «Схема взаимодействия приложения с БД (контекст …)» + ADR-010 (фрагмент) + матрица ролей + чек-лист сверки.

## Критерии оценки

| Критерий | Вес | Описание |
|----------|-----|----------|
| Полнота анализа | 20% | Карта каналов, точки ввода, места N+1, дефекты секретов/ролей — все найдены |
| Обоснованность решений | 30% | Выбор способа доступа через ≥2 trade-off-критерия; размер пула связан с лимитами; ADR содержит Consequences |
| Соответствие ограничениям | 20% | Учёт MVP-сроков, команды 8 человек, бюджета, PII-стратегии Л4 |
| Качество артефакта | 20% | Таблицы читаемы, ADR по формату Л1, чек-лист конкретен |
| Связь с бизнес-целями | 10% | Метрика «запросов на операцию» и снижение радиуса компрометации привязаны к NFR/рискам |

## Подсказки (для преподавателя / самопроверки)

- Направления диагностики N+1 и лечения — блок Т3 draft.md; сравнение способов доступа — таблица Т2 и диаграмма Д7.
- Слои защиты от инъекций — Т4; типичная ошибка «экранирование вместо параметризации» — анти-паттерн №1.
- Чек-лист сверки схемы опирается на `knowledge/data-modeling/conceptual-logical-physical.md` и `keys-constraints.md`.
- Формат ADR — `knowledge/system-design/ADR.md`; торговля критериями — `trade-offs.md`, приоритеты — `nfr.md`.

## Типичные ошибки студентов

1. «ORM везде» без анализа горячих списков → пропущенный N+1 в задании.
2. Размер пула «100» без связи с числом инстансов и лимитом сервера.
3. План защиты = «валидация ввода» без параметризации (перепутаны слои).
4. Одна роль `app_user` для всех субъектов; аналитик читает SoT напрямую (нарушение принципа Л4).
5. Секрет «в переменных окружения», но значение закоммичено в `.env.example`/README.
6. ADR без Consequences — решение без цены.
