# План (Outline) Лекции 5 — «Взаимодействие приложений с СУБД, уязвимости и инструменты разработчика»

## Цель занятия
Спроектировать безопасный и эффективный канал «приложение ↔ СУБД» для стека, выбранного на Лекции 4: понять физику клиент-серверного взаимодействия и пулов соединений, осознанно выбрать способ доступа (Raw SQL / ORM / хранимые процедуры) через trade-offs, научиться видеть проблему N+1, закрывать поверхность SQL-инъекций подготовленными выражениями, хранить секреты и роли по принципу наименьших привилегий, и использовать инструменты разработчика/аналитика для проверки реальной схемы. Итоговый артефакт — схема взаимодействия приложения с БД учебного кейса + ADR по способу доступа.

Общая длительность: **80 минут** (по `specs/content-contracts/lesson-contract.md`).
Формат: лекция-разбор с кейсовым блоком; уровень WHAT/WHY, без production-кода.

## Learning Objectives (к концу занятия студент:)
1. Объясняет клиент-серверную модель работы с БД: издержки соединения на запрос и назначение пула соединений; формулирует trade-off размера пула (очередь vs лимиты сервера).
2. Сравнивает Raw SQL / ORM / хранимые процедуры через trade-offs в контексте (команда, нагрузка, тип запроса); распознаёт импеданс-мисматч и проблему N+1, предлагает методы диагностики и решения на уровне архитектуры.
3. Объясняет механизм SQL-инъекции и предотвращает её подготовленными выражениями и whitelist-подходом к динамическим частям запроса; описывает контур хранения секретов подключения (env + secret storage, ротация).
4. Проектирует роли БД по принципу Least Privilege для приложения, миграций, аналитиков и поддержки (связка с PII-стратегией Л4).
5. Ориентируется в инструментах разработчика/аналитика (DBeaver, DataGrip — примеры): навигация по БД, метаданные, ER-диаграммы из реальной схемы; использует их для проверки соответствия физической модели логической (Л3) и матрице выбора (Л4).
6. Фиксирует выбор способа доступа в ADR (формат из Л1) и оформляет схему взаимодействия приложения с БД как артефакт Architecture Blueprint.

*Соответствие acceptance criteria spec:* LO1↔AC1, LO2↔AC2, LO3↔AC3, LO4↔AC4, LO5↔AC5, LO6 — интеграция артефакта (module-map).

## Последовательность блоков и переходы
- Hook → Т1: «оба эпизода истории живут на одном слое — канале приложение↔СУБД; начнём с его физики».
- Т1 → Т2: «соединение дешёвое благодаря пулу — теперь выбираем, чем именно по нему слать».
- Т2 → Т3: «ORM удобен, но скрытно умножает запросы — научимся видеть невидимое».
- Т3 → Т4: «увидели лишние запросы — убедимся, что нужные безопасны».
- Т4 → Т5: «все перечисленные проблемы диагностируются инструментами — покажем класс средств».
- Т5 → Case: применяем всё к стеку Л4.

## Визуальные материалы (создаются в diagrams.md)
- Д1: sequence «жизнь одного запроса» (TCP → auth → parse → execute → fetch).
- Д2: схема пула соединений (app workers ↔ pool ↔ server limit).
- Д3: граф запросов N+1 vs JOIN (два дерева).
- Д4: концентрические круги радиуса взрыва SQL-инъекции + матрица least-privilege ролей.
- Д5: карта каналов кейса (сервисы × хранилища АDR-008).
- Д6: flow «секрет из vault → env → драйвер» (без значений).
- Д7: таблица-обобщение «способ доступа × критерии» (для слайдов).
- Д8: скриншот-заместитель окна инструмента с подписями зон (навигация/метаданные/ER) [схематично, без реальных изображений].

## Принципы качества
- Каждое утверждение о производительности — с маркером «примерно/зависит от нагрузки»; конкретные лимиты — [требуется проверка].
- Технологии (Vault, SQLAlchemy, Hibernate, DBeaver, DataGrip) — примеры классов решений.
- Термины сверены с `knowledge/glossary.md`; новые — предложения в generation-report.
- Никаких рабочих эксплойтов; инъекция объясняется механизмом, не инструкцией.
