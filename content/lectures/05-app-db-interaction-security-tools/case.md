# Кейс: Каршеринг — канал к четырём домам (Лекция 5)

## Контекст
Сервис каршеринга из сквозного проекта курса (~200 автомобилей, 3 города, MVP за 3 месяца, команда 8 человек). На Лекции 4 по ADR-008 каждый контекст получил своё хранилище: OLTP-ядро для Бронирования и Оплаты, write-heavy хранилище Телематики, гео-поисковый профиль для поиска свободных машин, derived stores для аналитики. Модели данных спроектированы в 3НФ на Лекции 3. Приложение пока не подключено к новому стеку: канал «сервисы ↔ СУБД» нужно спроектировать с нуля. Команда бэкенда небольшая: 8 человек, разнородный опыт работы с БД; жёсткий срок MVP.

## Бизнес-цель
Подключить сервисы к выбранным хранилищам так, чтобы: (а) горячие пользовательские сценарии («найти машину рядом», «забронировать») укладывались в целевые NFR по latency из Лекций 1–2 [конкретные значения SLO — взять из артефакта Architecture Brief студента]; (б) ни одна точка ввода пользовательских данных не создавала поверхность SQL-инъекций; (в) компрометация любой одной учётной записи не давала доступа ко всей базе. Измеримые критерии успеха: число запросов к БД на операцию листинга ограничено константой (не растёт с размером выдачи); матрица ролей согласована с DPO; стандарт доступа зафиксирован в ADR до начала активной фазы разработки.

## Участники
- **Заказчик:** операционный директор каршеринга — интерес: стабильность часа пик и отсутствие скандалов с утечками данных.
- **Пользователи:** клиенты приложения (поиск/бронирование), внутренняя поддержка (работа с обращениями), аналитики отчётности.
- **Команда разработки:** 8 человек (backend/mobile/QA); часть не имеет опыта диагностики скрытых запросов ORM; один инженер «верит только в хранимые процедуры».
- **Стейкхолдеры:** DPO (персональные данные), финансовый контролёр (платежи и штрафы), DBA будущего продакшена (будет эксплуатировать то, что спроектировано сегодня — связь с курсом «Базы данных»).

## Текущая проблема
Прототип мобильной версии демонстрирует обе беды канала: форма «найти машину по госномеру» собирает SQL конкатенацией пользовательского ввода, а листинг «машины рядом» через ORM с ленивой загрузкой умножает сетевые round-trip на размер выдачи [учебная постановка, параметры — требует проверки]. Кроме того, пулы нигде не настроены — соединения открываются на запрос. Отдельно: креды прототипа лежат в файле конфигурации в репозитории, а все субъекты (приложение, ноутбук аналитика, скрипты поддержки) используют одну учётную запись с широкими правами. Проект находится на пороге: либо эти решения принимаются сейчас как архитектура (ADR), либо становятся наследием инцидентов.

## Ограничения
- **Бюджет:** облачная инфраструктура MVP без выделенных middleware-продуктов класса коммерческого прокси [альтернативы open-source — обсуждаются]; секреты — доступное решение класса secret storage или эквивалентный процесс [выбор — требуется проверка на этапе закупки].
- **Время:** MVP за 3 месяца; активная фаза разработки начинается со следующей недели — стандарты доступа должны быть приняты до первого релиза.
- **Технологии:** стек хранилищ зафиксирован ADR-008 (Л4); языки/фреймворки сервиса — на усмотрение команды; инструменты разработчика (класс DBeaver/DataGrip) должны быть едины для команды и лабораторий курса.
- **Комплаенс:** PII-стратегия Л4 (клиенты, документы, треки поездок) распространяется на роли и маскирование; требования к журналированию доступа к ПДн [формулировки 152-ФЗ/GDPR — требуется проверка юристом].

## Архитектурный вопрос
Как спроектировать канал взаимодействия каждого сервиса с каждым хранилищем (параметры подключения, пулы, способ доступа, защита, роли), чтобы решения были осознанными, различимыми по контекстам и фиксируемыми в ADR — а не унаследованными от привычек прототипа?

## Ожидаемое решение
Общий контур (без готового ответа): карта каналов «сервис × хранилище» с профилем нагрузки и свежестью; выбор способа доступа по каждому контексту через trade-offs (ORM / Raw SQL / хранимая процедура — допустимы разные ответы при обосновании); план защиты точек ввода (параметризация значений + whitelist динамических частей) и контур секретов (хранилище → env, ротация); матрица least-privilege ролей по субъектам; чек-лист проверки реальной схемы инструментом против модели Л3. Обязателен фрагмент ADR-010 с Consequences. Оценивается качество аргументации и связность с NFR/бюджетом/командой, а не «правильность» конкретной технологии.

## Артефакты для студентов
1. Схема взаимодействия приложения с БД (диаграмма каналов + таблица параметров по хранилищам).
2. ADR-010 «Способы доступа к хранилищам» (Context/Decision/Consequences).
3. План защиты от инъекций: перечень точек ввода пользователя и мер по каждой.
4. Матрица least-privilege ролей (субъект × объект × тип операции).
5. Чек-лист инструментальной сверки схемы (проде vs модель Л3).

## Вопросы для обсуждения
1. Почему для «перехвата свободной машины» (операция из шага 4 Л4) мог бы подойти Raw SQL, а не ORM? Что мы теряем, выбирая наоборот?
2. Если атакующий скомпрометировал учётку Booking-service — что он сможет сделать при нашей матрице ролей и чего не сможет? Кто отвечает за этот ответ?
3. Как измерить «стоимость» N+1 менеджеру до инцидента? Какая метрика попадает в бэклог качества?
4. Хранимая процедура ускоряет составную операцию, но усложняет эволюцию схемы (Л3). При каком изменении бизнес-требований наше решение о процедурах придётся пересматривать первым?
5. Как топология репликации из Лекции 6 изменит наши connection string и пулы? Какие решения сегодняшнего дня сделают этот переход дешёвым?

## Связь с другими лекциями
- Л4: вход — ADR-008, SoT/derived, PII-стратегия; выход — маршрутизация read/write.
- Л3: логическая модель как объект CRUD и эталон для инструментальной сверки; Expand/Contract для роли миграций.
- Л6: надёжность канала перестаёт зависеть от одного узла; connection string → адрес топологии.
- Л7/Л8: паттерны CQRS/Event Sourcing (Л7) используют те же каналы; метрики «запросов на операцию» пригодятся при шардировании и кэшировании (Л8).
