# Лекция 6. Надежность данных: репликация, резервное копирование и восстановление

> Статус: draft (черновик; review/fact-check человеком не проводились). Spec: `specs/lessons/lesson-06.spec.md`. Тема и тайминг — по `specs/syllabus.md` и `specs/content-contracts/lesson-contract.md` (80 мин).

## Цель занятия

Научиться проектировать отказоустойчивые системы хранения данных с учётом метрик RPO и RTO: выбирать тип и топологию репликации, строить политику резервного копирования и описывать процедуру восстановления, включая Point-in-Time Recovery.

## Learning Objectives

1. Классифицировать типы сбоев и сопоставлять каждый класс с адекватным методом защиты (HA vs DR).
2. Выбирать тип репликации через trade-offs «лаг ↔ консистентность ↔ латентность записи» и объяснять Split-Brain / Quorum.
3. Конструировать политику бэкапов (Full / Incremental / Differential / снапшоты + WAL) под заданные RPO/RTO.
4. Описывать процедуру восстановления, включая PITR, и обосновывать регулярные учения.
5. Обосновывать целевые RPO/RTO бизнес-требованиями из Лекций 1–2.

*(Соответствуют acceptance criteria спеки и блоку 6 learning-outcomes.)*

## Hook (5 мин)

Команда каршеринга из нашего сквозного кейса отчиталась руководству: «Отказоустойчивость обеспечена — два узла БД в режиме master-master, бэкап каждую ночь». Наступает обычный вторник:

1. **14:03.** Канал между двумя площадками мигает 40 секунд. Оба узла объявляют себя master. В городе А бронь оформлена на узле 1, в городе Б — на узле 2; после восстановления канала «правды» расходятся: два клиента считают один автомобиль занятым собой.
2. **14:31.** Стажёр запускает скрипт «миграции» с удалённым `WHERE`. История поездок за квартал исчезает. Реплики послушно копируют удаление — обе.
3. **15:00.** Вспомнили про ночной бэкап. Он лежит в том же дата-центре. Восстанавливаться им пробовали ровно никогда. Сколько займёт подъём — неизвестно; данные всё равно вчерашние: сутки изменений потеряны.

Три вопроса аудитории: (а) какой из трёх инцидентов вообще можно было предотвратить архитектурой, а какой только ограничить по последствиям? (б) чего не хватило — железа или метрик? (в) как согласованные заранее RPO/RTO изменили бы проект до вторника? Мораль Hook: **отказоустойчивость без измеренных целей — это купленное железо, а не надёжность**.

## Теоретический блок (30 мин)

### 1. Типы сбоев и концепция надёжности данных (5 мин)

Надёжность данных (Data Reliability) отвечает на два разных вопроса, которые часто путают:
- **Будут ли данные доступны?** (Availability → HA: репликация, failover)
- **Будут ли данные целы и восстановимы?** (Durability/Recoverability → DR: бэкапы, PITR)

| Класс сбоя | Пример | От чего защищает | От чего НЕ защищает |
|---|---|---|---|
| Аппаратный | умер диск/узел | репликация + автоматический failover | распространённая ошибка ПО, corruption |
| Программный | баг приложения записал мусор | ограничения/валидация (Л3), PITR-откат | — |
| Человеческий фактор | DROP TABLE без WHERE | бэкапы + PITR, least privilege (Л5) | репликация — нет: она реплицирует ошибку |
| Катастрофа площадки | пожар в ДЦ, недоступен регион | гео-репликация + копии в другом регионе (3-2-1) | — |
| Сетевое разбиение | порван канал между ЦОД | quorum/fencing при выборе нового primary | сам раздел никуда не денется — это CAP-выбор (Л4) |
| Злонамеренный | шифровальщик | изолированные неизменяемые копии, KMS-гигиена | «плоская» сеть прод=бэкап |

Ключевой вывод: **ни один механизм не покрывает все классы**. Синхронная репликация не спасёт от стажёра с DROP TABLE; идеальный бэкап не даст доступности в момент сбоя. Архитектор комбинирует слои, исходя из классификации рисков.

### 2. RPO и RTO: бизнес-метрики, а не технические настройки (5 мин)

- **RPO (Recovery Point Objective)** — максимальный объём потери данных во времени, который бизнес готов принять («как далеко назад мы можем потерять правду»). Определяет частоту/непрерывность копирования: RPO = 1 час → минимум часовые копии; RPO ≈ 0 → синхронная/кворумная репликация.
- **RTO (Recovery Time Objective)** — максимальное время простоя до восстановления сервиса («сколько часов бизнес может жить без системы»). Определяет степень готовности резерва: тёплый standby поднимается быстрее, подъём с холодных бэкапов — медленнее; важен и размер данных, и отработанность процедуры.

Обе метрики выводятся из NFR и цены простоя, собранных на Лекциях 1–2 (пример целевых значений из `knowledge/system-design/nfr.md`: RPO < 1 часа, RTO < 30 минут — для учебного профиля; [для реального проекта — требуется проверка и подписание бизнесом]). Графически: на таймлайне «сбой → детект → переключение → восстановление» RPO — горизонтальный отрезок «потерянных» изменений до момента сбоя, RTO — вертикальный отрезок недоступности после него (диаграмма Д3).

Важное следствие: **разные контексты одной системы имеют разные RPO/RTO**. Для каршеринга потеря минуты броней дороже, чем потеря часа телеметрии (её можно частично восстановить с бортовых буферов — [допущение, требует проверки на этапе MVP]); аналитическое хранилище может иметь RTO в часы без боли для клиента. Дифференциация метрик — источник экономии TCO (см. управленческий блок).

### 3. Репликация: типы, топологии, read replicas (8 мин)

Репликация (глоссарий) — копирование данных с primary на реплики. По модели подтверждения записи:

| Тип | Гарантия | Цена | Когда уместен |
|---|---|---|---|
| Синхронная | транзакция подтверждается после записи на реплику — при сбое primary данные не теряются (RPO≈0 для этого каскада) | рост latency каждой записи; при недоступности синхронной реплики primary может остановить запись (цена доступности!) | финансовое ядро, критичные брони — там, где потеря транзакции неприемлема |
| Полусинхронная | подтверждение после получения репликой (не обязательно применения) — компромисс | промежуточная гарантия зависит от реализации [детали — по конкретной СУБД, требует проверки] | баланс для write-heavy с умеренными рисками |
| Асинхронная | commit сразу; реплика догоняет фоном | Replication Lag = потенциальные потерянные изменения при сбое; чтения с реплики могут быть устаревшими | телеметрия, отчётность, гео-копии, derived stores |

Это дословно PACELC из Лекции 4, ставшее инженерной настройкой: E (штатный режим) — платим L (latency записи) за C (гарантию); P (раздел сети) — выбираем A или C.

Топологии (уровень WHAT, схемы Д2):
- **Primary–Replica (Master-Slave):** один пишет, многие читают; самый простой и предсказуемый вариант; failover = промоушение реплики.
- **Multi-Primary (Master-Master):** пишут несколько узлов; выше доступность записи, но конфликты разрешения и риск расходящихся состояний — например Galera/CockroachDB как примеры класса [поведение при разделах различается — требует проверки по версиям].
- **Cascading:** реплика реплицирует реплику — снижает нагрузку на primary, увеличивает lag конечных узлов.

**Read replicas** разгружают primary от чтений (отчёты, поиск, «backup с реплики не трогает прод»), но: (а) lag делает чтение устаревшим — нарушение read-your-writes для пользовательских сценариев «записал—сразу вижу»; (б) маршрутизация «какие запросы куда» — архитектурное решение уровня приложения (перекликается с Лекцией 5), фиксируется в ADR. Правило большого пальца: пишем в primary, читаем с реплики только там, где допускается lag; свежее чтение своей операции — всегда с primary.

### 4. Failover, Split-Brain, Quorum (5 мин)

Failover — переключение на резервный узел. Виды: автоматический (система сама; требует health checks и консенсуса), ручной (контроль, но время реакции = человек), полуавтоматический (обнаружила — подтвердил оператор).

Автоматизация имеет цену. Если решение «primary умер» принимается парой узлов без арбитра, при сетевом разделе оба считают друг друга мёртвыми и оба становятся master — **Split-Brain** (глоссарий): две расходящиеся правды, позднее слияние которых превращается в потерю данных или двойные брони (Hook, эпизод 1). Защиты:
- **Quorum (N/2+1):** новый master выбирается только большинством голосов — поэтому нечётное число участников (3, 5) принципиально; два узла без свидетеля не имеют большинства и обязаны остановиться на записи (лучше недоступность, чем две правды — CP-позиция из Л4).
- **Witness-узел (свидетель):** дешёвый арбитр без данных, дающий нечётность.
- **Fencing/STONITH:** «изолировать» сомнительный узел (забрать у него право писать) перед промоушением [точный механизм зависит от платформы — требует проверки].

Health checks следят за TCP-доступностью, временем ответа запросов и Replication Lag — последний важен: промоушать сильно отстающую реплику = добровольно выбросить хвост изменений (увеличить фактический RPO).

### 5. Стратегии резервного копирования (5 мин)

Типы (схема Д4):
- **Full** — копия всей БД: простое восстановление (одна копия), дорогой по объёму/времени создания.
- **Incremental** — изменения с момента последнего любого бэкапа: дёшев, но восстановление = full + вся цепочка incrementals (чем дальше от full, тем дольше и хрупче).
- **Differential** — изменения с момента последнего full: дороже incremental, но восстановление = full + последний differential (короче путь подъёма).
- **Снапшоты** (глоссарий) — мгновенные копии уровня дисковой подсистемы: быстрые, но привязаны к инфраструктуре и обычно живут рядом с продом (риск общей катастрофы).
- **WAL/Transaction Log Backup** — архивация журнала предзаписи (WAL из ACID-блока Л4): непрерывный поток изменений поверх полных копий — фундамент PITR.

Политика строится **от RPO**, а не от удобства: частота копирования ≤ допустимой потери. Хранение — правило **3-2-1**: 3 копии, 2 разных носителя, 1 вне площадки (другой регион/облако). Retention определяется комплаенсом и здравым смыслом (пример учебной политики: daily 30 дней, weekly год, monthly 7 лет для финансовых артефактов [нормативные сроки хранения для конкретного бизнеса — требует проверки юристом]). Связь с Лекцией 4: бэкапы содержат PII — значит, стратегия Data Governance распространяется на копии: шифрование at rest, крипто-шреддинг (удаление ключа KMS делает все копии с этим фрагментом нечитаемыми) обязан покрывать бэкап-хранилище, иначе «право на удаление» выполняется лишь частично.

### 6. Восстановление и PITR (2 мин)

Процедура восстановления — документированный сценарий: оценка ущерба → выбор точки восстановления → подъём копии → применение WAL до момента t−ε (перед ошибкой) → проверка целостности → включение трафика. **Point-in-Time Recovery** (глоссарий) — именно «подъём на момент»: full + WAL-архив дают машину времени; спасает от человеческих ошибок, которые репликация честно скопировала бы.

Два железных правила из `db-reliability.md`: **(1) бэкап без теста восстановления бесполезен** — регулярные DR-учения (восстановление копии в тестовую среду, замер фактического времени подъёма против RTO); **(2) процедура и время восстановления документируются** — невыполненный RTO выясняется только в бою, а бой не место для первого rehearsal.

## Case Study (20 мин) — «Каршеринг: план выживания для каждого контекста»

Вход: стек ADR-008 из Лекции 4 (реляционное OLTP-ядро «Бронирование/Оплата», time-series телеметрия, derived stores поиска/аналитики, crypto-shredding для PII), NFR и цена простоя из Лекций 1–2, команда 8 человек, бюджет MVP.

### Шаг 1. Дифференциация RPO/RTO по контекстам (5 мин)
Продукт owner и финансы подписывают таблицу (все значения — учебные оценки, [требуют проверки бизнесом]):

| Контекст | Потеря данных | Простой | Обоснование |
|---|---|---|---|
| Бронирование (OLTP-ядро) | RPO ≤ 1 мин | RTO ≤ 5 мин | двойная бронь/потерянная бронь = прямой конфликт с клиентом |
| Оплата | RPO ≈ 0 | RTO ≤ 15 мин | расхождение с выпиской — бухгалтерский и регуляторный риск |
| Телеметрия | RPO ≤ 15 мин | RTO ≤ 2 ч | бортовые буферы частично догонят; штрафы позже сверяются по фотофиксации [требует проверки] |
| Поиск (derived) | RPO не критичен (rebuild из SoT) | RTO ≤ 30 мин | проекция — перестроим из источника |
| Аналитика (DWH) | RPO ≤ 24 ч | RTO ≤ 8 ч | внутренние отчёты подождут |

Вывод шага: единые «RPO/RTO на всю систему» — анти-паттерн; дифференциация даёт и защиту, и экономию.

### Шаг 2. Репликация ядра (5 мин)
«Оплата + Бронирование» — один реляционный кластер: primary + синхронная реплика в другой зоне того же региона (латентность межзонного канала мала [число миллисекунд — требует измерения]) + асинхронная гео-реплика в другом регионе для DR. Trade-off принят осознанно: локальная синхронность платит ~удвоением сетевых RTT на commit, зато региональный сбой не стоит потерянных транзакций; гео-реплика асинхронна — при потере всего региона платим лаг (минуты) за возможность подняться. Раздел внутри региона → quorum-механизм выбора нового primary; внешний свидетель не нужен (3 узла достаточно для большинства). Multi-master сознательно отвергнут: конфликтующие брони разрешать дороже, чем платить за доступность записи в редком разделе.

### Шаг 3. Телеметрия и derived stores (3 мин)
Time-series-хранение: асинхронная репликация (write-heavy, потери единичных точек телеметрии допустимы — RPO 15 мин покрывается частыми снапшотами/WAL-подобным логом платформы [возможности конкретной СУБД — требует проверки]). Поиск и аналитика — не «бэкапируем», а **перестраиваем из Source of Truth** (CDC-проекция из Л4): их «восстановление» = повторная полная реконструкция индексов; это дешевле и честнее, чем хранить вторые копии производных данных.

### Шаг 4. Политика бэкапов и PITR ядра (4 мин)
Для OLTP-ядра: еженедельный full (снапшот volume) + ежедневные differential + непрерывная WAL-архивация в объектное хранилище другого региона (3-2-1 выполнен: прод-узел + реплика + копия вне региона, разные сервисы хранения). Точка PITR выбирается перед ошибочной транзакцией; восстановление идёт на изолированный стенд, проверяется контрольными суммами заказов, только затем становится новым primary. Бэкап снимается с реплики (не нагружает primary). PII-слой: копии шифрованы, персональные ключи — в KMS; отзыв согласия клиента → crypto-shredding применяется ко всем копиям, включая бэкап-хранилище (связка с Л4).

### Шаг 5. Фиксация — ADR-011 (3 мин)
Черновик **ADR-011 «Стратегия репликации и восстановления»**: Context (таблица RPO/RTO шага 1), Decision (шаги 2–4), Consequences (плата: latency commit в ядре, стоимость гео-копий, обязательные квартальные DR-учения, операционная сложность Patroni-подобного стека [экспертиза команды 8 человек — риск, требует оценки]).

## Связка с управленческими решениями (15 мин, интегрировано; итоговый разбор)

- **Каждое сокращение RPO/RTO имеет цену.** Переход от асинхронной к синхронной реплике — это постоянный налог на latency каждой записи и дополнительные узлы; переход от суточного бэкапа к WAL-архивации — хранилище и эксплуатация. Решение «RPO = 0 везде» экономически несостоятельно; таблица дифференциации шага 1 — инструмент торга с продуктом: «минута для оплат, 15 минут для телеметрии».
- **SLA рождает обязательства.** Если договор с корпоративными клиентами обещает доступность 99,9% [значения из Л1 — уточнить], RTO должен следовать из контракта, а не из удобства инженеров; невыполнимый RTO = юридические и репутационные риски.
- **Непроверенный DR — скрытый убыток.** Стоимость учения восстановления измеряется часами инженеров; стоимость «первого реального восстановления» — часами простоя и штрафами. Регулярные rehearsal — страховая премия, планируйте её в бюджете эксплуатации (TCO из Л4).
- **Комплаенс переезжает в копии.** GDPR/152-ФЗ (Л4) применяются к бэкапам: retention, шифрование, crypto-shredding вне региона порождает вопрос data residency копий [юридическая оценка — требует проверки]. Это архитектурное ограничение при выборе облака.
- **Передача DBA.** Итоговая таблица «контекст → RPO/RTO → топология → политика» — прямое ТЗ для администраторов БД следующего семестра: архитектор задаёт цели и границы, DBA выбирает средства реализации.

## Anti-pattern

1. **«Бэкап есть — значит защищены».** Копии в том же ДЦ, никогда не тестировались, восстановление не документировано → при катастрофе площадки бэкап делит судьбу прода, а фактический RTO оказывается непредсказуемо большим. Почему возникает: покупка «страховки» без проверки, что полис действует. Последствие: потеря данных и простои сверх SLA. Лечение: 3-2-1 + квартальные DR-учения с замером времени.
2. **«Master-master из двух узлов для надёжности».** Без quorum/arbiter пара узлов при сетевом разделе гарантированно производят split-brain: две расходящиеся правды, двойные брони, неразрешимые конфликты. Почему возникает: интуитивное «два пишут — значит доступнее». Лечение: нечётный состав кластера с quorum (при необходимости — witness-узел), fencing, либо сознательный primary-replica с ручным failover.
