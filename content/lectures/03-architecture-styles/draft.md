# Лекция 3. Архитектурные стили и их влияние на базы данных

## Цель занятия
Научить студентов выбирать архитектурный стиль ИТ-системы с учётом бизнес-контекста, размера команды, бюджета и требований к данным. Показать, как выбор архитектуры влияет на организацию хранения данных, интеграции и стоимость владения системой.

## Learning Objectives
По окончании лекции студенты смогут:
1. Объяснить суть основных архитектурных стилей (монолит, модульный монолит, микросервисы, event-driven, serverless)
2. Применять закон Конвея для анализа соответствия архитектуры структуре команды
3. Оценить влияние архитектурного стиля на организацию хранения данных
4. Сравнить подходы shared database и database-per-service
5. Выбрать подходящий архитектурный стиль для конкретного бизнес-кейса
6. Обосновать выбор архитектуры с учётом trade-offs
7. Определить источники истины для ключевых сущностей системы
8. Нарисовать C4 Container Diagram для выбранной архитектуры

## Hook

**Кейс: Стартап запускает сервис онлайн-записи к врачам**

Представьте команду из 5 человек:
- 2 бэкенд-разработчика
- 1 фронтенд-разработчик
- 1 мобильный разработчик
- 1 дизайнер

**Ситуация:**
- Бюджет ограничен, нужно выйти на рынок за 3 месяца
- Требования: защита персональных данных (152-ФЗ), высокая доступность
- Нагрузка на старте: примерно 1000 пользователей в день
- Прогноз роста: до 50 000 пользователей в день через год
- Функционал: запись к врачу, расписание, уведомления, платежи, профили пациентов и врачей

**Дилемма основателей:**
Один из инвесторов настаивает: «Нужно сразу делать микросервисы! Все успешные компании используют микросервисы!»

CTO возражает: «У нас команда из 5 человек. Мы не сможем поддерживать 10 микросервисов. Давайте начнём с монолита.»

**Вопрос аудитории:** Что бы вы выбрали? Почему?

*Запишите свой ответ. Вернёмся к этому кейсу после изучения теории.*

## Теоретический блок

### Что такое архитектурный стиль

**Архитектурный стиль** — это способ организации компонентов системы, их взаимодействия и организации данных. Это не просто выбор технологий, а фундаментальное решение о том, как система будет устроена.

Архитектурный стиль определяет:
- Как компоненты общаются друг с другом (синхронно/асинхронно)
- Как организованы данные (единая база / раздельные базы)
- Как система масштабируется (вертикально / горизонтально)
- Как происходит развёртывание (единым артефактом / независимо)
- Как обеспечивается отказоустойчивость

### Обзор архитектурных стилей

#### 1. Monolith (Монолит)

**Суть:** Всё приложение — единый код, единая база данных, развёртывается одним артефактом.

```
┌─────────────────────────────────────┐
│           Клиент                    │
│    (Web / Mobile / Desktop)         │
└──────────────┬──────────────────────┘
               │
               ▼
┌─────────────────────────────────────┐
│          Монолит                    │
│  ┌─────────────────────────────┐    │
│  │ UI Layer                    │    │
│  ├─────────────────────────────┤    │
│  │ Business Logic Layer        │    │
│  ├─────────────────────────────┤    │
│  │ Data Access Layer           │    │
│  └─────────────────────────────┘    │
│                                     │
│  ┌─────────────────────────────┐    │
│  │      Единая база данных     │    │
│  │  - пользователи             │    │
│  │  - записи                   │    │
│  │  - врачи                    │    │
│  │  - платежи                  │    │
│  │  - уведомления              │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
```

**Когда подходит:**
- Маленькая команда (до 5–7 человек)
- Ограниченный бюджет и сжатые сроки
- Простой домен без сложных границ
- Требуется быстрый выход на рынок (time-to-market критичен)

**Когда не подходит:**
- Команда более 10–15 разработчиков
- Разные части системы имеют разные требования к масштабированию
- Критически важна независимость развёртывания компонентов
- Высокие требования к отказоустойчивости отдельных функций

**Преимущества:**
- Простота разработки и тестирования
- Быстрое развёртывание (один артефакт)
- Простая отладка (все логи в одном месте)
- Низкая стоимость инфраструктуры
- Транзакции ACID легко реализовать

**Риски:**
- Сложность масштабирования при росте нагрузки
- Риск «божественного объекта» (god object)
- Долгое время сборки и развёртывания при росте кода
- Изменение в одной части может сломать другую

**Влияние на данные:**
- Единая база данных для всех компонентов
- Легко обеспечить согласованность (ACID транзакции)
- Риск coupling через общую схему данных
- Сложность выделения частей для миграции

**Влияние на команду и эксплуатацию:**
- Один человек может знать всю систему
- Простой онбординг новых разработчиков
- Единый процесс CI/CD
- Мониторинг централизован

#### 2. Modular Monolith (Модульный монолит)

**Суть:** Монолит с явным разделением на модули по доменным границам. Модули общаются через чёткие интерфейсы, не обращаются напрямую к внутренностям друг друга.

```
┌─────────────────────────────────────────────────┐
│                Клиенты                          │
└────────────────────┬────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────┐
│           Модульный монолит                     │
│                                                 │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────┐ │
│  │  Модуль     │  │   Модуль    │  │ Модуль  │ │
│  │  Пациенты   │  │   Врачи     │  │ Записи  │ │
│  │             │  │             │  │         │ │
│  │ [API]       │  │ [API]       │  │ [API]   │ │
│  └──────┬──────┘  └──────┬──────┘  └────┬────┘ │
│         │                │                │      │
│  ┌──────┴────────────────┴────────────────┴───┐  │
│  │         Общая база данных                  │  │
│  │  ┌──────────┬──────────┬──────────────┐   │  │
│  │  │ схема    │ схема    │ схема        │   │  │
│  │  │ patients │ doctors  │ appointments │   │  │
│  │  └──────────┴──────────┴──────────────┘   │  │
│  └────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

**Когда подходит:**
- Команда 5–15 человек
- Домен имеет чёткие границы (можно выделить модули)
- Планируется рост и возможное выделение сервисов в будущем
- Нужен баланс между скоростью разработки и архитектурной чистотой

**Когда не подходит:**
- Очень маленькая команда (2–3 человека) — избыточно
- Критически требуется независимое масштабирование компонентов
- Разные части системы требуют разных технологий (СУБД, языки)

**Преимущества:**
- Чёткие границы между компонентами
- Возможность эволюции в микросервисы при необходимости
- Сохраняется простота развёртывания монолита
- Лучшая тестируемость по сравнению с «спагетти-монолитом»

**Риски:**
- Модули могут со временем стать связанными (architectural drift)
- Требуется дисциплина команды для соблюдения границ
- Риск превращения в «распределённый монолит» при неправильном выделении

**Влияние на данные:**
- Единая физическая база данных
- Логическое разделение по схемам (schemas)
- Межмодульное взаимодействие через API, не через прямые JOIN между схемами
- Источник истины остаётся единым

**Влияние на команду и эксплуатацию:**
- Команды могут работать над разными модулями
- Требуется координация при изменении межмодульных интерфейсов
- Единый процесс CI/CD, но модульные тесты изолированы

#### 3. Microservices (Микросервисы)

**Суть:** Система состоит из независимых сервисов, каждый со своей базой данных. Сервисы общаются через API (синхронно) или события (асинхронно).

```
┌─────────────────────────────────────────────────────────────────┐
│                         API Gateway                             │
└───────┬──────────────┬──────────────┬──────────────┬───────────┘
        │              │              │              │
        ▼              ▼              ▼              ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│   Сервис     │ │   Сервис     │ │   Сервис     │ │   Сервис     │
│  Пациенты    │ │   Врачи      │ │   Записи     │ │  Уведомления │
│              │ │              │ │              │ │              │
│ ┌──────────┐ │ │ ┌──────────┐ │ │ ┌──────────┐ │ │ ┌──────────┐ │
│ │   БД     │ │ │ │   БД     │ │ │ │   БД     │ │ │ │  Queue   │ │
│ │ patients │ │ │ │ doctors  │ │ │ │appoint-  │ │ │ │          │ │
│ │          │ │ │ │          │ │ │ │ ments    │ │ │ │          │ │
│ └──────────┘ │ │ └──────────┘ │ │ └──────────┘ │ │ └──────────┘ │
└──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘
```

**Когда подходит:**
- Команда более 10–15 разработчиков (несколько команд)
- Разные части системы имеют разные требования к масштабированию
- Критически важна независимость развёртывания
- Зрелая DevOps-культура и инфраструктура

**Когда не подходит:**
- Маленькая команда (менее 7 человек)
- Ограниченный бюджет
- Простой домен без сложных границ
- Отсутствие опыта эксплуатации распределённых систем

**Преимущества:**
- Независимое развёртывание сервисов
- Масштабирование отдельных компонентов по мере необходимости
- Отказоустойчивость: падение одного сервиса не ломает всю систему
- Возможность использовать разные технологии для разных сервисов

**Риски:**
- Высокая операционная сложность (мониторинг, логирование, трассировка)
- Распределённые транзакции сложнее (eventual consistency)
- Сетевые задержки и отказы
- Стоимость инфраструктуры выше примерно в 3–5 раз
- Требует зрелости команды и процессов

**Влияние на данные:**
- Database-per-service: каждый сервис владеет своей базой
- Нет прямых JOIN между сервисами
- Согласованность через события (eventual consistency)
- Сложнее обеспечить целостность данных

**Влияние на команду и эксплуатацию:**
- Каждая команда владеет своим сервисом end-to-end
- Требуется развитая DevOps-инфраструктура
- Необходимы service mesh, API gateway, centralized logging
- Выше требования к квалификации разработчиков

#### 4. Event-Driven Architecture (Событийная архитектура)

**Суть:** Компоненты общаются асинхронно через события. Производитель события не знает о потребителях.

```
┌──────────────┐      ┌─────────────────────────────────────┐
│   Сервис     │─────▶│         Message Broker              │
│  Записи      │事件   │  (Kafka / RabbitMQ / Azure Service │
│              │      │            Bus)                     │
└──────────────┘      └──────────────┬──────────────────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              │                      │                      │
              ▼                      ▼                      ▼
┌─────────────────────┐ ┌─────────────────────┐ ┌─────────────────────┐
│    Сервис           │ │    Сервис           │ │    Сервис           │
│  Уведомлений        │ │   Аналитики         │ │    Платежей         │
│                     │ │                     │ │                     │
│ ┌─────────────────┐ │ │ ┌─────────────────┐ │ │ ┌─────────────────┐ │
│ │  Отправка email │ │ │ │  Агрегация      │ │ │ │  Процессинг     │ │
│ │  SMS push       │ │ │ │  метрик         │ │ │ │  платежей       │ │
│ └─────────────────┘ │ │ └─────────────────┘ │ │ └─────────────────┘ │
└─────────────────────┘ └─────────────────────┘ └─────────────────────┘
```

**Когда подходит:**
- Требуются высокая отказоустойчивость и масштабируемость
- Важна асинхронная обработка (например, уведомления)
- Система должна реагировать на события в реальном времени

**Когда не подходит:**
- Простые CRUD-приложения без сложных потоков событий
- Команда без опыта работы с очередями сообщений
- Требования к строгой согласованности данных (strong consistency)

**Преимущества:**
- Слабая связанность компонентов
- Лучшая отказоустойчивость (очередь буферизирует пики)
- Масштабируемость потребителей событий
- Возможность добавлять новых потребителей без изменения производителя

**Риски:**
- Сложность отладки асинхронных потоков
- Eventual consistency может быть неприемлема для некоторых сценариев
- Очереди не заменяют базу данных (не хранить состояние в очереди!)
- Требует мониторинга очередей и обработки «мёртвых» сообщений

**Влияние на данные:**
- События хранятся в брокере сообщений (временное хранение)
- Состояние хранится в базах данных сервисов
- Может потребоваться Event Sourcing для полного аудита
- Важно обеспечить idempotency обработчиков

**Влияние на команду и эксплуатацию:**
- Требуется понимание асинхронных паттернов
- Необходим мониторинг очередей (lag, dead letters)
- Сложнее тестировать端到端 сценарии

#### 5. Serverless / FaaS (Functions as a Service)

**Суть:** Код выполняется в виде функций по событию. Провайдер управляет инфраструктурой. Оплата за фактическое использование.

```
┌─────────────────────────────────────────────────────────────┐
│                    Cloud Provider                           │
│                                                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │  Function   │  │  Function   │  │  Function   │         │
│  │  "Create    │  │  "Send      │  │  "Process   │         │
│  │  Appointment"│  │  Reminder"  │  │  Payment"   │         │
│  │             │  │             │  │             │         │
│  │  ▶ Trigger: │  │  ▶ Trigger: │  │  ▶ Trigger: │         │
│  │    HTTP     │  │    Schedule │  │    Event    │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              Managed Databases                      │   │
│  │         ( Cosmos DB / DynamoDB / Aurora )           │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

**Когда подходит:**
- Непредсказуемая или переменная нагрузка
- Event-driven сценарии (обработка файлов, триггеры)
- Маленькая команда без желания управлять серверами
- Прототипирование и MVP

**Когда не подходит:**
- Постоянная высокая нагрузка (дороже виртуальных машин)
- Требования к низкой задержке (cold start проблема)
- Vendor lock-in неприемлем
- Сложные долгоживущие процессы

**Преимущества:**
- Нет управления инфраструктурой
- Оплата только за время выполнения
- Автоматическое масштабирование
- Быстрый старт проекта

**Риски:**
- Vendor lock-in (привязка к провайдеру)
- Cold start: задержка при первом вызове функции
- Сложность отладки распределённых функций
- Ограничения на время выполнения (таймауты)

**Влияние на данные:**
- Функции stateless (не хранят состояние)
- Состояние во внешних managed databases
- Важно управлять соединениями с БД (connection pooling сложно)

**Влияние на команду и эксплуатацию:**
- Меньше операций, больше разработки
- Требуется знание облачных сервисов провайдера
- Мониторинг через облачные инструменты

#### 6. Hybrid Architecture (Гибридная архитектура)

**Суть:** Комбинация нескольких стилей. Например, монолит + отдельные микросервисы для специфических задач.

**Пример:**
- Основное приложение — модульный монолит
- Сервис уведомлений — отдельный микросервис (event-driven)
- Обработка платежей — serverless функции
- Аналитика — отдельный сервис с own database

**Когда подходит:**
- Разные части системы имеют разные требования
- Постепенная миграция от монолита к микросервисам
- Оптимизация стоимости и производительности

**Когда не подходит:**
- Отсутствие чёткого понимания границ
- Недостаточная квалификация команды

### Закон Конвея

**Формулировка:** «Организации создают системы, копирующие их коммуникационную структуру.»

**Практический вывод:** Если у вас 5 человек в одной команде, архитектура из 10 микросервисов будет неестественной и сложной в поддержке.

**Пример:**
- Команда из 3 человек → монолит или модульный монолит
- 3 команды по 5 человек → микросервисы с чёткими границами

**Как применять:**
1. Проанализируйте структуру команды
2. Выделите коммуникационные границы
3. Спроектируйте архитектуру, отражающую эти границы
4. При изменении команды адаптируйте архитектуру

### Подходы к организации данных

#### 1. Shared Database (Общая база данных)

Несколько сервисов/модулей обращаются к одной базе данных.

**Плюсы:**
- Простота обеспечения согласованности
- Легко делать JOIN между таблицами
- Низкая стоимость

**Минусы:**
- Coupling через схему данных
- Изменение в одной части влияет на другие
- Блокировки и конкуренция за ресурсы

**Когда допустимо:** В монолите или модульном монолите на ранних этапах.

**Когда анти-паттерн:** В микросервисах — нарушает принцип независимости.

---

#### 2. Logical Separation (Логическое разделение)

Единая физическая база, но данные разделены по схемам (schemas).

**Пример:**
```
База данных: medical_app
├── schema: patients
├── schema: doctors
├── schema: appointments
└── schema: billing
```

**Плюсы:**
- Логические границы между модулями
- Сохраняется возможность JOIN при необходимости
- Проще миграции

**Минусы:**
- Физически всё ещё единая точка отказа
- Ограниченное масштабирование

---

#### 3. Database-per-service (База на сервис)

Каждый сервис владеет своей базой данных. Другие сервисы не имеют прямого доступа.

**Плюсы:**
- Полная независимость сервисов
- Можно выбрать СУБД под задачу сервиса
- Изоляция отказов

**Минусы:**
- Нет JOIN между сервисами
- Eventual consistency
- Выше стоимость и сложность

---

#### 4. Derived Stores (Производные хранилища)

Данные дублируются в разных форматах для разных целей.

**Пример:**
- Основная база: реляционная (транзакции)
- Поисковый индекс: Elasticsearch (поиск)
- Кэш: Redis (быстрый доступ)

**Важно:** Определить источник истины (source of truth) и механизмы синхронизации.

---

#### 5. Source of Truth (Источник истины)

Для каждой сущности должен быть определён единственный сервис, который владеет данными.

**Пример для сервиса записи:**
| Сущность | Источник истины |
|----------|-----------------|
| Пациент | Сервис пациентов |
| Врач | Сервис врачей |
| Запись | Сервис записей |
| Платёж | Сервис платежей |

Другие сервисы получают данные через API или события.

## Case Study

Вернёмся к кейсу стартапа: сервис онлайн-записи к врачам.

**Контекст:**
- Команда: 5 человек
- Срок выхода на рынок: 3 месяца
- Бюджет: ограниченный
- Нагрузка на старте: примерно 1000 пользователей в день
- Прогноз роста: до 50 000 пользователей в день через год

### Вариант A: Монолит

**Архитектура:**
- Единое приложение (например, на .NET или Java)
- Одна база данных (PostgreSQL)
- Все модули в одном коде

**Оценка:**

| Критерий | Оценка | Комментарий |
|----------|--------|-------------|
| Time-to-market | ⭐⭐⭐⭐⭐ | Быстрый старт, минимум настройки |
| Стоимость разработки | ⭐⭐⭐⭐⭐ | Низкая, один репозиторий |
| Стоимость эксплуатации | ⭐⭐⭐⭐⭐ | Один сервер, простая инфраструктура |
| Сложность команды | ⭐⭐⭐⭐⭐ | Низкая, все в одном контексте |
| Масштабируемость | ⭐⭐ | Ограниченная, вертикальное масштабирование |
| Отказоустойчивость | ⭐⭐ | Падение всего приложения при ошибке |
| Влияние на данные | ⭐⭐⭐⭐ | Простая согласованность, ACID |
| Риски | ⭐⭐⭐ | Риск роста сложности кода |

**Вердикт:** Подходит для быстрого старта, но потребуется рефакторинг при росте.

---

### Вариант B: Модульный монолит

**Архитектура:**
- Единое приложение с явными модулями:
  - Patients (Пациенты)
  - Doctors (Врачи)
  - Appointments (Записи)
  - Notifications (Уведомления)
  - Billing (Платежи)
- Единая база данных с разделением по схемам
- Межмодульное взаимодействие через внутренние API

**Оценка:**

| Критерий | Оценка | Комментарий |
|----------|--------|-------------|
| Time-to-market | ⭐⭐⭐⭐ | Чуть дольше монолита из-за проектирования границ |
| Стоимость разработки | ⭐⭐⭐⭐ | Немного выше из-за дисциплины |
| Стоимость эксплуатации | ⭐⭐⭐⭐⭐ | Как у монолита |
| Сложность команды | ⭐⭐⭐⭐ | Требует понимания границ |
| Масштабируемость | ⭐⭐⭐ | Лучше монолита, можно выделять модули |
| Отказоустойчивость | ⭐⭐⭐ | Изоляция на уровне модулей |
| Влияние на данные | ⭐⭐⭐⭐ | Логическое разделение, ACID сохраняется |
| Риски | ⭐⭐⭐⭐ | Architectural drift риск |

**Вердикт:** **Рекомендуемый вариант.** Баланс скорости и архитектурной чистоты. Возможность эволюции.

---

### Вариант C: Микросервисы

**Архитектура:**
- 5+ сервисов (Patients, Doctors, Appointments, Notifications, Billing, ...)
- Database-per-service
- API Gateway для маршрутизации
- Message Broker для асинхронной коммуникации

**Оценка:**

| Критерий | Оценка | Комментарий |
|----------|--------|-------------|
| Time-to-market | ⭐⭐ | Долгий старт из-за инфраструктуры |
| Стоимость разработки | ⭐⭐ | Высокая, много boilerplate |
| Стоимость эксплуатации | ⭐ | Очень высокая (3–5× монолита) |
| Сложность команды | ⭐ | Требует зрелости DevOps |
| Масштабируемость | ⭐⭐⭐⭐⭐ | Отличная |
| Отказоустойчивость | ⭐⭐⭐⭐ | Хорошая |
| Влияние на данные | ⭐⭐ | Сложная согласованность |
| Риски | ⭐ | Высокие риски для стартапа |

**Вердикт:** **Не рекомендуется.** Преждевременная оптимизация для команды из 5 человек.

---

### Рекомендация для кейса

**Выбор: Модульный монолит**

**Обоснование:**
1. Соответствует размеру команды (5 человек)
2. Позволяет выйти на рынок за 3 месяца
3. Даёт чёткие границы для будущей эволюции
4. Сохраняет простоту эксплуатации
5. При росте нагрузки можно выделить сервисы уведомлений и платежей отдельно

**План эволюции:**
1. **Месяц 1–3:** Модульный монолит, запуск MVP
2. **Месяц 4–6:** Мониторинг, выявление узких мест
3. **Месяц 7–12:** При росте нагрузки >10 000 пользователей в день:
   - Выделить сервис уведомлений (event-driven)
   - Выделить сервис платежей (требования PCI DSS)
4. **Год 2+:** При команде >15 человек рассмотреть полную микросервисную архитектуру

## Связка с управленческими решениями

### Как архитектура влияет на бизнес-метрики

| Метрика | Влияние архитектуры |
|---------|---------------------|
| Time-to-market | Монолит быстрее на старте, микросервисы быстрее при зрелой платформе |
| Cost of development | Монолит дешевле, микросервисы требуют больше разработчиков |
| Cost of operations | Микросервисы дороже примерно в 3–5 раз (инфраструктура, мониторинг) |
| Reliability | Микросервисы лучше изолируют отказы, но сложнее в диагностике |
| Scalability | Микросервисы позволяют масштабировать отдельные компоненты |
| Team productivity | Закон Конвея: архитектура должна соответствовать структуре команды |

### TCO (Total Cost of Ownership)

**Примерная оценка для проекта на 3 года:**

| Статья расходов | Монолит | Модульный монолит | Микросервисы |
|-----------------|---------|-------------------|--------------|
| Инфраструктура | ~$500/мес | ~$600/мес | ~$2000/мес |
| Разработка | 5 человек | 5–7 человек | 10–15 человек |
| DevOps | 0.5 человека | 1 человек | 2–3 человека |
| Инструменты | ~$200/мес | ~$300/мес | ~$1000/мес |
| Обучение | Минимальное | Среднее | Высокое |

*Цифры примерные, зависят от региона и стека технологий.*

### Когда переходить от монолита к микросервисам?

**Признаки того, что пора задуматься о разделении:**
1. Команда выросла до 10–15+ разработчиков
2. Время сборки и развёртывания превышает 30 минут
3. Разные части системы имеют разные требования к масштабированию
4. Частые конфликты при слиянии кода
5. Невозможность независимого тестирования компонентов

**Признаки того, что ещё рано:**
1. Команда менее 7 человек
2. Продукт на стадии поиска product-market fit
3. Нет выделенной DevOps-роли
4. Отсутствие автоматизированного тестирования
5. Неясные границы домена

### Роль архитектора / ИТ-менеджера

**Что должен делать:**
- Анализировать бизнес-контекст и ограничения
- Оценивать trade-offs архитектурных решений
- Фиксировать решения в ADR (Architecture Decision Records)
- Коммуницировать решения команде и стейкхолдерам
- Планировать эволюцию архитектуры

**Чего избегать:**
- Следования хайпу («все используют микросервисы»)
- Преждевременной оптимизации
- Игнорирования закона Конвея
- Решений без учёта TCO

## Ключевые термины

- **Monolith (Монолит)** — архитектурный стиль, где всё приложение — единый код и база данных
- **Modular Monolith (Модульный монолит)** — монолит с явным разделением на модули по доменным границам
- **Microservices (Микросервисы)** — архитектура из независимых сервисов, каждый со своей базой данных
- **Event-Driven Architecture** — стиль, где компоненты общаются асинхронно через события
- **Serverless / FaaS** — выполнение кода в виде функций по событию без управления серверами
- **Закон Конвея** — организации создают системы, копирующие их коммуникационную структуру
- **Shared Database** — анти-паттерн, когда несколько сервисов используют одну базу данных
- **Database-per-service** — паттерн микросервисов, где каждый сервис владеет своей базой
- **Source of Truth** — единственный сервис, который владеет данными сущности
- **Eventual Consistency** — модель согласованности, где данные становятся согласованными со временем
- **TCO (Total Cost of Ownership)** — совокупная стоимость владения системой

## Anti-pattern

### ❌ Anti-pattern 1: Микросервисы для маленькой команды

**Симптомы:**
- Команда из 3–5 человек создаёт 10+ микросервисов
- Каждый сервис требует своего CI/CD пайплайна
- Разработчики тратят больше времени на деплой, чем на разработку
- Невозможно быстро исправить баг (нужно деплоить 3 сервиса)

**Последствия:**
- Time-to-market увеличивается в разы
- Стоимость эксплуатации растёт
- Команда выгорает от операционной нагрузки

**Решение:** Начать с монолита или модульного монолита. Переходить к микросервисам при росте команды и нагрузки.

---

### ❌ Anti-pattern 2: Shared Database между микросервисами

**Симптомы:**
- Несколько сервисов пишут в одну базу данных
- Сервисы делают JOIN между таблицами других сервисов
- Изменение схемы в одном сервисе ломает другие

**Последствия:**
- Нарушается независимость сервисов
- Появляется скрытое coupling
- Невозможно независимо масштабировать и деплоить

**Решение:** Database-per-service. Взаимодействие через API или события.

---

### ❌ Anti-pattern 3: Преждевременное разделение без понимания домена

**Симптомы:**
- Границы сервисов выделены до анализа предметной области
- Часто приходится менять границы
- Данные дублируются между сервисами

**Последствия:**
- Дорогостоящий рефакторинг
- Потеря целостности данных
- Путаница в ответственности сервисов

**Решение:** Сначала провести Event Storming и выделить доменные границы (Лекция 2). Затем проектировать сервисы.

---

### ❌ Anti-pattern 4: Использование очереди как базы данных

**Симптомы:**
- Состояние приложения хранится в сообщениях очереди
- Нет персистентного хранилища
- При перезапуске брокера данные теряются

**Последствия:**
- Потеря данных
- Невозможность выполнить сложные запросы
- Нарушение durability требований

**Решение:** Очередь — для передачи событий, база данных — для хранения состояния.

## Мостик к следующей лекции

Мы выбрали архитектурный стиль для нашего сервиса записи к врачам. Но архитектура — это только верхнеуровневое решение. Следующий критический шаг — **детальное проектирование данных**.

**В Лекции 4 «Проектирование данных и выбор СУБД» мы разберём:**

1. **Нормализация и денормализация:**
   - Когда нормализовать данные?
   - Когда допустима денормализация для производительности?

2. **Выбор типа СУБД:**
   - Реляционные (PostgreSQL, MySQL) — когда и почему?
   - Документные (MongoDB) — какие use cases?
   - Колоночные (ClickHouse) — для аналитики
   - Key-Value (Redis) — для кэша
   - Графовые (Neo4j) — для связей

3. **Индексы и производительность:**
   - Как индексы ускоряют запросы?
   - Когда индексы вредят?

4. **Транзакции и согласованность:**
   - ACID vs BASE
   - Уровни изоляции транзакций
   - Паттерны distributed transactions

5. **Паттерны работы с данными:**
   - CQRS (Command Query Responsibility Segregation)
   - Event Sourcing
   - Saga для распределённых транзакций

**Домашнее задание:** Повторить основы реляционных баз данных (таблицы, первичные ключи, внешние ключи, индексы).
