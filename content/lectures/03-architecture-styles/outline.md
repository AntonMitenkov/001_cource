# План Лекции 3

## Цель
Научить студентов выбирать архитектурный стиль ИТ-системы на основе анализа бизнес-контекста, ограничений команды и требований к данным. Сформировать понимание компромиссов между различными архитектурными подходами.

## Learning Objectives
По окончании лекции студенты смогут:
1. Объяснить суть основных архитектурных стилей (монолит, модульный монолит, микросервисы, event-driven, serverless)
2. Применять закон Конвея для анализа соответствия архитектуры структуре команды
3. Оценить влияние архитектурного стиля на организацию хранения данных
4. Сравнить подходы shared database и database-per-service
5. Выбрать подходящий архитектурный стиль для конкретного бизнес-кейса
6. Обосновать выбор архитектуры с учётом trade-offs
7. Определить источники истины для ключевых сущностей системы
8. Нарисовать C4 Container Diagram для выбранной архитектуры

## Последовательность блоков

### 1. Hook (5 мин)
- Кейс стартапа: сервис онлайн-записи к врачам
- Дилемма основателей: монолит для быстрого запуска или микросервисы для будущего роста?
- Вопрос аудитории: что бы вы выбрали?

### 2. Теоретический блок (30 мин)
- Что такое архитектурный стиль
- Обзор стилей:
  - Monolith: единое приложение, единая база
  - Modular Monolith: разделение по модулям внутри одного приложения
  - Microservices: независимые сервисы, database-per-service
  - Event-Driven Architecture: асинхронная коммуникация через события
  - Serverless / FaaS: функции по событию без управления серверами
  - Hybrid Architecture: комбинация подходов
- Закон Конвея и его влияние
- Подходы к организации данных:
  - Shared database
  - Logical separation
  - Database-per-service
  - Derived stores
  - Source of truth

### 3. Case Study (20 мин)
- Анализ кейса сервиса записи к врачам
- Сравнение трёх вариантов:
  - Вариант A: Монолит (быстрый старт, простые развёртывание)
  - Вариант B: Модульный монолит (баланс, возможность эволюции)
  - Вариант C: Микросервисы (преждевременно для команды из 5 человек)
- Рекомендация: начать с модульного монолита

### 4. Связка с управленческими решениями (15 мин)
- Как архитектура влияет на:
  - Time-to-market
  - Стоимость разработки и эксплуатации
  - Требования к команде
  - Масштабируемость
  - Отказоустойчивость
- TCO (Total Cost of Ownership) для разных стилей
- Когда переходить от монолита к микросервисам
- Роль архитектора в принятии решений

### 5. Резюме и мостик к Лекции 4 (10 мин)
- Ключевые выводы
- Ответы на вопросы
- Анонс Лекции 4: проектирование данных и выбор СУБД

## Ключевые тезисы по блокам

### Блок 1: Hook
- Стартап с ограниченным бюджетом и сжатыми сроками
- Команда из 5 человек не может поддерживать 10 микросервисов
- Выбор архитектуры — стратегическое решение

### Блок 2: Теория
- Архитектурный стиль определяет способ организации компонентов и данных
- Монолит: простота разработки, сложность масштабирования
- Микросервисы: независимость развёртывания, высокая операционная сложность
- Модульный монолит: золотая середина для растущих проектов
- Event-driven: асинхронность, лучшая отказоустойчивость
- Serverless: оплата за использование, vendor lock-in риск
- Закон Конвея: «Организации создают системы, копирующие их коммуникационную структуру»
- Shared database — анти-паттерн для микросервисов
- Database-per-service требует зрелости команды

### Блок 3: Case Study
- Для сервиса записи к врачам на старте оптимален модульный монолит
- Выделение модулей: Пациенты, Врачи, Записи, Уведомления, Платежи
- Единая база данных с логическим разделением схем
- План эволюции: при росте нагрузки выделить сервис уведомлений и платежей

### Блок 4: Управленческие решения
- Монолит снижает time-to-market на ранних этапах
- Микросервисы увеличивают стоимость эксплуатации примерно в 3–5 раз
- Переход к микросервисам оправдан при:
  - Команде более 10–15 разработчиков
  - Разных требованиях к масштабируемости компонентов
  - Необходимости независимого развёртывания
- TCO включает: инфраструктуру, зарплаты, инструменты мониторинга, обучение

### Блок 5: Резюме
- Нет универсального решения — есть контекстно-обоснованный выбор
- Архитектура должна эволюционировать вместе с продуктом
- Следующий шаг: детальное проектирование данных

## Практика
**Задание:** Сравнить архитектурные стили для кейса сервиса записи к врачам

**Артефакты:**
1. Матрица сравнения архитектурных стилей (5 стилей × 8 критериев)
2. Обоснование выбора архитектуры (1 страница)
3. C4 Container Diagram выбранного решения
4. Таблица источников истины для сущностей

**Критерии оценки:**
- Полнота анализа (20%)
- Обоснованность выбора (30%)
- Качество диаграммы (20%)
- Учёт ограничений кейса (20%)
- Связь с бизнес-целями (10%)

## Переход к Лекции 4
В Лекции 4 мы перейдём от выбора архитектурного стиля к детальному проектированию данных:
- Нормализация и денормализация
- Выбор между реляционными и нереляционными СУБД
- Индексы и производительность запросов
- Транзакции и согласованность данных
- Паттерны работы с данными в распределённых системах
