# Практика к лекции 3: Концептуальная и логическая модели данных. Нормализация и эволюция схемы

## Цель практики

Отработать навык проектирования структуры данных от бизнес-уровня до логической схемы: строить концептуальную модель по доменным событиям, переводить её в логическую схему с ключами и ограничениями, приводить схему к 3НФ, обосновывать денормализацию через ADR и планировать Zero-Downtime миграцию по паттерну Expand and Contract.

**Отрабатываемый навык:** трансформация «событий и правил бизнеса» (Лекция 2) в нормализованные модели данных (Лекция 3) — уровень WHAT/WHY, без программирования.

**Создаваемый артефакт:** пакет «Модель данных контекста»: концептуальная ER-схема + логическая схема в 3НФ (таблицы, PK/FK, Constraints) + ADR об обоснованной денормализации + план миграции Expand and Contract. Артефакт входит в итоговый Architecture Blueprint.

**Связь с лекцией:** выполняется после Лекции 3, опирается на события и ограниченные контексты из Лекции 2; результат становится входом для выбора СУБД на Лекции 4.

## Кейс

**Сервис каршеринга «DriveShare»** (сквозной кейс курса, Лекции 1–3).

На Лекции 2 команда провела Event Storming и выделила ограниченные контексты: **Бронирование**, **Телематика**, **Оплата**, **Штрафы**, **Поддержка**. Запуск MVP — 3 месяца, парк ~200 автомобилей на город, 3 города, команда 8 человек, бюджет ~5 млн руб.; NFR: доступность 99.9%, строгая консистентность при бронировании, eventual consistency допустима между контекстами.

**Текущая ситуация.** Быстрая «первая версия» схемы сделана одной таблицей на контекст (по образцу `trips_raw` из Hook лекции): списки через запятую, дублирование тарифов и данных клиентов в каждой строке. При изменении цены тарифа скрипт правит сотни тысяч строк; удаление тестовой поездки «съедает» клиента; добавление нового тарифа невозможно без поездки. Каждое изменение схемы блокирует сервис на неопределённое время.

**Задача:** спроектировать модели данных для назначенного контекста так, чтобы аномалии исчезли, бизнес-правила стали ограничениями схемы, а будущие изменения проводились без простоя.

## Входные данные

1. **Список доменных событий контекста** (из практики Лекции 2; варианты ниже).
2. **Бизнес-правила** (фрагменты из Лекции 2–3):
   - Бронирование не может существовать без клиента и автомобиля;
   - один автомобиль не может быть забронирован на пересекающиеся интервалы;
   - чек должен показывать цену минуты на момент поездки даже после смены тарифа;
   - штраф может быть выставлен постфактум, в том числе привязан к поездке;
   - путевой лист связывает поездку и водителя (many-to-many);
   - платёж относится к поездке, возможны частичные оплаты и возвраты.
3. **NFR и ограничения:** доступность 99.9% (миграции без простоя), GDPR/152-ФЗ (PII: телефон, email, паспортные данные), команда 8 человек (схема должна быть понятна всем), срок MVP 3 месяца.
4. **«Плохая» таблица-монолит** выбранного контекста — см. шаблон результата, Шаг 0.

### Варианты контекстов (выдать студентам/группам)

| Вариант | События (примеры) | Особенности |
|---|---|---|
| A. Оплата | Платёж инициирован / подтверждён / отклонён / возврат оформлен | PII минимум, но аудит и неизменяемость истории |
| B. Штрафы | Штраф выявлен / выставлен / оспорен / оплачен / снят | state machine статуса, связь с ГИБДД как внешний источник |
| C. Поддержка | Обращение создано / назначено оператору / решено / эскалировано | M:N обращения↔категории, вложения, SLA-таймеры |
| D. Телематика | GPS-точка получена / поездка начата / превышение зафиксировано | высокий поток событий; подсказка: сырые точки и агрегаты — разные структуры |

## Задание

1. **Шаг 0. Аудит «плохой» таблицы.** Для выданной таблицы-монолита своего контекста найдите и опишите: нарушения 1НФ (списки, повторяющиеся группы), потенциальные INSERT/UPDATE/DELETE-аномалии, транзитивные зависимости.
2. **Шаг 1. Концептуальная модель.** Из существительных событий выпишите 5–8 сущностей; установите связи с кардинальностями (1:1, 1:N, M:N) и обязательностью; формализуйте 3–4 бизнес-правила из входных данных прямо на схеме (подписи связей). Нотация — Чен или Crow's Foot (Mermaid erDiagram).
3. **Шаг 2. Логическая модель.** Переведите концептуальную модель в таблицы: для каждой укажите PK (обоснуйте выбор: естественный/суррогатный/составной), FK с политикой удаления (CASCADE/SET NULL/RESTRICT — как отражение бизнес-правила), минимум 4 ограничения NOT NULL / UNIQUE / CHECK / DEFAULT с формулировкой «какое бизнес-правило защищает». M:N реализуйте промежуточной таблицей.
4. **Шаг 3. Проверка 3НФ.** Пройдите по цепочке: 1НФ (атомарность) → 2НФ (полная зависимость от PK) → 3НФ (нет транзитивных зависимостей). Зафиксируйте каждое найденное нарушение и действие по устранению (вынос атрибута в отдельную таблицу). Итоговая схема обязана быть в 3НФ.
5. **Шаг 4. ADR о компромиссе.** Выберите один факт вашего контекста, который целесообразно хранить снимком/денормализованно (например, сумма чека, статус клиента на момент обращения), и заполните ADR по формату Лекции 1: контекст → решение → альтернативы → последствия (включая риск рассинхронизации и меру против него). Если считаете, что денормализация не нужна — напишите ADR с решением «остаёмся в строгой 3НФ» и обоснуйте.
6. **Шаг 5. План эволюции схемы.** Новое бизнес-требование (пост-запуск): «к штрафу нужно добавить составное нарушение: один штраф может ссылаться на несколько поездок» (для варианта B; для остальных — аналог 1:N→M:N или разделение поля, выдаёт преподаватель). Опишите миграцию по Expand and Contract: что происходит на каждой фазе, где backfill и двойная запись, почему удаление старой структуры — отдельный поздний релиз, как обеспечивается откат на каждом шаге. Никакого кода — только последовательность шагов и состояний системы.

**Ожидаемый результат:** пакет «Модель данных контекста» (4 документа в одном файле/папке): ER-концептуальная, логическая 3НФ-схема, ADR, план миграции.

## Критерии оценки

| Критерий | Вес | Описание |
|----------|-----|----------|
| Полнота анализа (Шаг 0) | 15% | Названы реальные нарушения и аномалии, а не абстракции |
| Обоснованность решений | 25% | Выбор ключей и политик FK объяснён бизнес-правилами; ADR содержит альтернативы и последствия |
| Соответствие ограничениям | 20% | Схема поддерживает NFR (консистентность бронирования, PII/GDPR, zero-downtime миграция) |
| Качество артефакта | 25% | Корректная нотация, итоговая схема действительно в 3НФ (проверяется по ФД), читаемость |
| Связь с бизнес-целями | 15% | Видно, как модель обслуживает события/правила Лекции 2, а не «идеальную норму ради нормы» |

## Подсказки

- 💡 Сначала глаголы (события), потом существительные (сущности): каждое событие «X сделал Y с Z» даёт кандидата в сущности или связь.
- 💡 Тест на 3НФ: «этот атрибут зависит от ключа, только от ключа и ни от чего другого?» Если ответ требует слова «через другое поле» — это транзитивная зависимость.
- 💡 Снимок ≠ денормализация-зло: если факт исторический и не должен меняться (цена на момент поездки), иммутабельный снимок — корректная модель, а JOIN к меняющемуся справочнику был бы ошибкой.
- 💡 Материалы: `knowledge/data-modeling/normalization.md`, `keys-constraints.md`, `schema-evolution.md`, разделы «Часть 3–6» draft'а лекции.

## Типичные ошибки

- ❌ «Нормализовать всё до 5НФ любой ценой» — 30 таблиц для отчёта раз в месяц; достаточно 3НФ (эмпирическое правило курса; точная доля внешним источником не подтверждена).
- ❌ Телефон/email как PK — PII «размазывается» по FK, право на удаление по 152-ФЗ/GDPR превращается в каскадную операцию.
- ❌ Реализация M:N колонкой со списком ID через запятую вместо промежуточной таблицы (нарушение 1НФ).
- ❌ План миграции «переименовали колонку одним ALTER и сразу удалили старую» — нет окна отката, сервис в простое/ошибках у старых инстансов приложения.
- ❌ CHECK-ограничение без формулировки бизнес-правила — ограничение, которое никто не понимает и боится менять.

## Академическая честность

- При использовании внешних источников (Codd 1970, Chen 1976, Клейтманн DDIA гл. 3–4, документация инструментов миграций) — ссылки в формате APA.
- Разделы «Концептуальная модель», «Логическая модель», «ADR» проверяются на заимствования; AI-ассистенты допускаются как редакторы формулировок, но проектные решения и обоснования должны быть собственными (согласно правилам курса [требуется проверка: актуальная редакция правил академической честности]).
