# План Лекции 2

## Цель
Научить студентов декомпозировать сложную предметную область с помощью DDD, выявлять бизнес-события через Event Storming и формулировать измеримые требования к качеству системы.

## Learning Objectives
По окончании лекции студенты смогут:
1. Объяснить, почему понимание предметной области критично для архитектуры
2. Применять ключевые понятия DDD: Ubiquitous Language, Bounded Context, Context Map
3. Провести мини-сессию Event Storming для выявления доменных событий
4. Различать функциональные и нефункциональные требования
5. Сформулировать Quality Attribute Scenario по шаблону (stimulus, environment, response, measure)
6. Показать, как границы контекстов влияют на архитектуру данных и интеграции

## Последовательность блоков

### 1. Hook (5 мин)
- Ситуация: компания запускает сервис каршеринга
- Проблема: отдел разработки, отдел эксплуатации и бухгалтерия по-разному понимают «Поездку» и «Автомобиль»
- Результат: ошибки интеграции, дублирование данных, задержка запуска
- Вопрос: как избежать недопонимания между отделами?

### 2. Теоретический блок (30 мин)
**Часть 1: Domain-Driven Design (15 мин)**
- Что такое DDD и зачем он нужен
- Ubiquitous Language: единый словарь для бизнеса и разработки
- Bounded Context: границы модели предметной области
- Context Map: взаимосвязи между контекстами
- Aggregate, Entity, Value Object — кратко

**Часть 2: Event Storming (10 мин)**
- Что такое Event Storming и зачем он нужен
- Роли участников: бизнес-эксперты, разработчики, аналитики
- Типы стикеров: события, команды, агрегаты, контексты
- Процесс проведения сессии

**Часть 3: Quality Attribute Scenarios (5 мин)**
- Функциональные vs нефункциональные требования
- Шаблон Quality Attribute Scenario
- Примеры измеримых требований

### 3. Case Study (20 мин)
**Кейс: Сервис каршеринга**

**Шаг 1: Выявление событий**
- «Автомобиль забронирован»
- «Поездка началась»
- «Поездка завершена»
- «Оплата прошла»
- «Штраф выставлен»

**Шаг 2: Определение контекстов**
- Контекст «Бронирование»: доступность автомобилей, тарифы
- Контекст «Телематика»: местоположение, состояние автомобиля
- Контекст «Оплата»: транзакции, счета, возвраты
- Контекст «Штрафы»: нарушения, уведомления, оспаривание
- Контекст «Поддержка»: обращения клиентов, инциденты

**Шаг 3: Построение Context Map**
- Связи между контекстами
- Типы интеграций (синхронные/асинхронные)

**Шаг 4: Формулировка NFR**
- Доступность: 99.9% в часы пик
- Время ответа: 95% запросов < 300 мс
- Консистентность: eventual consistency между контекстами

### 4. Связка с управленческими решениями (15 мин)
**Что должен понимать ИТ-менеджер / Product Owner:**

1. **Команда и коммуникации**
   - Выделение контекстов → выделение команд (Conway's Law)
   - Единый язык снижает количество встреч и уточнений

2. **Бюджет и сроки**
   - Event Storming экономит время на переделку архитектуры
   - Раннее выявление противоречий снижает риски

3. **Архитектурные решения**
   - Границы контекстов → границы микросервисов
   - Каждый контекст → своя база данных
   - Выбор технологий зависит от требований контекста

4. **Риски игнорирования DDD**
   - Большая запутанная модель (Big Ball of Mud)
   - Дорогая поддержка и развитие
   - Невозможность масштабирования команды

### 5. Резюме и переход к Лекции 3 (10 мин)
**Ключевые выводы:**
- Предметная область определяет архитектуру
- DDD помогает управлять сложностью через разделение контекстов
- Event Storming — инструмент быстрого совместного анализа
- NFR должны быть измеримыми (Quality Attribute Scenarios)
- Границы контекстов влияют на выбор баз данных и интеграций

**Мостик к Лекции 3:**
В Лекции 3 студенты узнают, как выбранные контексты влияют на выбор архитектурного стиля (монолит, микросервисы, модульный монолит) и какие требования это накладывает на базы данных и интеграции.

## Ключевые тезисы по блокам

### Блок 1: DDD
- DDD фокусируется на глубоком понимании предметной области
- Ubiquitous Language устраняет недопонимание между бизнесом и техникой
- Bounded Context позволяет разным частям системы использовать одни термины по-разному
- Не пытайтесь создать универсальную модель на всю систему

### Блок 2: Event Storming
- Event Storming — совместная сессия с бизнес-экспертами
- Доменные события (оранжевые стикеры) — факты, произошедшие в системе
- Быстрый способ выявления процессов и противоречий
- Требует участия экспертов предметной области

### Блок 3: Quality Attribute Scenarios
- NFR описывают, **как** система работает, а не **что** она делает
- Шаблон: stimulus → environment → response → response measure
- Пример: «При 1000 одновременных пользователей (stimulus) в часы пик (environment) система должна отвечать за 300 мс (response) для 95% запросов (measure)»
- Без измеримости нельзя проверить выполнение требования

## Практика
**Задание:** Провести мини-сессию Event Storming для сервиса каршеринга

**Артефакты:**
1. Список доменных событий (минимум 10)
2. Выделенные ограниченные контексты (4–6)
3. Context Map со связями
4. 3 Quality Attribute Scenarios для ключевых требований
5. Заполненный Architecture Brief

**Время на практику:** 30–40 минут (аудиторная + самостоятельная работа)

## Переход к Лекции 3
Выделенные в этой лекции ограниченные контексты станут основой для выбора архитектурных стилей в Лекции 3. Студенты узнают:
- Какой стиль архитектуры подходит для каждого контекста
- Как архитектурный стиль влияет на требования к базам данных
- Какие паттерны интеграции выбрать для связи контекстов
- Как разные контексты могут требовать разные типы СУБД (полиглотное хранение)
