## Слайд. Hook: Проблема каршеринга

**Ситуация:** Запуск сервиса каршеринга, 200 автомобилей, 3 месяца до запуска

**Проблема:** Разные отделы по-разному понимают сущности:

| Отдел | Понимание «Автомобиля» |
|-------|------------------------|
| Эксплуатация | VIN, пробег, GPS, топливо |
| Бухгалтерия | Актив, амортизация, налоги |
| Продажи | Тариф, доступность, акции |
| Разработка | Таблица `cars` с 47 полями |

**Результат:** Ошибки интеграции, дублирование данных, задержка на 2 месяца

## Слайд. Domain-Driven Design (DDD)

**Определение:** Подход к разработке, фокусирующийся на глубоком понимании предметной области

**Ключевая идея:** Архитектура должна отражать структуру бизнеса, а не технические слои

**Зачем нужен:**
- Связывает бизнес-требования с техническими решениями
- Даёт методы декомпозиции сложных систем
- Формирует общий язык для бизнеса и разработки

---

## Слайд. Ubiquitous Language

**Единый словарь** для разработчиков и бизнес-экспертов

**Зачем:**
- Устраняет недопонимание
- Каждый термин имеет одно значение
- Снижает количество встреч и уточнений

**Правило:** Термин меняется в коде → меняется в документации и речи, и наоборот

**Пример:**
- ✅ «Бронирование» = оформленная заявка с временем начала и окончания
- ❌ «Заказ» = может означать бронирование, поездку или счёт

---

## Слайд. Bounded Context

**Ограниченный контекст** — граница модели предметной области со своим языком

**Зачем:** Разные части системы могут использовать одни термины по-разному

**Пример «Автомобиль»:**

| Контекст | Атрибуты |
|----------|----------|
| Бронирование | ID, класс, тариф, статус доступности |
| Телематика | VIN, GPS, топливо, пробег |
| Бухгалтерия | Стоимость, амортизация, категория |
| Поддержка | История инцидентов, ремонты |

**Правило:** Одна модель — один контекст. Не создавайте универсальную модель!

---

## Слайд. Context Map

**Карта контекстов** — взаимосвязи между ограниченными контекстами

**Типы связей:**

| Тип | Описание | Пример |
|-----|----------|--------|
| Partnership | Сотрудничество на равных | Бронирование ↔ Телематика |
| Customer-Supplier | Один зависит от другого | Телематика → Оплата |
| Conformist | Зависимый следует модели | Поддержка → Все контексты |
| ACL | Защита от чужой модели | Оплата → Платёжный шлюз |

## Слайд. Event Storming

**Метод совместного анализа** предметной области с цветными стикерами

**Роли:** Бизнес-эксперты, разработчики, аналитики, тестировщики

**Типы стикеров:**

| Цвет | Тип | Пример |
|------|-----|--------|
| 🟠 | Domain Event | «Автомобиль забронирован» |
| 🔵 | Command | «Забронировать автомобиль» |
| 🟡 | Aggregate | Агрегат «Бронирование» |
| 🟢 | Policy | «Если отмена < 24ч → штраф» |
| 🔴 | Problem | «Неясно, кто возвращает залог» |

**Время:** 2–4 часа на сессию

---

## Слайд. Процесс Event Storming

1. **Выявление событий** (15–30 мин) — оранжевые стикеры
2. **Добавление команд** (15 мин) — синие стикеры
3. **Выявление агрегатов** (15 мин) — жёлтые стикеры
4. **Определение политик** (15 мин) — зелёные стикеры
5. **Выделение контекстов** (15 мин) — чёрные рамки
6. **Выявление проблем** (10 мин) — красные стикеры

**Результат:** Общее понимание домена, выявленные противоречия

## Слайд. Функциональные vs Нефункциональные требования

**Функциональные** — **что** система делает:
- «Система должна позволять забронировать автомобиль»
- «Система должна рассчитывать стоимость поездки»

**Нефункциональные (NFR)** — **как** система работает:
- «95% запросов < 300 мс»
- «Доступность 99.9% в часы пик»
- «Данные о GPS обновляются каждые 10 сек»

---

## Слайд. Quality Attribute Scenario

**Шаблон формулировки NFR:**

| Элемент | Вопрос | Пример |
|---------|--------|--------|
| Stimulus | Что происходит? | Запрос на бронирование |
| Environment | В каких условиях? | Часы пик, 500 пользователей |
| Response | Что делает система? | Обрабатывает запрос |
| Response Measure | Как измерить? | 95% < 300 мс |

**Итог:** «При 500 пользователях в часы пик 95% запросов обрабатываются < 300 мс»

**Важно:** Без меры требование нельзя проверить!

---

## Слайд. Конфликты между NFR

| NFR 1 | NFR 2 | Конфликт | Решение |
|-------|-------|----------|---------|
| Производительность (< 100 мс) | Консистентность (strong) | Валидация замедляет | Eventual consistency |
| Доступность (99.99%) | Стоимость | 3 региона дорого | 99.9% для MVP |
| Безопасность (MFA) | Удобство | Дополнительные шаги | Аутентификация по риску |
| Масштабируемость | Консистентность | Шардирование сложно | Шард по ключу |

**Вывод:** Невозможно максимизировать всё. Приоритизируйте 2–3 атрибута!

## Слайд. Кейс: Контексты каршеринга

**5 ограниченных контекстов:**

1. **Бронирование** — доступность, тарифы, заявки
2. **Телематика** — GPS, состояние, поездки
3. **Оплата** — транзакции, счета, возвраты
4. **Штрафы** — нарушения, оспаривание
5. **Поддержка** — обращения, инциденты

**Каждый контекст:**
- Своя модель данных
- Своя база данных
- Свой тип консистентности

## Слайд. Управленческие решения

**Команда и коммуникации:**
- Выделение контекстов → выделение команд
- Закон Конвея: структура команды копирует архитектуру

**Бюджет и сроки:**
- Event Storming (4–8 часов) экономит недели переделки
- Раннее выявление противоречий снижает риски

**Архитектура:**
- Границы контекстов → границы микросервисов
- Каждый контекст → своя БД
- Не начинать микросервисы без DDD!

## Слайд. Риски игнорирования DDD

| Риск | Последствие |
|------|-------------|
| Big Ball of Mud | Запутанная модель, невозможно поддерживать |
| Дорогая поддержка | Каждое изменение ломает другие части |
| Невозможность масштабирования | Онбординг 3 месяца вместо 2 недель |
| Конфликты команд | Меняют одни и те же таблицы |

---

## Слайд. Anti-pattern

**❌ Единая модель на всё** — таблица `cars` с 47 полями

**❌ Технические границы** — Frontend/Backend/Database вместо бизнес-контекстов

**❌ Размытые NFR** — «Система должна быть быстрой»

**❌ JOIN между контекстами** — прямая зависимость баз данных

**❌ Event Storming без экспертов** — только разработчики

**❌ DDD для CRUD** — сложные паттерны там, где не нужно
