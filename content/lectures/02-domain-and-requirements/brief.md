# Бриф Лекции 2

## Тема
Предметная область и требования: DDD, Event Storming, Quality Attribute Scenarios

## Цель лекции
Научить студентов декомпозировать сложную предметную область с помощью методов Domain-Driven Design (DDD), выявлять ключевые бизнес-события через Event Storming и формализовать требования к качеству системы через Quality Attribute Scenarios.

## Ключевые сообщения
1. Предметная область определяет архитектуру — понимание бизнеса важнее выбора технологий
2. Единый язык (Ubiquitous Language) устраняет недопонимание между бизнесом и разработкой
3. Ограниченные контексты (Bounded Contexts) помогают управлять сложностью через разделение ответственности
4. Event Storming — быстрый способ совместного анализа домена с экспертами
5. Нефункциональные требования должны быть измеримыми (Quality Attribute Scenarios)
6. Границы контекстов часто становятся границами микросервисов и баз данных

## Целевая аудитория
- Студенты направления «Бизнес-информатика»
- ИТ-менеджеры и Product Owners
- Начинающие Solution Architects
- Специалисты, переходящие из разработки в архитектуру

## Кейс для hook
**Сервис каршеринга**: компания запускает платформу аренды автомобилей с функциями бронирования, телематики, оплаты, штрафов и поддержки клиентов. Проблема: разные отделы по-разному понимают сущности «Автомобиль», «Клиент», «Поездка», что приводит к ошибкам интеграции и дублированию данных.

## Основные термины
- Domain-Driven Design (DDD)
- Ubiquitous Language (Единый язык)
- Bounded Context (Ограниченный контекст)
- Context Map (Карта контекстов)
- Domain Event (Событие предметной области)
- Aggregate (Агрегат)
- Entity (Сущность)
- Value Object (Объект-значение)
- Event Storming
- Quality Attribute Scenario
- Functional Requirements (Функциональные требования)
- Non-Functional Requirements (Нефункциональные требования)

## Практика
Студенты проведут мини-сессию Event Storming для кейса «Сервис каршеринга»:
1. Опишут бизнес-цель и ключевых стейкхолдеров
2. Выявят доменные события (Domain Events)
3. Определят ограниченные контексты
4. Построят Context Map
5. Сформулируют Quality Attribute Scenarios для ключевых требований
6. Заполнят шаблон Architecture Brief с выделенными контекстами

## Визуальные материалы
1. Схема процесса: Бизнес-цель → Доменный анализ → Контексты → Требования → Архитектура
2. Пример Event Storming доски с цветными стикерами (ASCII/Mermaid)
3. Context Map для сервиса каршеринга (Mermaid)
4. Шаблон Quality Attribute Scenario (таблица)
5. Сравнение понимания сущности «Автомобиль» в разных контекстах

## Риски и анти-паттерны
- ❌ Единая модель данных на всю систему (игнорирование Bounded Contexts)
- ❌ Технические границы вместо бизнес-логических (разделение по слоям UI/Backend/DB)
- ❌ Размытые формулировки NFR («система должна быть быстрой»)
- ❌ Прямые JOIN между таблицами разных контекстов
- ❌ Event Storming без участия бизнес-экспертов
- ❌ Попытка максимизировать все NFR одновременно без приоритетов

## Мостик к Лекции 3
Выделенные ограниченные контексты станут основой для выбора архитектурных стилей. В Лекции 3 студенты узнают, как разные контексты могут требовать разных архитектурных подходов (монолит, микросервисы, модульный монолит) и как это влияет на выбор баз данных и интеграционных паттернов.
