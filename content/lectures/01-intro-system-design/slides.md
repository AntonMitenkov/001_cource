## Слайд 5. Проблема / Hook

**Кейс: розничная сеть запускает программу лояльности**

- 50 магазинов, бюджет ~5 млн руб., запуск за 3 месяца
- Цель: увеличить повторные покупки на 20%

**Что пошло не так?**
Команда выбрала «модную NoSQL БД» без анализа требований → потеря данных о баллах → репутационные риски

**Вывод:** System Design начинается с бизнес-цели, а не с технологии!

---

## Слайд 6. Что такое System Design

**System Design** — процесс проектирования архитектуры системы для удовлетворения требований

**Вопросы, на которые отвечает System Design:**
- Зачем строится система? (бизнес-цель)
- Кто будет использовать? (стейкхолдеры)
- Что система должна делать? (функциональные требования)
- Как система должна работать? (NFR)
- Какие есть ограничения? (бюджет, сроки, регуляторика)

---

## Слайд 7. Бизнес-цель как источник архитектуры

**Процесс перевода бизнес-цели в архитектуру:**

```
Бизнес-цель → Ограничения → Требования → Архитектурные решения → Технологии
```

**Важно:** Выбор технологии происходит **последним**, а не первым!

---

## Слайд 8. Архитектурные драйверы

**Архитектурный драйвер** — требование или ограничение, существенно влияющее на архитектуру

| Тип | Примеры |
|-----|---------|
| **Функциональные** | «Начислять баллы за покупки», «Интеграция с кассами» |
| **Нефункциональные (NFR)** | Производительность, доступность, надёжность, безопасность, масштабируемость |

**Пример NFR:** «95% запросов < 200 мс при нагрузке 1000 RPS»

---

## Слайд 9. Роль данных как ограничения

**Данные — это актив компании. Потеря данных = потеря денег и репутации.**

**Вопросы при проектировании:**
1. Какие данные нельзя потерять? (баланс баллов)
2. Какие данные требуют строгой согласованности? (транзакции)
3. Какие данные можно кэшировать? (каталог товаров)
4. Где находится источник истины?

**Важно:** Очередь сообщений ≠ База данных!

## Слайд 10. C4 System Context Diagram

**C4 Model Level 1** показывает систему в окружении пользователей и внешних систем

**Элементы:**
- 👤 **Person** — пользователь или роль
- 📦 **System** — наша система или внешний сервис
- 🔗 **Relationship** — взаимодействие (стрелка с подписью)

**Правило:** Никаких технологий внутри, только границы и связи!

---

## Слайд 11. Кейс: программа лояльности

**Стейкхолдеры:**

| Роль | Интерес | Требование |
|------|---------|------------|
| Клиент | Удобство, выгода | Быстрый доступ к балансу |
| Маркетинг | Рост продаж | Гибкость правил |
| ИТ | Стабильность | Простота поддержки |
| Бухгалтерия | Точность | Аудируемость |
| Руководство | ROI | Контроль бюджета |

**Ограничения:** бюджет ~5 млн руб., срок 3 месяца, 152-ФЗ

---

## Слайд 12. Управленческий вывод

**Trade-offs в архитектуре:**

| Решение | Выгода (+) | Потеря (-) |
|---------|------------|------------|
| **Быстрый запуск** (Managed) | Скорость | Долгосрочная стоимость |
| **Доступность 99.9%** | ~8 часов простоя/год | Стоимость инфраструктуры |
| **Доступность 99.99%** | ~52 минуты простоя/год | +3–5× к стоимости |

**Архитектура важнее технологии!** Технология — инструмент, архитектура — план.

## Слайд 13. Практика

**Задание:** Создать Architecture Brief + System Context Diagram

**Шаги:**
1. Описать бизнес-цель (1 абзац)
2. Определить стейкхолдеров (3–5 ролей)

**Время:** 30–40 минут

## Слайд 14. Ключевые термины

| Термин | Определение |
|--------|-------------|
| **System Design** | Проектирование архитектуры для удовлетворения требований |
| **Архитектурный драйвер** | Требование/ограничение, влияющее на решения |
| **Стейкхолдер** | Лицо/группа, влияющая на систему |
| **System Context Diagram** | C4 Level 1: система и внешние взаимодействия |
| **NFR** | Нефункциональное требование (как система работает) |
| **Source of Truth** | Единственное авторитетное хранилище данных |

## Слайд 15. Anti-pattern

❌ **Выбор технологии до понимания задачи**
> «Возьмём Kafka и Kubernetes, потому что модно!»

❌ **Очередь как база данных**
> Хранение баланса в очереди → потеря данных

❌ **Игнорирование ограничений**
> Проект без учёта бюджета и сроков

❌ **Максимизация всех NFR**
> «Хотим всё и сразу!» → бюджет превышен
