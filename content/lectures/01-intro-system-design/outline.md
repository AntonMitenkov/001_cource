# План Лекции 1

## Цель
Научить студентов переводить бизнес-цели в архитектурные требования и выявлять ключевые драйверы дизайна системы.

## Learning Objectives
По окончании лекции студенты смогут:
1. **Знать** определение System Design и его роль в разработке ИТ-решений.
2. **Понимать** связь между бизнес-целью и архитектурными решениями.
3. **Применять** технику выявления архитектурных драйверов.
4. **Анализировать** ограничения и требования стейкхолдеров.
5. **Создавать** System Context Diagram (C4 Level 1) для проекта.

## Тайминг
| Блок | Время (мин) | % от общего времени |
|------|-------------|---------------------|
| Hook (Введение) | 5 | ~6% |

| Case Study | 20 | ~25% |
| Связка с управленческими решениями | 15 | ~19% |
| Резюме и вопросы | 10 | ~13% |
| **Итого** | **80** | **100%** |

## Последовательность блоков

### 1. Hook (5 мин)
- Кейс: розничная сеть запускает программу лояльности.
- Вопрос: что может пойти не так, если начать с выбора технологии?
- Пример провала: компания выбрала модную NoSQL БД, но потеряла данные о транзакциях.

### 2. Теоретический блок (30 мин)
- Что такое System Design и зачем он нужен бизнесу.
- От бизнес-стратегии к техническим требованиям.
- Архитектурные драйверы: функциональные и нефункциональные.
- Роль данных как архитектурного ограничения.
- C4 Model: System Context Diagram (Level 1).
- Стейкхолдеры, ограничения, метрики успеха.

### 3. Case Study (20 мин)
- Разбор кейса программы лояльности.
- Выявление стейкхолдеров: маркетинг, ИТ, клиенты, бухгалтерия.
- Определение ограничений: бюджет, сроки, регуляторика (персональные данные).
- Выделение ключевых сущностей: клиент, карта лояльности, баллы, транзакция.
- Построение System Context Diagram.

### 4. Связка с управленческими решениями (15 мин)
- Как технические решения влияют на бюджет и сроки.
- Trade-offs: скорость запуска vs масштабируемость.
- Почему выбор архитектуры начинается до выбора технологий.
- Риски игнорирования NFR.

### 5. Резюме и мостик к Лекции 2 (10 мин)
- Ключевые выводы лекции.
- Вопросы для самопроверки.
- Анонс Лекции 2: предметная область, DDD, границы контекстов.

## Ключевые тезисы по блокам

### Hook
- System Design — это не про код, это про понимание бизнеса.
- Неправильный старт ведёт к потере данных и денег.

### Теория
- Бизнес-цель → Ограничения → Требования → Архитектура → Технологии.
- Архитектурный драйвер — это то, без чего система не достигнет цели.
- Данные — это актив, который нельзя потерять.
- System Context Diagram показывает, кто и как взаимодействует с системой.

### Case Study
- Стейкхолдеры имеют разные интересы: маркетинг хочет роста, ИТ хочет стабильности.
- Ограничения определяют архитектуру не меньше, чем требования.
- Потеря данных о клиентах = потеря репутации.

### Управленческие решения
- Выбор технологии до понимания задачи = технический долг.
- NFR влияют на стоимость: доступность 99.9% vs 99.99% — разница в цене примерно в 3–5 раз.
- Архитектура фиксируется в ADR (Architecture Decision Record).

## Практика
**Задание:** Создать Architecture Brief и System Context Diagram для кейса программы лояльности.

**Артефакты:**
1. Описание бизнес-цели (1 абзац).
2. Список стейкхолдеров (3–5 ролей).
3. Список ограничений (бюджет, сроки, регуляторика).
4. Ключевые сущности (5–7 элементов).
5. Требования к данным (что нельзя потерять, что требует согласованности).
6. System Context Diagram (Mermaid или ASCII).

**Критерии оценки:**
- Полнота анализа стейкхолдеров.
- Корректность выделения границ системы.
- Учёт ограничений в архитектуре.
- Качество диаграммы (читаемость, нотация).

## Переход к Лекции 2
Лекция 2 ответит на вопрос: «Как декомпозировать сложную систему на управляемые части?»
- Domain-Driven Design (DDD): домены, сабдомены, контексты.
- Event Storming для выявления событий и процессов.
- Quality Attribute Scenarios для формализации требований к качеству.
- Границы контекстов и взаимодействие между ними.
