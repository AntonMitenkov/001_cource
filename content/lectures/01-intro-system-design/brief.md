# Бриф Лекции 1

## Тема
Введение в System Design: от бизнес-цели к архитектурным драйверам

## Цель лекции
Научить студентов переводить бизнес-цели в конкретные архитектурные требования и выявлять ключевые драйверы дизайна системы.

## Ключевые сообщения
1. System Design начинается с понимания бизнес-цели, а не с выбора технологий.
2. Архитектурные драйверы — это требования и ограничения, которые существенно влияют на архитектуру.
3. Данные являются архитектурным ограничением: их нельзя потерять, они требуют согласованности.
4. System Context Diagram (C4 Level 1) показывает границы системы и внешние взаимодействия.
5. Выбор архитектуры происходит до выбора конкретных технологий и баз данных.

## Целевая аудитория
- Студенты направления "Бизнес-информатика"
- ИТ-менеджеры, Product Owners
- Начинающие Solution Architects
- Требуется: базовые знания информатики, понимание бизнес-процессов
- Не требуется: глубокие технические знания SQL или администрирования СУБД

## Кейс для hook
**Компания запускает программу лояльности для розничной сети.**

Ситуация:
- Розничная сеть из 50 магазинов хочет запустить единую программу лояльности.
- Бизнес-цель: увеличить повторные покупки на 20% за 6 месяцев.
- Ограничения: бюджет примерно 5 млн руб. на первый год, запуск за 3 месяца.
- Риски: потеря данных о клиентах недопустима, простои системы в часы пик критичны.

## Основные термины
- **System Design** — процесс проектирования архитектуры системы для удовлетворения требований.
- **Архитектурный драйвер** — ключевое требование или ограничение, влияющее на архитектурные решения.
- **Стейкхолдер** — лицо или группа, влияющая на систему или находящаяся под её влиянием.
- **System Context Diagram** — диаграмма C4 Level 1, показывающая систему и внешние взаимодействия.
- **NFR (Non-Functional Requirement)** — нефункциональное требование, описывающее как система должна работать.

## Практика
Студенты должны:
1. Описать бизнес-цель проекта.
2. Определить стейкхолдеров и их интересы.
3. Выявить ограничения (бюджет, сроки, регуляторика).
4. Выделить ключевые сущности будущей системы.
5. Определить, какие данные нельзя потерять.
6. Определить, какие данные требуют строгой согласованности.
7. Нарисовать System Context Diagram.
8. Заполнить Architecture Brief.

## Визуальные материалы
1. Схема влияния бизнес-цели на архитектуру:
   ```
   Бизнес-цель → Ограничения → Требования → Архитектурные решения → Технологии
   ```

2. Пример System Context Diagram в ASCII.

3. Пример System Context Diagram в Mermaid.

## Риски и анти-паттерны
- ❌ Выбор технологии до понимания бизнес-цели.
- ❌ Использование очереди сообщений как базы данных.
- ❌ Игнорирование ограничений (бюджет, сроки, команда).
- ❌ Попытка максимизировать все NFR одновременно без приоритетов.
- ❌ Утверждение, что одна технология подходит для всех задач.
