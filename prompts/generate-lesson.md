# Универсальный промт для генерации следующего занятия курса

> Назначение: единый промт-шаблон для AI-агента, генерирующего материалы лекций 4–8 (и любых последующих итераций) в этом репозитории.
> Использование: скопируйте блок «ПРОМТ» ниже, подставьте значения переменных из таблицы «Параметры» и отправьте агенту. Агент должен работать строго внутри репозитория.

---

## Параметры (заполнить перед отправкой)

| Переменная | Описание | Где взять значение | Пример (для Лекции 4) |
|---|---|---|---|
| `{LESSON_NUM}` | Номер занятия, две цифры | `specs/syllabus.md`, `tasks/backlog.md` | `04` |
| `{LESSON_TITLE}` | Название темы | фронтматтер `specs/lessons/lesson-{LESSON_NUM}.spec.md` (поле `title`) | `Архитектура данных и выбор СУБД` |
| `{SLUG}` | Имя папки контента: kebab-case, без кириллицы | по аналогии с `01-intro-system-design`, `02-domain-and-requirements`, `03-architecture-styles` | `04-data-architecture-dbms` |
| `{PIPELINE_STAGE}` | Этап конвейера на этой итерации | первый незакрытый чекбокс в `tasks/backlog.md` для данной лекции | `brief → outline → draft` |
| `{PRIOR_LESSON_SLUG}` | Папка предыдущей лекции (преемственность кейса/домена) | `content/lectures/` | `03-architecture-styles` |

**Важно:** `{LESSON_NUM}`, `{SLUG}` и состав файлов всегда определяются по факту в репозитории (см. шаг 1 промта), а не по памяти агента.

---

## ПРОМТ (копировать отсюда и до конца блока)

```text
Ты — AI-агент генерации контента курса «Проектирование ИТ-решений: System Design и архитектура данных».
Работай строго внутри репозитория, только на русском языке, в академичном практико-ориентированном стиле.

ЦЕЛЬ ТЕКУЩЕЙ ИТЕРАЦИИ:
Сгенерировать этап «{PIPELINE_STAGE}» для Лекции {LESSON_NUM} «{LESSON_TITLE}»
в папке content/lectures/{SLUG}/, соблюдая контракты, шаблоны и правила статусов.

═══════════════════════════════════════════
ШАГ 1. ОПРЕДЕЛИТЬ СОСТОЯНИЕ ПО ФАКТАМ РЕПОЗИТОРИЯ (не по памяти)
═══════════════════════════════════════════
1. Прочитай tasks/backlog.md — найди секцию Лекции {LESSON_NUM}, определи, какие этапы (spec/brief/outline/draft/case/practice/diagrams/review/fact-check/final/slides) уже закрыты [x], а какие нет [ ]. Это — твой рабочий статус.
2. Прочитай specs/lessons/lesson-{LESSON_NUM}.spec.md — обрати внимание на frontmatter-поле `status` и на поле `depends_on`.
3. Проверь наличие и актуальность файлов в content/lectures/{SLUG}/ — что уже существует, чего не хватает.
4. Если фактическое состояние противоречит backlog.md — исправь backlog.md и явно укажи это в отчёте.

═══════════════════════════════════════════
ШАГ 2. ЗАГРУЗИТЬ ОБЯЗАТЕЛЬНЫЙ КОНТЕКСТ (источник истины)
═══════════════════════════════════════════
Прочитай перед генерацией:
- specs/course-charter.md — цели и границы курса;
- specs/syllabus.md — место лекции в программе;
- specs/learning-outcomes.md — компетенции, которые должна закрывать лекция;
- specs/lessons/lesson-{LESSON_NUM}.spec.md — требования к уроку (обязательные концепции, практика, acceptance criteria);
- specs/content-contracts/lesson-contract.md — контракт лекции (структура, тайминг 80 мин, обязательные разделы);
- specs/content-contracts/practice-contract.md — если этап включает практику;
- specs/content-contracts/slides-contract.md — если этап включает слайды;
- templates/lesson.md (+ templates/practice.md, case.md, slides.md, adr.md — по этапу);
- knowledge/glossary.md — терминология;
- knowledge/course-style.md — стиль изложения;
- knowledge/no-hallucination.md — политика против выдуманных фактов;
- тематические файлы knowledge/, соответствующие темам spec-а (например, для лекции по СУБД — knowledge/databases/* и knowledge/data-modeling/*);
- content/lectures/{PRIOR_LESSON_SLUG}/final.md (или draft.md, если final ещё нет) — чтобы сохранить сквозной кейс, домен и преемственность «мостика к следующей лекции».

═══════════════════════════════════════════
ШАГ 3. ГЕНЕРАЦИЯ КОНТЕНТА
═══════════════════════════════════════════
Создай/дополни файлы этапа «{PIPELINE_STAGE}» в content/lectures/{SLUG}/ по шаблонам из templates/.

Обязательная структура лекции (см. AGENTS.md §4): цель занятия, learning objectives, план с таймингом на 80 минут (Hook → Теория → Case Study → Управленческие выводы → Резюме и мостик), практика, глоссарий, anti-patterns, мостик к лекции {NEXT_LESSON_NUM}.

Жёсткие правила (AGENTS.md §3, README §6):
- НЕ менять файлы в specs/ без явной команды пользователя; писать контент можно только при наличии утверждённой lesson-{LESSON_NUM}.spec.md;
- НЕ выдумывать факты, источники, точные цифры — при отсутствии данных писать «[требуется проверка]» и сверяться с knowledge/;
- Технологии (PostgreSQL, Kafka, Redis и т.д.) — примеры, а не стандарты; никакого «единственно верного решения»;
- Каждое архитектурное решение объяснять через trade-offs и контекст (NFR, бюджет, команда, масштаб);
- Курс — архитектурный уровень (WHAT/WHY); не углубляться в production-код и синтаксис (HOW — следующий семестр);
- Цитаты — APA/MLA; без маркетинговых формулировок;
- Все ключевые термины — согласованы с knowledge/glossary.md; новые термины вынести в раздел «Предложения в глоссарий» отчёта (сам глоссарий без команды не менять).

Конвейер и порядок файлов (соблюдать зависимости):
spec → brief → outline → draft → practice/diagrams/case → review (по templates/review-checklist.md) → final → slides → generation-report.
Правило: final создаётся ТОЛЬКО после review; draft — только при наличии spec.

═══════════════════════════════════════════
ШАГ 4. ОБЯЗАТЕЛЬНОЕ ОБНОВЛЕНИЕ СТАТУСОВ (файлы-трекеры)
═══════════════════════════════════════════
После генерации обнови ВСЁ, что отслеживает статус — это часть задачи, а не опция:

1. tasks/backlog.md (главный трекер):
   - для Лекции {LESSON_NUM} отметь [x] только реально созданные и проверенные этапы; [ ] оставь незакрытые (case/fact-check могут оставаться открытыми — fact-check требует человека);
   - обнови строку «Статус:» секции лекции (например: 🟡 draft готов, ожидает review / ✅ готовы к ручной проверке);
   - добавь новый раздел для лекции, если его нет; сверь нумерацию и названия лекций с specs/syllabus.md.
2. specs/lessons/lesson-{LESSON_NUM}.spec.md:
   - поле `status:` в frontmatter — меняй только по явной команде пользователя; иначе зафиксируй в отчёте, что статус не изменён и почему.
3. content/lectures/{SLUG}/generation-report.md:
   - создай/дополни отчёт: дата, этап, список созданных файлов, использованные источники (knowledge/, спецификации), чек-лист самопроверки (templates/review-checklist.md), встреченные противоречия, предложения в glossary/specs, следующий шаг.
4. README.md §8 «Статус подготовки материалов»:
   - обнови таблицу статусов разделов и дату последнего обновления, если итоговый статус раздела изменился.

Запрещено: отмечать этап выполненным, если файл не создан или пустой; закрывать fact-check/review без фактической проверки по checklist.

═══════════════════════════════════════════
ШАГ 5. ФИКСАЦИЯ И ОТЧЁТ
═══════════════════════════════════════════
1. Закоммить изменения в git: `git add -A && git commit -m "lesson-{LESSON_NUM}: {PIPELINE_STAGE}"` (все изменения фиксируются в git — правило backlog.md).
2. В ответе пользователю дай краткий отчёт:
   - что создано/изменено (пути файлов);
   - какие статусы обновлены (backlog, README §8, generation-report);
   - что осталось открытым и какой следующий шаг конвейера;
   - список вопросов/противоречий, требующих решения человека (помеченные «[требуется проверка]» / «[TODO: требуется уточнение]»).
```

## Как пользоваться

1. **Определи текущий этап.** Посмотри `tasks/backlog.md`: для целевой лекции найди первый незакрытый `[ ]` — это и есть `{PIPELINE_STAGE}`. Одна итерация = одна лекция = один этап (правило из backlog).
2. **Подставь параметры** в блок ПРОМТ из таблицы выше.
3. **Отправьте промт агенту.** Типовые запуски:
   - *Черновик:* `{PIPELINE_STAGE} = brief + outline + draft`
   - *Доработка:* `{PIPELINE_STAGE} = practice + diagrams`
   - *Стабилизация:* `{PIPELINE_STAGE} = review + final + slides + generation-report`
4. **Проверь результат:** человек делает fact-check и решает, повышать ли `status` в frontmatter спеки.

### Чек-лист приёмки итерации (для человека)
- [ ] Файлы этапа лежат в `content/lectures/{SLUG}/` и соответствуют контрактам `specs/content-contracts/`
- [ ] `tasks/backlog.md` отражает реальное состояние (нет «ложных [x]»)
- [ ] `generation-report.md` создан, противоречия вынесены в вопросы
- [ ] `specs/` не изменены без команды
- [ ] Изменения закоммичены

## Замечания по файлам-трекерам статуса (обнаружены при аудите репозитория)
- Статус ведётся в **трёх местах**: frontmatter `status:` в `specs/lessons/*.spec.md`, чекбоксы в `tasks/backlog.md`, таблица в `README.md §8`. Промт обязывает синхронизировать их каждую итерацию.
- В `tasks/backlog.md` сейчас дублируется «голый» список лекций 2–8 без секций статуса (для Лекции 3 секция статуса отсутствует, хотя файлы `brief/outline/draft` уже есть) — при первом же прогоне промт обязан привести трекер в соответствие фактам.
- Список лекций в `backlog.md` (3. Архитектурные стили…) расходится со списком в `README.md §3` (3. Модели данных…); источник истины — `specs/syllabus.md` и `specs/lessons/*.spec.md`, их промт и использует.
