# Контент-контракт: Практика (Practice Contract)

## Назначение

Этот документ задает требования к практическим заданиям курса.

Практика должна помогать студенту применять архитектурные решения, а не просто воспроизводить теорию.

---

## Цели практики

Практические задания курса должны:

1. Закреплять материал лекции.
2. Формировать практические навыки проектирования.
3. Создавать артефакты для итогового Architecture Blueprint.
4. Быть связанными с бизнес-контекстом.
5. Быть выполнимыми без глубокого программирования.
6. Подготавливать студентов к курсу «Базы данных».

---

## Область применения

Контракт применяется ко всем практикам:
- практикумы внутри лекций;
- сквозной проект;
- кейсы для групповой работы;
- задания для самостоятельной работы.

---

## Типы практических заданий

В курсе могут использоваться следующие типы практик:

1. **Анализ бизнес-контекста**
   - определение целей, стейкхолдеров, ограничений.

2. **Доменное проектирование**
   - выделение bounded contexts;
   - построение Context Map.

3. **Архитектурное проектирование**
   - выбор архитектурного стиля;
   - построение C4 Container Diagram.

4. **Проектирование данных**
   - создание концептуальной модели;
   - выбор классов СУБД;
   - заполнение Storage Selection Matrix.

5. **Проектирование интеграций**
   - проектирование очередей, брокеров, событий;
   - определение retry, DLQ, idempotency.

6. **NFR и надежность**
   - расчет нагрузки;
   - определение SLO, RTO, RPO;
   - выбор паттернов отказоустойчивости.

7. **Принятие решений**
   - сравнение альтернатив;
   - расчет TCO;
   - написание ADR.

8. **Финальная сборка**
   - подготовка Architecture Blueprint.

---

## Обязательные разделы практики

Каждая практика должна содержать следующие разделы:

1. **Цель практики**
   - какой навык формируется.

2. **Связь с лекцией**
   - к какой лекции относится практика.

3. **Кейс**
   - бизнес-ситуация или предметная область.

4. **Входные данные**
   - что дано студенту.

5. **Задание**
   - пошаговые действия студента.

6. **Ожидаемый результат**
   - какой артефакт должен получиться.

7. **Шаблон результата**
   - таблица, список, диаграмма, ADR, матрица.

8. **Критерии оценки**
   - как преподаватель или агент проверяет работу.

9. **Подсказки**
   - что можно использовать, если студент затрудняется.

10. **Типичные ошибки**
   - какие ошибки часто допускают студенты.

11. **Связь с итоговым проектом**
   - как результат практики входит в Architecture Blueprint.

---

## Требования к кейсам

Кейс для практики должен:

1. Быть понятным студенту бизнес-информатики.
2. Содержать бизнес-цель.
3. Содержать ограничения.
4. Содержать неопределенность, требующую архитектурного решения.
5. Не требовать программирования.
6. Допускать несколько возможных решений.
7. Быть связанным с темой лекции.

Рекомендуемые предметные области:
- маркетплейс;
- финтех;
- телемедицина;
- каршеринг;
- онлайн-образование;
- логистика;
- сервис бронирования.

---

## Требования к заданиям

Задание должно быть:

1. Конкретным.
2. Выполнимым за 30–60 минут.
3. Ориентированным на архитектурный результат.
4. Понятным без дополнительных устных объяснений.
5. Проверяемым по заранее заданным критериям.

Запрещено:

1. Давать задания в стиле «изучите тему».
2. Давать задания без ожидаемого артефакта.
3. Требовать писать производственный код.
4. Требовать администрирование реальной СУБД.
5. Давать задания, не связанные с лекцией.

---

## Допустимые студенческие артефакты

Практика может завершаться одним или несколькими артефактами:

- Architecture Brief;
- System Context Diagram;
- Domain Context Map;
- Quality Attribute Scenario;
- C4 Container Diagram;
- Conceptual Data Model;
- Storage Selection Matrix;
- Data Flow Diagram;
- Integration Architecture;
- Sequence Diagram;
- Event Catalog;
- Queue / Broker Design;
- NFR Sheet;
- Reliability / Security View;
- Trade-off Matrix;
- TCO Summary;
- ADR;
- Risk Register;
- Deployment View.

---

## Требования к уровню сложности

Уровень сложности должен соответствовать студентам бизнес-информатики.

Студент должен:
- анализировать;
- выбирать;
- обосновывать;
- рисовать верхнеуровневые схемы;
- сравнивать варианты;
- заполнять таблицы решений.

Студент не обязан:
- писать сложный код;
- настраивать Kubernetes;
- администрировать PostgreSQL;
- развертывать Kafka;
- оптимизировать SQL-запросы на продвинутом уровне.

---

## Требования к связи с курсом «Базы данных»

Практики должны постепенно готовить студента к курсу «Базы данных».

Для этого практики должны включать вопросы:

1. Какие сущности будут в системе?
2. Кто владеет данными?
3. Какие данные являются источником истины?
4. Какие данные являются производными?
5. Какой класс СУБД подходит под задачу?
6. Нужна ли сильная согласованность?
7. Допустима ли eventual consistency?
8. Каковы требования к backup, replication, security?
9. Каков ожидаемый объем данных?
10. Какова стоимость выбранного решения?

---

## Критерии оценки практики

Каждая практика должна иметь критерии оценки.

Рекомендуемые критерии:

1. Правильность понимания задачи.
2. Соответствие решения бизнес-цели.
3. Обоснованность архитектурного выбора.
4. Корректность терминологии.
5. Наличие требуемого артефакта.
6. Качество диаграмм или таблиц.
7. Учет ограничений.
8. Учет рисков.
9. Связь с материалом лекции.
10. Готовность результата для использования в итоговом проекте.

---

## Запреты для практик

В практиках запрещено:

1. Использовать одну СУБД как универсальное решение без обоснования.
2. Описывать очередь как полноценную замену базе данных.
3. Давать задания без бизнес-контекста.
4. Требовать точные технические настройки без цели.
5. Использовать технологии как самоцель.
6. Игнорировать стоимость и риски.
7. Создавать практики, не связанные с итоговым проектом.
